# Cross-DP 아키텍처 감사

**일자** 2026-09-15 · **대상** `doc-architect/` 전체 (DP1 / DP2 / DP3, 설계 문서 · 구현 UML · Configuration)

세 Design Point를 **개별 문서가 아니라 하나의 설계로 보고** 교차 감사한 결과다. 각 DP 안에서는 일관된 서술이 DP 경계를 넘을 때 어긋나는 지점, 그리고 세 DP가 공통으로 비어 있는 항목을 찾는 것이 목적이다.

**개별 DP의 설계 품질은 감사 대상이 아니다.** 후보 구조가 옳은지, QA 등급이 맞는지는 측정이 답할 문제이며 본 문서의 범위가 아니다.

## 2. 발견 상세

### 2.1 F1 — Demote와 Drop의 혼동 (높음, 수정됨)

**증상.** DP3는 회수를 일관되게 `Low Tier로 Eviction`이라고 썼다(§1 ③, C1·C2 개념, §5). 그런데 평가 지표는 `Fully Retained KV 대비 Task Accuracy`, `중요 KV 오분류율`을 포함했다.

**왜 문제인가.** KV를 하위 계층으로 **옮기면** 내용이 보존되므로 Attention 결과가 **비트 단위로 동일**하다. Accuracy는 떨어질 수 없다. 떨어지려면 KV를 **버려야** 한다. 즉 DP3의 핵심 Trade-off("System Efficiency ↔ Model Accuracy")가 서술된 동작 위에서는 성립하지 않았다.

**연쇄 효과가 크다.** 이 혼동을 방치했다면,

- 측정에서 Accuracy 손실이 0으로 나와도 **설계가 옳아서인지 지표가 틀려서인지 구분되지 않는다**
- DP1의 Demote가 만든 용량 이득이 **DP3의 성과로 집계된다** (기준선이 B0였으므로)
- 결국 DP3가 DP1과 같은 일을 다른 이름으로 하는 것이 된다

**수정.** DP3 §2.1에서 두 동작을 가르고 Drop만 DP3에 귀속시켰다. 기준선을 B1(Demote-only)로 바꿨고, `M-C5 Drop/Demote 분해`를 "DP3가 실제로 한 일의 크기"를 재는 지표로 넣었다. [ADR-004](adr/adr-004-demote-vs-drop.md)에 기록.

> **부수 효과 — DP3의 주장 범위가 줄었다.** B1이 이미 용량 제약을 해소하는 구성에서는 DP3가 불필요하다는 결론이 나올 수 있다. 이는 손실이 아니라 정확해진 것이며, 조건부 선정에 그대로 기술하면 된다.

### 2.2 F2 — 삭제된 수치를 계속 인용한다 (중간, 수정됨)

**증상.** DP1의 세 곳이 §4.4의 수치를 인용하는데 §4.4에 그 수치가 없다.

| 위치 | 인용 | 실제 |
|---|---|---|
| §5.4 (4) | "§4.4가 낸 **N ≈ 27**은" | `6825670`이 손익분기 유도(`164 + 3.4 N = 9.5 N → N ≈ 27`)를 삭제 |
| §11.2 M-P3 | "§4.4에서 보였듯 두 Mode가 **8.3배** 차이난다" | `dc035c0`이 `Mode A(11.93 ms) / Mode C(1.43 ms)` 비교를 삭제 |
| §11.6 Sweep | "§4.4 손익분기(**N≈27**)가 이 값에 걸려 있다" | 동상 |

**왜 문제인가.** §4는 명시적으로 **"본 장은 구조와 그 성립 조건만 다룬다. 수치를 기재하지 않는다"** 고 선언한다. 그 선언과 세 인용이 모순이며, **문서가 스스로 유도하지 않는 수치를 근거처럼 제시**하게 된다. 두 커밋(`6825670`, `dc035c0`)이 예측 성능을 걷어낼 때 인용 쪽을 함께 정리하지 않은 것이 원인이다.

**수정.** 세 곳에서 수치 주장을 걷어내고 의존 관계만 남겼다 — "§4.4의 손익분기가 이 값에 걸려 있다", "§3.3대로 비대칭이 크므로 두 Mode의 비용이 크게 갈린다 — 그 격차의 크기는 시뮬레이션이 답한다".

> **재발 방지.** 수치를 걷어낼 때 그 수치를 인용하는 곳을 함께 찾는 것이 규칙이 되어야 한다. 현재 문서량에서는 `grep`으로 충분하다.

### 2.3 F3 — 회수 실행 시점이 없다 (중간, 수정됨)

**증상.** DP1은 "결정 시점은 두 곳이다"로 못박고 각 지점의 후보 집합과 입력 특성까지 표로 구분한다. DP3에는 대응하는 절이 없었다 — C1/C2가 "언제 판단하는가"의 축이라는 것만 있고, **회수가 실제로 언제 실행되는지**가 없었다.

**왜 문제인가.** 실행 시점이 고정되지 않으면 **C1을 Admission 시점에, C2를 Step 경계에 돌린 뒤 "C1이 TTFT가 낫다"고 보고**할 수 있고, 그 차이가 평가 방식 때문인지 실행 시점 때문인지 분리되지 않는다.

**수정.** DP3 §2.3에서 축을 둘로 갈랐다 — 평가 시점(C1/C2)과 실행 시점(E1 Watermark / E2 Admission / E3 Step 경계 / E4 비활성 전환). §9.6에 "두 후보에 동일하게 고정한다"를 보고 원칙으로 넣었다.

**부수 소득.** 이 구분이 §5의 정성적 주장 두 개에 **구조적 근거**를 줬다.

- "C2의 Runtime Overhead가 크다" → C2는 Actual Query의 Attention을 봐야 하므로 평가가 **E3, 즉 Critical Path 위**에서 일어난다
- "C1이 선제적·공격적이다" → Importance가 이미 산출되어 있어 **E1·E2·E4를 자유롭게 쓸 수 있는 자유도**에서 나온다. 평가 방식 자체 때문이 아니다

### 2.4 F4 — DP1 결정점 B와 DP3가 겹친다 (높음, 수정됨)

**증상.** DP3의 E4(비활성 전환)는 DP1 §1의 **결정점 B**와 시점도 대상도 같다. 같은 순간 같은 세션의 KV를 두고 두 정책이 서로 다른 기준(재접근 시점 vs Attention Importance)으로 결정을 내리는데 **순서가 정의되어 있지 않았다.**

**왜 문제인가.** 두 결정의 무게가 다르다. Demote는 되돌릴 수 있고 Drop은 되돌릴 수 없다. 순서가 없으면 **강등만으로 해결됐을 KV를 버리는 경로**가 열려 있고, 그 손실은 복구되지 않는다.

**수정.** [ADR-005](adr/adr-005-dp1-before-dp3.md) — **DP1이 먼저, DP3는 그 결과가 용량 제약을 만족하지 못할 때만 개입한다.** DP3는 병렬 경로가 아니라 실패 처리 경로다. 구현에서는 `ReclaimCoordinator`가 두 정책을 아는 유일한 모듈이고, `dp3_kv_reclaim → dp1_kv_placement` 단방향 의존이 이를 구조로 고정한다.

> **측정상의 소득이 크다.** "DP1 배치 실패" 분기에 들어가는 빈도가 곧 **"이 구성에서 Drop이 필요하기는 한가"** 에 대한 답이 된다. 실행 통계로 직접 관측되므로 별도 실험이 필요 없다.

### 2.5 F5 — DP2 UML이 존재하지 않는 DP1 타입을 참조한다 (중간, 수정됨)

**증상.** DP2 구현 UML이 참조하는 DP1의 모듈·타입이 DP1 구현 UML에 없다.

| DP2가 참조 | DP1의 실제 |
|---|---|
| `dp1_placement/` | `dp1_kv_placement/` |
| `tiers.py`의 `MemoryTier` | `memories.py`의 `MemorySpec` |
| `TierStateView` | `MemoryStateView` |
| `vllm_shim.py`의 `Locality, Medium` | `vllm_shim.py` 없음. `Medium`은 `memories.py` |
| `PlacementEstimator` | 없음 (`PlacementExecutor`) |

DP2가 **"DP1과의 결합은 한 지점으로 제한한다"** 고 선언한 그 한 지점이 정확히 깨져 있었다. DP1 UML이 나중에 다시 쓰이면서(`a1cf817`~`e87f760`) 이름이 바뀌었고 DP2 쪽이 따라가지 않았다.

**추가로 드러난 것 — `MemoryTierKind`에 `CUSTOM_HBM`이 없다.** DP2는 `HBM / DRAM / CXL / HBF / SSD` 다섯 값만 갖는다. **[ADR-002](adr/adr-002-custom-hbm-separate-node.md)에 따라 Custom HBM은 별도 노드이고, 그 배치야말로 DP2의 Data Movement Cost를 가장 크게 바꾸는 요소**인데 DP2가 그것을 표현할 수 없었다.

**수정.** 참조를 DP1의 현재 이름으로 맞추고 `CUSTOM_HBM`을 추가했다. 또한 DP2가 자체 `MemoryTierKind`/`Locality`를 정의하면서 동시에 DP1 타입을 참조한다고 쓴 모순을 정리했다 — **DP2는 좁은 투영만 갖고 DP1의 `Medium`에서 매핑해 받는다**로 결합 지점을 하나로 명시했다.

### 2.6 F6 — DP2의 Cost Model이 KV 이동만 표현한다 (높음, **미해결**)

**이것이 남은 유일한 항목이며, 설계 판단이 필요하다.**

**증상.** DP2의 Data Access / Movement Cost는 다음과 같다.

```text
C_data(n) = f(KV Location, Memory Tier, BW, Transfer Path)
```

> "KV가 Candidate Node에서 Local한 경우 작아지고, Remote Memory 또는 다른 Node에 존재하는 경우 증가한다."

**즉 KV가 옮겨진다는 것을 전제한다.** 그런데 DP1은 그 전제를 두 곳에서 깬다.

**(1) DP1 §4.5 — 재활성 경로가 둘이다.**

| 경로 | 비용 구조 |
|---|---|
| 복원(Restore) | `KV bytes / 외부 대역폭` — 상위 계층 용량을 점유한다 |
| **스트리밍(Streaming)** | `max(KV bytes / 외부 대역폭, GPU Prefill 연산 시간)` — **Prefill이 연산 한계이므로 외부 대역폭이 충분하면 전송이 연산 아래로 숨어 추가 비용이 0에 수렴한다** |

`f(...)`가 단조 증가 함수로 서술되어 있어 **스트리밍의 `max` 구조를 담지 못한다.** 스트리밍이 성립하는 메모리에서는 "Remote이므로 비싸다"가 틀린 결론이 될 수 있다.

**(2) DP1 결정점 A — KV가 연산형 메모리에 상주할 수 있다.** Mode C에서 KV는 Custom HBM 노드나 CXL-PNM에 있고 **Attention이 그 자리에서 수행된다.** DP2가 다루는 것은 Prefill이고 Prefill은 GPU 고정([ADR-001](adr/adr-001-prefill-gpu-pinning.md))이므로 KV가 GPU 쪽으로 와야 하지만, **그 KV의 출발점이 "Decode Attention을 수행 중인 연산형 메모리"라는 상태가 `KV Location`으로 표현되는지**가 불분명하다.

**확인한 사실.** DP2 설계 문서에서 "오프로드"는 **1회** 등장하며 그마저 *"지연에 덜 민감한 요청을 여유 P Node로 오프로드"* 라는 무관한 용법이다. DP2 구현 UML에는 0회다. **DP2는 DP1 §4의 실행 구조를 알지 못한 채 작성되었다.** DP2에 "결정점"이라는 단어도 0회 등장한다.

**왜 높음인가.** DP2의 목적함수 자체가 영향을 받는다. `argmin C(n)`에서 `C_data`가 틀리면 선택되는 노드가 달라지고, **C2(Cost-aware)의 존재 이유가 정확한 Cost 계산이므로 이 오차는 C1/C2 비교 결과를 직접 뒤집을 수 있다.**

**권고 — 세 가지 중 택일.** 어느 쪽이든 작성자의 설계 판단이며 본 감사에서 임의로 정하지 않았다.

| 안 | 내용 | 비용 |
|---|---|---|
| **A. `C_data`를 분해한다** (권장) | `C_data = min(C_restore, C_stream)`로 두고 `C_stream = max(전송, GPU 연산)`을 명시. `KV Location`에 `ReactivationMode`(Resident / Restore / Attention Offload)를 추가 | Cost Model 절 개정. DP2 UML의 `MemoryLocation`에 필드 1개 추가 |
| **B. 범위를 명시적으로 좁힌다** | "DP2는 DP1이 Mode A/B로 배치한 KV만 대상으로 한다"고 비목표에 적는다 | 정직하지만 DP1 결정점 A가 활성인 구성에서 DP2를 쓸 수 없다 |
| **C. 현행 유지** | `f(...)`가 스트리밍을 포함한다고 간주 | **권장하지 않음** — 함수가 명세되지 않아 구현자마다 다르게 해석한다 |

> **A를 권한다.** DP1 §4.5가 이미 두 경로의 비용식을 갖고 있으므로 새로 유도할 것이 없고, 필요한 것은 DP2가 그 구분을 입력으로 받는 것뿐이다. **DP2의 프로토타입 결과(`dp2-prototype-results.md`)가 이 Cost Model 위에서 측정되었다면, 유효 범위에 "Mode A/B 배치 한정"을 병기해야 한다.**

### 2.7 F7 · F8 — 공통 누락 (수정됨)

- **F7.** 세 DP가 전제로 깔고 있으나 기록되지 않은 결정이 7건 있었다. 그중 둘은 이미 한 번 번복된 것이었고(결정점 하나 → 둘, Custom HBM on-package → 별도 노드) **번복의 근거가 본문 서술에만 남아 있었다.** `adr/` 7건으로 고정했다.
- **F8.** DP1·DP2는 구현 UML을 갖고 있었으나 DP3는 없었다. 설계 문서의 주장이 구조 수준에서 재확인되지 않은 상태였으며, `dp3-implementation-uml.md`로 채웠다.

## 3. 세 DP를 관통하는 구조적 관찰

발견이 아니라 **설계가 실제로 어떤 모양인지**에 대한 관찰이다.

### 3.1 세 DP는 독립 최적화 문제가 아니며, 그 결합이 단방향이다

README는 "세 DP는 독립적인 최적화 문제가 아니다"라고 쓴다. 감사 결과 그 결합은 **방향이 있다.**

```text
   ADR-001 (Prefill GPU 고정)
        │
        ▼
   DP1 §4 실행 구조 (Attention 오프로드 성립 범위)
        │
        ├──────────────────► DP2  : Prefill 노드 선택의 비용 구조를 정한다  ← F6이 여기서 끊겨 있다
        │
        └──────────────────► DP3  : Demote로 충분한 범위를 정한다 (§2.2 (b))
                                    → 연산형 계층 용량이 클수록 DP3가 불필요해진다
```

**DP1의 메모리 구성이 DP2와 DP3의 성립 범위를 동시에 정한다.** 따라서

- **DP2·DP3의 결과는 DP1 Configuration을 병기하지 않으면 해석 불가능하다.** 두 문서의 보고 원칙에 이를 명시해야 한다 (DP3 §9.6에는 반영했다).
- **DP3의 Sweep에는 반드시 연산형 계층 용량이 들어가야 한다.** 이 축을 고정하면 "DP3가 필요한가"라는 선행 질문에 답할 수 없다.

### 3.2 "회수"라는 단어가 세 가지를 가리켰다

F1의 일반화다. 세 DP에서 KV를 하위 계층으로 보내는 동작이 서로 다른 것을 뜻했다.

| DP | 동작 | 트리거 | 되돌릴 수 있는가 |
|---|---|---|---|
| DP1 결정점 B | Demote | 수요 소멸 (이 KV가 지금 안 쓰인다) | ✅ |
| DP1 선점(Preemption) | Demote 또는 재계산 | Scheduler의 자원 압력 | ✅ / ❌ |
| DP3 | **Drop** | 공급 부족 (DP1이 배치에 실패) | ❌ |

**세 번째 행이 나머지와 다르다는 것이 드러나지 않고 있었다.** 특히 **Recompute 기반 선점은 DP3와 거의 같은 동작**(버리고 나중에 재계산)이며, 차이는 버릴 대상을 Attention Importance로 고르는가 Request 단위로 통째로 고르는가뿐이다. **Recompute 선점을 켠 채 측정하면 DP3의 고유 기여가 분리되지 않는다** — DP3 §9.6.1에 고정 규칙으로 반영했다.

### 3.3 세 DP 모두 "정책 없음" 대조군을 충분히 쓰지 않는다

DP1 §11.4는 "C1–C2 간 격차보다 **정책이 있는가 없는가**의 격차가 훨씬 클 가능성이 높다"고 적고 Maintainability에 한해 As-Is 대조군을 요구한다. **이 통찰은 Maintainability에만 적용될 이유가 없다.**

세 DP 모두 후보 둘을 비교하는 구조인데, **"그 결정 자체가 필요한가"** 를 묻는 대조군이 Performance 지표에는 약하게만 들어가 있다. DP3는 이번에 B1으로 이를 명시했다(§9.2). **DP1과 DP2에도 같은 질문이 유효하다.**

| DP | "결정이 필요한가"를 묻는 대조군 | 어디에 선언되어 있는가 |
|---|---|---|
| DP1 | As-Is (HBM 우선 + 순차 Spill) | **설계 문서** §11.6 |
| DP2 | `AlwaysLocalPolicy` (항상 `D_current`에서 실행) | **프로토타입 명세** — 설계 문서에는 없다 |
| DP3 | B1 (Demote-only) | **설계 문서** §9.2 (이번에 추가) |

**세 DP 모두 대조군을 갖고 있다.** DP2도 `AlwaysLocalPolicy`를 As-Is 기준선으로 삼아 1.0으로 정규화하며, *"이 프로토타입이 증명할 수 없는 최적해를 분모로 쓰지 않는다"* 는 근거까지 적어 두었다.

**남는 것은 선언 위치의 차이뿐이다.** DP2만 기준선이 프로토타입 명세에 있고 설계 문서에는 없다. 설계 문서만 읽는 사람에게는 "이 결정이 필요한가"라는 질문이 보이지 않으므로, **설계 문서 쪽에 한 줄 참조를 두는 편이 낫다.** 설계 변경이 아니며 우선순위도 낮다.

### 3.4 문서 간 참조가 검증되지 않는다

F2와 F5는 원인이 같다 — **문서 A가 문서 B의 내용을 인용하는데 B가 바뀌어도 A가 따라가지 않는다.** 현재 문서량(`doc-architect/` 최상위 11개, 약 6,100줄)에서는 사람이 놓친다.

세 DP의 설계 문서가 서로를, 그리고 자기 자신의 절을 참조하는 횟수가 많다(`§` 참조가 DP1 한 문서에만 180회). **최소한 다음 두 가지는 기계로 확인할 수 있다.**

| 검사 | 방법 |
|---|---|
| 내부 절 참조가 존재하는 절을 가리키는가 | 헤딩 목록과 `§n.m` 참조를 대조 |
| mermaid 블록이 렌더되는가 | `mmdc`로 전체 파싱 — `c205804`의 선례 |

이번 감사에서 mermaid 28블록은 전수 검증했다(전부 통과). **절 참조 검증은 아직 자동화되어 있지 않다.**
