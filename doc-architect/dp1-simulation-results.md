**대상** [`dp1-heterogeneous-memory-data-placement.md`](dp1-heterogeneous-memory-data-placement.md) §7의 C1/C2
**구현** [`dp1_sim/`](dp1_sim/) — 구현 UML의 클래스 구조를 그대로 코드로 옮긴 이산 사건 시뮬레이터
**원자료** [`dp1_sim/results.json`](dp1_sim/results.json) · [`dp1_sim/static_metrics.json`](dp1_sim/static_metrics.json)

> **설계 문서 §11의 평가 가정은 쓰지 않았다.** 물리 모델(§4)과 Configuration(§3.4)만 가져오고, 워크로드·시나리오·별점 기준은 본 문서에서 독립적으로 정의한다.

> **정책 비용의 회계 범위.** Performance의 모든 시간 지표(TTFT·TPOT·Goodput·꼬리)에 **정책 결정 시간과 데이터 이동 시간이 포함되어 있다.** 결정점 A의 판단·이동은 Decode 시작을 막고, 결정점 B의 판단·이동은 유휴 시간과 겹치되 유휴보다 길면 그 초과분이 **다음 턴의 TTFT로 이월**된다. 이 회계가 결론을 바꾸므로 §3.4에 따로 적었다.
>
> **Endurance는 평가 축에서 뺐다.** 저내구성 매체(HBF)의 수명은 실제 배치 결정에서 우선순위가 낮다는 판단에 따라, 내구성을 고려해 매체를 고르는 논리도 넣지 않았고 QA 축으로도 세지 않는다. 구현의 `endurance_headroom_of()`는 어느 정책도 호출하지 않는다.

## 1. 요약 — 별점

각 QA를 3점 만점으로 평가한다. **임계값의 근거는 §4에 있다.** As-Is(HBM 우선 + 순차 Spill)를 함께 평가하는 이유는, C1–C2 간 격차보다 "정책이 있는가 없는가"의 격차가 더 클 수 있기 때문이다.

| QA | 측정 지표 | As-Is | C1 (메모리 특성) | C2 (Data 특성) |
|---|---|:---:|:---:|:---:|
| **Performance** — 처리량 | SLO-제약 Goodput (As-Is=1.0) | 기준선 | ★★☆ `1.31x` | ★★☆ `1.37x` |
| **Performance** — 시간 | SLO Attainment | ★☆☆ `0.644` | ★★☆ `0.888` | ★★☆ `0.917` |
| **Performance** — 꼬리 안정성 | 부하 급변 시 `ttft_p99` 팽창률 | ★★☆ `2.33x` | ★★☆ `3.00x` | ★☆☆ `12.2x` |
| **Performance** — 정책 오버헤드 | (결정+이동) ÷ 턴 시간 | ★★★ `0.09%` | ★★★ `5.7%` | ★★☆ `17.9%` |
| **Performance** — 자원 | HBM 유휴 KV 감소율 | ★☆☆ `0%` | ★★★ `95.6%` | ★★★ `96.6%` |
| **Flexibility** | M-F1 신규 메모리 지원 수 | ★☆☆ `0/4` | ★★☆ `2/4` | ★★☆ `3/4` |
| **Maintainability** | McCabe 순환복잡도 | ★★★ `4` | ★★★ `2` | ★☆☆ `30` |

### 한 줄 결론

> **기본 구조는 C1이다.** C2는 18개 셀 중 4개에서만 유의하게 앞서고, 그 밖의 구간에서는 지는 정도가 아니라 **무너진다** — Burst 고부하에서 C2의 SLO Attainment는 0.203으로 C1의 0.348보다 낮고 `ttft_p99`는 177.8초로 C1의 40.3초의 4.4배다.

**두 후보의 실패 모드가 서로 다르고, 그것이 선택 기준이 된다.**

| | C1의 실패 모드 | C2의 실패 모드 |
|---|---|---|
| 무엇이 | **TPOT** (Decode step 예산) | **TTFT** (재활성 지연) |
| 왜 | 후보를 좁히지 않고 argmax를 하므로 **가장 좋은 오프로드 매체 한 곳에 91~92%가 몰린다.** 그 매체의 대역폭이 포화하면 step 예산(50 ms)을 넘긴다 | 분류 결과를 따라 연산 불가 매체까지 퍼뜨린다. 부하가 급변하면 그 KV가 **Mode B(전량 복원)** 로 돌아오고, 이동이 유휴 안에 숨지 못해 다음 턴을 밀어낸다 |
| 언제 | 유휴가 길고 부하가 꾸준할 때 (`agent_swarm` 고부하: `tpot_p99` = 예산의 **98%**) | 부하가 급변하거나 과부하일 때 (Burst 고부하: Mode B 비중 **38.0%**, C1은 0.0%) |
| 얼마나 | Goodput이 As-Is **아래**로 내려간다 (47.4 vs 57.2) | Goodput −22%, SLO −0.145 (CI [−0.214, −0.076]) |

C1의 실패는 **점진적**이고 C2의 실패는 **급격**하다. 과부하 ×12에서도 C1의 정책 오버헤드는 18.0%에 머무는 반면 C2는 **72.7%** — 턴 시간의 3/4을 데이터 이동에 쓴다.

## 2. 구현

구현 UML의 모듈 구조를 그대로 따랐다. 파일명이 UML의 모듈명과 1:1 대응한다.

| 파일 | 내용 | UML 대응 |
|---|---|---|
| `core.py` | `MemorySpec` · `ModelShape` · `MemoryStateView` · `QueueStateView` · `LinkCostModel` | §2.1 공통 |
| `policy.py` | `PlacementPolicy` · `TierScorer` · `FeasibilityFilter` · `PlacementExecutor` | §2.1 공통 |
| `analyzer.py` | `KVCharacteristicAnalyzer` · `KVClassifier` · `PlacementPolicyTable` + 세 추정 모델 | §2.3 C2 전용 |
| `policies/c1_memory_centric.py` | `MemoryStateCollector` → `PlacementPlanner` | §2.2 |
| `policies/c2_data_centric.py` | `MemoryStateAwareRefiner` | §2.3 |
| `policies/as_is.py` | 고정 Spill 순서 | 기준선 |
| `engine.py` | 이산 사건 엔진. **GPU 점유와 메모리 점유를 별도 자원으로 두고 `max`로 합친다** | §4.6 |

### 구현에서 확인된 설계 문서의 주장

- **§4.6 자원 병렬화가 실제로 측정된다.** As-Is의 자원 병렬도는 `1.016`(사실상 직렬)인 반면 C1은 `1.57`, C2는 `1.63`이다. `max`를 `sum`으로 바꾸면 이 차이가 사라진다.
- **§4.4의 네 조건이 후보를 가른다.** `ssd_pim`은 `SOFTMAX` 미지원으로 Mode C 대상에서 탈락하고, 기본 구성에서 오프로드가 성립하는 것은 `custom_hbm`과 `cxl_pnm` 둘뿐이다.
- **C1은 `analyzer` 모듈을 import하지 않는다.** 추정 오차가 도달할 경로가 구조적으로 없다.

### 구현 중 내린 판단 두 가지

UML 검수(`dp1-implementation-uml-review.md`)가 미해결로 남긴 항목을 구현에서 결정해야 했다.

- **U3 (`FeasibilityFilter` 호출 주체)** — 권고안 A를 채택했다. `PlacementManager`가 정책 호출 **전에** 적용하므로 두 후보가 동일한 후보 집합을 받는 것이 보장된다. 이것 없이는 후보 범위 차이가 정책 차이로 오인된다.
- **U6 (`PlacementPolicyTable`의 신규 메모리 편입)** — `Medium`을 열거하지 않고 **메모리의 성질로 일반 판정**하도록 구현했다. 그 결과가 §5.6의 M-F1 측정값이다.

## 3. 실험 설계

### 3.1 워크로드 — opencode 8종 툴

opencode의 permission 대상 툴은 `bash·read·edit·glob·grep·webfetch·task·todowrite·websearch·lsp·skill` 이다. 이 중 **실행 시간 특성이 서로 구분되는 8종**을 골랐다. 제외 사유: `todowrite`는 실질 0초라 유휴가 생기지 않고, `websearch`는 `webfetch`와, `lsp`는 `read`와, `skill`은 `task`와 같은 등급이다.

| 툴 | 중앙값 | σ(log) | 결과 토큰 | 근거 |
|---|---:|---:|---:|---|
| `read` | 0.02s | 0.5 | 2000 | 로컬 파일 읽기. 페이지 캐시 유무로 수 ms~수십 ms |
| `write` | 0.04s | 0.5 | 50 | 쓰기 + fsync. 읽기보다 비싸나 여전히 로컬 I/O |
| `edit` | 0.06s | 0.6 | 200 | 매칭 후 부분 치환 — 읽기와 쓰기를 모두 포함 |
| `glob` | 0.15s | 0.8 | 400 | ripgrep 파일 순회. 레포 크기에 비례 |
| `grep` | 0.40s | 1.0 | 800 | ripgrep 내용 스캔. 순회보다 무겁다 |
| `webfetch` | 1.20s | 0.9 | 3000 | 네트워크 왕복 + 본문 변환 |
| `bash` | 1.50s | **1.6** | 600 | 서브프로세스. ls 수 ms ~ 테스트 수십 초 — **분산 최대** |
| `task` | 25.0s | 1.2 | 1000 | 서브에이전트. 내부에서 LLM 호출이 여러 번 |

실행 시간은 lognormal을 쓴다 — 소프트웨어 실행 시간은 하한이 0이고 오른쪽 꼬리가 길다. **절대값은 ASSUMED이지만 상대 순서(로컬 I/O < 검색 < 네트워크 < 서브프로세스)는 근거가 있으며**, 절대값이 결론을 바꾸는지는 §6.1의 Sweep이 확인한다.

### 3.2 시나리오 6종 × 부하 3수준

| 시나리오 | 툴 믹스 특징 | Context | 유휴 중앙값 | 의도 |
|---|---|---:|---:|---|
| `interactive_coding` | read/edit/grep 65% | 16K | 0.055s | 유휴가 짧아 하위 계층 왕복을 회수할 시간이 없다 |
| `deep_research` | webfetch/task 60% | 48K | 0.698s | 유휴가 길어 깊은 계층이 값을 한다 |
| `build_test_loop` | bash 55% | 24K | 0.268s | 같은 툴 아래 실행 시간 분산이 가장 크다 |
| `agent_swarm` | task 45% | 64K | 1.956s | 유휴가 수십 초 — 가장 깊은 계층까지 성립 |
| `mixed_uniform` | 8종 균등 | 32K | 0.165s | 한 세션 안에서 유휴가 자릿수로 널뛴다 |
| `long_context` | 혼합 | 96K | 0.168s | 세션당 KV가 커 용량 압력이 지배적 |

부하는 도착률 배수로 **low(×1) / mid(×4) / high(×6)** 세 수준을 둔다. 세션은 Poisson 도착하고 각 턴은 `Incremental Prefill(GPU 고정) → 결정점 A → Decode → 결정점 B → 유휴`를 거친다.

### 3.3 판정 규칙 (실행 전 고정)

- **워크로드를 정책과 무관하게 먼저 생성한다.** 정책마다 난수 소비 순서가 달라지면 같은 seed라도 서로 다른 워크로드를 보게 되어 짝지은 비교가 무효가 된다. 세 정책은 완전히 같은 trace를 소비한다.
- **동일 seed에서 짝지어(paired) 비교하고, 95% 신뢰구간이 0을 지나면 "차이 없음"으로 판정한다.** 점 추정의 부호로 판정하지 않는다.
- **Goodput의 분모는 horizon(400초)으로 고정한다.** 정책마다 마지막 이벤트 시각이 다르므로 그것을 분모로 쓰면 처리량 비교가 성립하지 않는다.
- **최초 턴은 SLO 판정과 Goodput 분자에서 제외한다.** 배치 결정 **이전**이므로 대조군으로만 쓴다 (설계 문서 §11.2 M-P2).
- seed 24개, horizon 400초.

### 3.4 정책 비용이 시간에 들어가는 방식

이 회계가 결과를 좌우하므로 명시한다 (`engine.py:260-359`).

```
TTFT      = (이전 턴 이월 stall) + 복원 시간 + Incremental Prefill
GPU 점유  = 복원 + Prefill + [결정 A 판단] + [결정 A 이동] + Decode
메모리 점유 = 복원 + 오프로드 Attention   ... 턴 시간 = max(GPU, 메모리)
결정 B    : deact = [결정 B 판단] + [결정 B 이동]
            이월 stall = max(0, deact − 유휴 시간)      ← 다음 턴 TTFT에 더해진다
            이동은 대상 메모리의 대역폭도 점유한다
```

- **결정점 A의 비용은 숨길 곳이 없다.** Decode 시작을 막으므로 그대로 턴 시간에 더해진다.
- **결정점 B의 비용은 유휴에 숨을 수 있다.** 다만 유휴보다 길면 그 초과분이 다음 턴의 TTFT가 된다. **이것이 C2의 꼬리 실패 모드를 만드는 경로다.**
- 결정 **판단** 자체는 두 후보 모두 무시할 수준이다 — 턴당 C1 `24 µs`, C2 `31 µs`로 턴 시간의 0.01% 미만. **비용은 판단이 아니라 이동에 있다:** 턴당 중앙값 C1 `50 ms`, C2 `132 ms` (최대 C1 `270 ms`, C2 `384 ms`).

## 4. 별점 기준 — 임계값과 근거

### 4.0 먼저: 측정 노이즈의 크기

임계값이 노이즈보다 커야 의미가 있으므로, 먼저 본 실험의 재현성을 측정했다.

```
Goodput의 seed 간 변동계수(CV)    중앙값 0.210  (p90 0.362)
24-seed paired 비교의 최소검출차   1.96 × 0.210 / √24 = 0.084  →  8.4%
```

**따라서 8.4%보다 작은 차이는 본 실험에서 재현되지 않는다.** 이 값이 아래 임계값들의 하한 근거가 된다.

### 4.1 Performance — 처리량 (SLO-제약 Goodput)

정규화: As-Is = 1.0. 대표값은 **중부하·고부하 12개 셀의 중앙값**을 쓴다(저부하는 세 정책이 동일해 배치 결정이 실재하지 않는 구간이므로 제외).

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 1.10x` | 24-seed 최소검출차가 8.4%이므로 10%는 그것을 안전하게 넘는 최소 크기다. 이보다 작으면 재현되지 않는다 |
| ★★☆ | `1.10x ~ 2.00x` | 유의한 개선이지만 장비 대수를 바꾸지 못한다 |
| ★★★ | `≥ 2.00x` | **같은 SLO에서 처리량 2배 = 필요 장비 절반.** 하드웨어 투자 결정을 뒤집는 크기이므로 만점의 기준으로 삼는다 |

### 4.2 Performance — 시간 (SLO Attainment)

SLO는 `재활성 TTFT ≤ 2.0s AND TPOT ≤ 50ms`. Attainment는 SLO를 만족한 출력 토큰의 비율이다. TTFT에는 §3.4의 이월 stall이 포함된다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 0.80` | 다섯 요청 중 하나 이상이 SLO를 놓치는 수준. 대화형 서비스의 체감이 무너지는 하한 |
| ★★☆ | `0.80 ~ 0.95` | 대다수를 만족하나 목표 미달 |
| ★★★ | `≥ 0.95` | 대화형 서비스의 통상적 SLO 목표(p95)를 달성 |

### 4.3 Performance — 꼬리 안정성

**부하가 급변할 때 꼬리가 얼마나 팽창하는가.** 같은 시나리오(`mixed_uniform`)·같은 도착률에서 Burst 도착 조건의 `ttft_p99` ÷ 정상 도착 조건의 `ttft_p99`. 세 부하 수준의 중앙값.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `> 5x` | 부하 변동을 흡수하지 못하고 꼬리가 자릿수로 튄다. 용량 계획이 불가능해진다 |
| ★★☆ | `2x ~ 5x` | 팽창하지만 예측 가능한 범위 |
| ★★★ | `≤ 2x` | 부하 변동을 흡수했다고 볼 수 있는 수준 |

> **이 지표는 절대값과 함께 읽어야 한다.** As-Is의 팽창률이 가장 낮지만(2.33x), 그것은 정상 조건에서 **이미** p99가 8.8초로 나빠 더 나빠질 여지가 적기 때문이다. 팽창률만 보면 As-Is가 가장 안정적이라는 잘못된 결론이 나온다.

### 4.4 Performance — 정책 오버헤드

`(결정 판단 시간 + 데이터 이동 시간) ÷ 턴 시간`. **토큰을 만들지 않는 시간의 비율**이다. 중부하·고부하 12개 셀의 중앙값.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★★★ | `≤ 8.4%` | §4.0의 최소검출차와 같은 값. 오버헤드가 이보다 작으면 **그것만으로는 측정 가능한 처리량 차이를 만들 수 없다** |
| ★★☆ | `8.4% ~ 20%` | 측정 가능한 비용이지만 장비 대수를 바꾸지는 않는다 |
| ★☆☆ | `> 20%` | 같은 토큰을 내려면 `1/(1−0.2) = 1.25배`의 장비가 필요해진다. **하드웨어 조달 단위의 비용**이므로 §4.1의 ★★★ 기준(2배 = 장비 절반)과 같은 축에서 최하점으로 둔다 |

### 4.5 Performance — 자원 (HBM 유휴 KV 감소율)

`1 − (후보의 HBM 유휴 KV 평균 ÷ As-Is의 HBM 유휴 KV 평균)`. **이 DP의 직접적 개선 대상**이다. 고부하 6개 시나리오의 중앙값.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 50%` | 절반도 줄이지 못하면 계층을 쓰는 이유가 약하다 |
| ★★☆ | `50% ~ 90%` | 부분적 해결 |
| ★★★ | `≥ 90%` | 유휴 KV가 HBM의 10% 미만만 점유한다. HBM 192 GiB 기준 **평균 세션 하나(약 10 GB)분 이하**이므로 "문제가 해소됐다"고 볼 수 있다 |

### 4.6 Flexibility (M-F1)

기존 6종이 갖지 못한 특성 조합을 하나씩 대표하는 신규 메모리 4종을 투입하고, **Configuration 교체만으로 실제 배치가 발생하는지** 센다. 투입 세트는 실행 전에 고정했고 사후에 바꾸지 않았다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `0~1 / 4` | 대부분의 새 특성을 활용하지 못한다 |
| ★★☆ | `2~3 / 4` | 일부만 활용 |
| ★★★ | `4 / 4` | 투입 4종이 각각 다른 특성 축을 대표하므로, 전부 써야 "정책이 적응했다"고 말할 수 있다 |

계수 규칙(설계 문서 §11.3): 배치 bytes = 0이면 **미지원**(존재를 견딘 것이지 적응이 아니다). 코드 수정 없이 배치가 발생하면 지원.

### 4.7 Maintainability — McCabe 순환복잡도

정책 결정 경로의 순환복잡도(분기 수 + 1)를 구현 코드에서 AST로 센다. 공통 인프라는 셋 다 쓰므로 제외하고 **그 정책 때문에 존재하는 코드**만 센다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★★★ | `CC ≤ 10` | McCabe(1976)의 원 권고. 단순하고 테스트 가능한 구간 |
| ★★☆ | `CC 11 ~ 20` | 보통 |
| ★☆☆ | `CC > 20` | **NIST SP 500-235가 "복잡·위험" 으로 분류하는 구간.** 20을 넘으면 모든 분기를 테스트로 덮는 비용이 급증한다 |

> 임계값을 임의로 정하지 않고 널리 인용되는 외부 기준을 그대로 쓴다. 이 QA는 대리 지표이므로 자체 기준을 만들면 근거가 순환하게 된다.

#### (1) C1은 한 매체에 몰아서 TPOT를 깨뜨린다

## 7. 선택 규칙

### 7.1 두 조건의 논리곱

§5.3의 두 실패 모드를 그대로 판정식으로 옮기면 다음이 된다.

```
C2를 쓸 조건 =  ①  C1의 tpot_p99 > Decode step 예산의 40%
            AND ②  턴당 유휴 시간의 중앙값 > C2의 턴당 이동 시간
```

- **①은 "C1이 실패하는가"** — C1이 한 매체에 몰아서 step 예산에 접근하고 있어야, 후보를 좁혀 부하를 쪼갤 이유가 생긴다. 40%를 경계로 둔 것은 §6.1·§6.3에서 우열이 갈리는 지점이 모두 이 근처이기 때문이다(비유의 구간 33~42%, 유의 구간 52~71%).
- **②는 "C2가 실패하지 않는가"** — C2의 이동이 유휴 안에 숨어야 한다. 숨지 못하면 §3.4의 이월 stall이 쌓여 꼬리가 터진다.

**시나리오 18개 셀 전부에서 이 규칙이 실제 유의성 판정과 일치한다 (18/18).**

| 셀 | ① `tpot_p99`/예산 | ② 유휴 vs 이동 | 규칙 | 실제 |
|---|---:|---|:---:|:---:|
| `interactive_coding` / high | 0.12 ✗ | 0.055 > 0.022 ✓ | C1 | C1 |
| `deep_research` / mid | 0.22 ✗ | 0.698 > 0.135 ✓ | C1 | C1 |
| `deep_research` / high | 0.43 ✓ | 0.698 > 0.149 ✓ | **C2** | **C2** |
| `build_test_loop` / high | 0.20 ✗ | 0.268 > 0.034 ✓ | C1 | C1 |
| `agent_swarm` / mid | 0.73 ✓ | 1.956 > 0.322 ✓ | **C2** | **C2** |
| `agent_swarm` / high | 0.98 ✓ | 1.956 > 0.364 ✓ | **C2** | **C2** |
| `mixed_uniform` / mid | 0.34 ✗ | 0.165 > 0.088 ✓ | C1 | C1 |
| `mixed_uniform` / high | 0.57 ✓ | 0.165 > 0.129 ✓ | **C2** | **C2** |
| `long_context` / mid | 0.63 ✓ | 0.168 **<** 0.279 ✗ | C1 | C1 |
| `long_context` / high | 0.92 ✓ | 0.168 **<** 0.384 ✗ | C1 | C1 |
| 나머지 8개 (저부하 등) | — | — | C1 | C1 |

> **`long_context`가 규칙의 값어치를 보여준다.** C1이 명백히 실패하는데도(예산의 92%) C2가 답이 아니다 — 96K context의 KV는 이동 시간이 유휴보다 길어, C2로 바꾸면 C1의 TPOT 문제를 C2의 TTFT 문제로 바꿀 뿐이다. 실제로 `long_context` 고부하에서 C2의 `ttft_p99`는 14.30초로 C1의 10.90초보다 나쁘다.

**규칙은 이 18개 셀에서 유도했으므로 그 안에서의 일치는 적합(fit)이지 검증이 아니다.** Sweep 14개 셀(§6, 규칙 유도에 쓰지 않음)에 적용하면 **12/14가 일치**한다. 불일치 2개는 모두 ① 경계 바로 근처다(×1.0에서 0.42, mc16에서 0.35).

| 검증 셀 | ① | ② | 규칙 | 실제 |

### 7.2 권고

**기본값은 C1이다.**

1. **C2가 이기는 구간이 좁다.** 시나리오 18개 중 4개, Sweep 14개 중 4개. 그리고 그 구간은 사전에 알 수 없는 것이 아니라 §7.1의 두 조건으로 **운영 중 측정 가능**하다.
2. **C1의 실패는 점진적이고 C2의 실패는 급격하다.** C1은 최악의 조건에서도 정책 오버헤드 18.0%, `ttft_p99` 40.3초에 머문다. C2는 같은 조건에서 72.7%, 177.8초다. **용량 계획을 세울 수 있는 쪽은 C1이다.**
3. **비용이 자릿수로 다르다.** 순환복잡도 2 vs 30, Tuning Knob 0개 vs 7개, 고유 코드 56 LoC vs 205 LoC.
4. **C2의 우위는 C2 고유의 능력에서 오지 않는다.** §5.3(1)이 보였듯 C2가 이기는 이유는 "부하를 여러 매체에 쪼갠다"는 것이며, 이것은 데이터 특성 분석 없이도 얻을 수 있다.

### 7.3 C1을 고른다면 반드시 고쳐야 할 것 — 그리고 그게 더 싸다

C1의 `agent_swarm` 실패(As-Is의 0.83배)는 **점수 함수가 아니라 후보 형성의 문제**다.

- **`FeasibilityFilter`에 step 예산 조건을 추가한다.** 현재는 `gpu_reachable`이면 통과시키지만(`policy.py:59-67`), Mode A 상주 시의 `resident_decode_seconds`가 step 예산을 넘는 메모리는 **후보에서 빼야 한다.** 이미 Mode C 경로에는 같은 조건이 `can_serve_decode_attention()` 안에 들어 있다(§4.4) — 그 조건을 Mode A로 확장하는 것뿐이다.
- 이것은 **분기 하나**다. C2 전체(분기 29개, Knob 7개)를 도입하는 것과 비교할 대상이 아니다.
- 남는 것은 한 매체 포화 시의 분산인데, `TierScorer`의 `W_LOAD`를 **점유율이 아니라 "예상 step 시간 ÷ 예산"으로 재정의**하면 같은 argmax 구조 안에서 해결된다.

**이 두 변경으로 §7.1의 조건 ①이 성립하지 않게 되면, C2를 채택할 이유는 측정 범위 안에서 사라진다.** 이것을 확인하는 것이 다음 실험이다 — 본 문서는 그 실험을 하지 않았다.

### 7.4 그래도 C2를 채택한다면

`agent_swarm`급 워크로드(유휴 중앙값 2초 이상)가 지배적이고 부하가 안정적이라고 확신한다면 C2의 +20~45%는 실재한다. 다만 다음을 함께 해야 한다.

1. **이동 예산(migration budget)을 둔다.** 결정점 B의 `deact` 시간이 예상 유휴 시간을 넘으면 이동하지 않고 제자리에 둔다. §5.3(2)의 붕괴는 전부 이 조건이 없어서 생긴다.
2. **Mode B 비중을 SLI로 감시한다.** C2의 붕괴는 Mode B 비중이 0%→38%로 가는 것으로 먼저 보인다. Goodput이 떨어지기 **전에** 보인다.
3. **7개 Threshold의 재튜닝 주기를 정한다.** 워크로드가 바뀌면 이 값들이 함께 바뀌어야 한다.

## 8. 유효 범위와 한계

**이 결과가 성립하는 범위를 벗어나면 결론을 인용하면 안 된다.**

| 항목 | 내용 |
|---|---|
| **Configuration 의존** | `configs/memories_default.json`의 값 위에서만 성립한다. 그중 `custom_hbm`의 **내부 대역폭·용량·fabric 지연**, 연산형 메모리의 **TFLOPS**가 모두 ASSUMED다. §5.3(1)의 C1 실패는 `custom_hbm`의 대역폭 값에 직접 의존한다 |
| **툴 실행 시간** | 8종 툴의 중앙값과 σ는 ASSUMED다. 상대 순서만 근거가 있다. §6.1이 보였듯 **이 축이 결론을 가장 크게 바꾼다** |
| **이동 시간 모델** | 이동 시간 = `bytes ÷ 대상 메모리 외부 대역폭`. 실제 시스템의 DMA 셋업, 페이지 단위 전송, 경쟁은 모델링하지 않았다. 따라서 이동 비용은 **과소 추정** 쪽이며, 이는 C2에 관대한 방향이다 |
| **단일 노드** | GPU 1장 + 메모리 6종. 다중 노드에서의 거동은 측정하지 않았다 (DP2의 범위) |
| **Scheduler 고정** | Chunked Prefill off, Prefix Caching off, Preemption 없음. §6.3이 보였듯 동시성 설정만으로도 우열이 뒤집힌다 |
| **추정 모델** | C2의 세 추정 모델은 사후 관측으로 학습한다. Cold start 구간의 오분류가 포함되어 있으며, 별도의 사전 학습을 주면 C2가 더 유리해질 수 있다 |
| **Endurance 미평가** | 저내구성 매체의 수명은 평가 축에서 뺐고 정책 로직에도 넣지 않았다. HBF를 왕복 매체로 쓰는 구성을 실제로 검토한다면 **별도로 따져야 한다** — 본 문서는 그 판단의 근거를 제공하지 않는다 |
| **측정하지 않은 것** | GPU Occupancy 실측, 에너지, Prefix Cache 공유 효과, 유휴 중 재조정(직교 축) |
| **M-P8 미측정** | 추정 오차를 의도적으로 주입하는 민감도 실험은 하지 않았다. C2의 추정은 "학습으로 자연히 생기는 오차"만 포함한다 — 즉 **본 결과는 C2에 관대한 쪽**이다 |
| **§7.1 규칙의 지위** | 18개 셀에서 유도하고 14개 Sweep 셀로 확인했다. 두 임계값(40%, 유휴 > 이동)은 이 구성에서 얻은 것이며, 다른 Configuration에서는 **경계값을 다시 재야 한다.** 구조(두 조건의 논리곱)는 §5.3의 메커니즘에서 나오므로 더 일반적일 것으로 본다 |
