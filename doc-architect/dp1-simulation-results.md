## 1. 요약 — 별점

각 QA를 3점 만점으로 평가한다. **임계값의 근거는 §4에 있다.** As-Is(HBM 우선 + 순차 Spill)를 함께 평가하는 이유는, C1–C2 간 격차보다 "정책이 있는가 없는가"의 격차가 더 클 수 있기 때문이다.

| QA | 측정 지표 | As-Is | C1 (메모리 특성) | C2 (Data 특성) |
|---|---|:---:|:---:|:---:|
| **Performance** — 처리량 | SLO-제약 Goodput (As-Is=1.0) | 기준선 | ★★☆ `1.30x` | ★★☆ `1.42x` |
| **Performance** — 시간 | SLO Attainment | ★☆☆ `0.644` | ★★☆ `0.907` | ★★☆ `0.931` |
| **Performance** — 꼬리 안정성 | 부하 급변 시 p99 팽창률 | ★★☆ `2.4x` | ★★☆ `4.9x` | ★☆☆ `16.5x` |
| **Performance** — 자원 | HBM 유휴 KV 감소율 | ★☆☆ `0%` | ★★★ `97.9%` | ★★★ `98.2%` |
| **Flexibility** | M-F1 신규 메모리 지원 수 | ★☆☆ `0/4` | ★★☆ `2/4` | ★★☆ `3/4` |
| **Maintainability** | McCabe 순환복잡도 | ★★★ `4` | ★★★ `2` | ★☆☆ `30` |
| **Risk** | M-E1 저내구성 매체 수명 | ★★★ `해당 없음` | ★★★ `해당 없음` | ★☆☆ `0.11~0.31년` |

**한 줄 요약.** 두 후보 모두 As-Is를 크게 앞서지만 **서로 간의 처리량 차이는 대부분의 조건에서 통계적으로 유의하지 않다.** C2는 유휴가 긴 워크로드에서만 유의하게 앞서며, 그 대가로 **꼬리 지연·유지보수성·매체 수명 세 축에서 모두 C1보다 나쁘다.**

## 2. 구현

구현 UML의 모듈 구조를 그대로 따랐다. 파일명이 UML의 모듈명과 1:1 대응한다.

| 파일 | 내용 | UML 대응 |
|---|---|---|
| `core.py` | `MemorySpec` · `ModelShape` · `MemoryStateView` · `QueueStateView` · `LinkCostModel` | §2.1 공통 |
| `policy.py` | `PlacementPolicy` · `TierScorer` · `FeasibilityFilter` · `PlacementExecutor` | §2.1 공통 |
| `analyzer.py` | `KVCharacteristicAnalyzer` · `KVClassifier` · `PlacementPolicyTable` + 세 추정 모델 | §2.3 C2 전용 |
| `policies/c1_memory_centric.py` | `MemoryStateCollector` → `PlacementPlanner` | §2.2 |
| `policies/c2_data_centric.py` | `MemoryStateAwareRefiner` | §2.3 |
| `policies/as_is.py` | 고정 Spill 순서 | 기준선 |
| `engine.py` | 이산 사건 엔진. **GPU 점유와 메모리 점유를 별도 자원으로 두고 `max`로 합친다** | §4.6 |

### 구현에서 확인된 설계 문서의 주장

- **§4.6 자원 병렬화가 실제로 측정된다.** As-Is의 자원 병렬도는 `1.008`(직렬)인 반면 C1은 `1.528`, C2는 `1.537`이다. `max`를 `sum`으로 바꾸면 이 차이가 사라진다.
- **§4.4의 네 조건이 후보를 가른다.** `ssd_pim`은 `SOFTMAX` 미지원으로 Mode C 대상에서 탈락하고, 기본 구성에서 오프로드가 성립하는 것은 `custom_hbm`과 `cxl_pnm` 둘뿐이다.
- **C1은 `analyzer` 모듈을 import하지 않는다.** 추정 오차가 도달할 경로가 구조적으로 없다.

### 구현 중 내린 판단 두 가지

UML 검수(`dp1-implementation-uml-review.md`)가 미해결로 남긴 항목을 구현에서 결정해야 했다.

- **U3 (`FeasibilityFilter` 호출 주체)** — 권고안 A를 채택했다. `PlacementManager`가 정책 호출 **전에** 적용하므로 두 후보가 동일한 후보 집합을 받는 것이 보장된다. 이것 없이는 후보 범위 차이가 정책 차이로 오인된다.
- **U6 (`PlacementPolicyTable`의 신규 메모리 편입)** — `Medium`을 열거하지 않고 **메모리의 성질로 일반 판정**하도록 구현했다. 그 결과가 §5.5의 M-F1 측정값이다.

## 3. 실험 설계

### 3.1 워크로드 — opencode 8종 툴

opencode의 permission 대상 툴은 `bash·read·edit·glob·grep·webfetch·task·todowrite·websearch·lsp·skill` 이다. 이 중 **실행 시간 특성이 서로 구분되는 8종**을 골랐다. 제외 사유: `todowrite`는 실질 0초라 유휴가 생기지 않고, `websearch`는 `webfetch`와, `lsp`는 `read`와, `skill`은 `task`와 같은 등급이다.

| 툴 | 중앙값 | σ(log) | 결과 토큰 | 근거 |
|---|---:|---:|---:|---|
| `read` | 0.02s | 0.5 | 2000 | 로컬 파일 읽기. 페이지 캐시 유무로 수 ms~수십 ms |
| `write` | 0.04s | 0.5 | 50 | 쓰기 + fsync. 읽기보다 비싸나 여전히 로컬 I/O |
| `edit` | 0.06s | 0.6 | 200 | 매칭 후 부분 치환 — 읽기와 쓰기를 모두 포함 |
| `glob` | 0.15s | 0.8 | 400 | ripgrep 파일 순회. 레포 크기에 비례 |
| `grep` | 0.40s | 1.0 | 800 | ripgrep 내용 스캔. 순회보다 무겁다 |
| `webfetch` | 1.20s | 0.9 | 3000 | 네트워크 왕복 + 본문 변환 |
| `bash` | 1.50s | **1.6** | 600 | 서브프로세스. ls 수 ms ~ 테스트 수십 초 — **분산 최대** |
| `task` | 25.0s | 1.2 | 1000 | 서브에이전트. 내부에서 LLM 호출이 여러 번 |

실행 시간은 lognormal을 쓴다 — 소프트웨어 실행 시간은 하한이 0이고 오른쪽 꼬리가 길다. **절대값은 ASSUMED이지만 상대 순서(로컬 I/O < 검색 < 네트워크 < 서브프로세스)는 근거가 있으며**, 절대값이 결론을 바꾸는지는 §6.1의 Sweep이 확인한다.

### 3.2 시나리오 6종 × 부하 3수준

| 시나리오 | 툴 믹스 특징 | Context | 의도 |
|---|---|---:|---|
| `interactive_coding` | read/edit/grep 65% | 16K | 유휴가 짧아 하위 계층 왕복을 회수할 시간이 없다 |
| `deep_research` | webfetch/task 60% | 48K | 유휴가 길어 깊은 계층이 값을 한다 |
| `build_test_loop` | bash 55% | 24K | 같은 툴 아래 실행 시간 분산이 가장 크다 |
| `agent_swarm` | task 45% | 64K | 유휴가 수십 초 — 가장 깊은 계층까지 성립 |
| `mixed_uniform` | 8종 균등 | 32K | 한 세션 안에서 유휴가 자릿수로 널뛴다 |
| `long_context` | 혼합 | 96K | 세션당 KV가 커 용량 압력이 지배적 |

부하는 도착률 배수로 **low(×1) / mid(×4) / high(×6)** 세 수준을 둔다. 세션은 Poisson 도착하고 각 턴은 `Incremental Prefill(GPU 고정) → 결정점 A → Decode → 결정점 B → 유휴`를 거친다.

### 3.3 판정 규칙 (실행 전 고정)

- **워크로드를 정책과 무관하게 먼저 생성한다.** 정책마다 난수 소비 순서가 달라지면 같은 seed라도 서로 다른 워크로드를 보게 되어 짝지은 비교가 무효가 된다. 세 정책은 완전히 같은 trace를 소비한다.
- **동일 seed에서 짝지어(paired) 비교하고, 95% 신뢰구간이 0을 지나면 "차이 없음"으로 판정한다.** 점 추정의 부호로 판정하지 않는다.
- **Goodput의 분모는 horizon(400초)으로 고정한다.** 정책마다 마지막 이벤트 시각이 다르므로 그것을 분모로 쓰면 처리량 비교가 성립하지 않는다.
- **최초 턴은 SLO 판정과 Goodput 분자에서 제외한다.** 배치 결정 **이전**이므로 대조군으로만 쓴다 (설계 문서 §11.2 M-P2).
- seed 24개, horizon 400초.

## 4. 별점 기준 — 임계값과 근거

### 4.0 먼저: 측정 노이즈의 크기

임계값이 노이즈보다 커야 의미가 있으므로, 먼저 본 실험의 재현성을 측정했다.

```
Goodput의 seed 간 변동계수(CV)    중앙값 0.202  (p90 0.359)
24-seed paired 비교의 최소검출차   1.96 × 0.202 / √24 = 0.081  →  8.1%
```

**따라서 8.1%보다 작은 차이는 본 실험에서 재현되지 않는다.** 이 값이 아래 모든 임계값의 하한 근거가 된다.

### 4.1 Performance — 처리량 (SLO-제약 Goodput)

정규화: As-Is = 1.0. 대표값은 **중부하·고부하 12개 셀의 중앙값**을 쓴다(저부하는 세 정책이 동일해 배치 결정이 필요 없는 구간이므로 제외).

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 1.10x` | 24-seed 최소검출차가 8.1%이므로 10%는 그것을 안전하게 넘는 최소 크기다. 이보다 작으면 재현되지 않는다 |
| ★★☆ | `1.10x ~ 2.00x` | 유의한 개선이지만 장비 대수를 바꾸지 못한다 |
| ★★★ | `≥ 2.00x` | **같은 SLO에서 처리량 2배 = 필요 장비 절반.** 하드웨어 투자 결정을 뒤집는 크기이므로 만점의 기준으로 삼는다 |

### 4.2 Performance — 시간 (SLO Attainment)

SLO는 `재활성 TTFT ≤ 2.0s AND TPOT ≤ 50ms`. Attainment는 SLO를 만족한 출력 토큰의 비율이다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 0.80` | 다섯 요청 중 하나 이상이 SLO를 놓치는 수준. 대화형 서비스의 체감이 무너지는 하한 |
| ★★☆ | `0.80 ~ 0.95` | 대다수를 만족하나 목표 미달 |
| ★★★ | `≥ 0.95` | 대화형 서비스의 통상적 SLO 목표(p95)를 달성 |

### 4.3 Performance — 꼬리 안정성

**부하가 급변할 때 꼬리가 얼마나 팽창하는가.** Burst 도착 조건의 `ttft_p99` ÷ 정상 도착 조건의 `ttft_p99`.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `> 5x` | 부하 변동을 흡수하지 못하고 꼬리가 자릿수로 튄다. 용량 계획이 불가능해진다 |
| ★★☆ | `2x ~ 5x` | 팽창하지만 예측 가능한 범위 |
| ★★★ | `≤ 2x` | 부하 변동을 흡수했다고 볼 수 있는 수준 |

> **이 지표는 절대값과 함께 읽어야 한다.** As-Is의 팽창률이 가장 낮지만(2.4x), 그것은 정상 조건에서 **이미** p99가 8.8초로 나빠 더 나빠질 여지가 적기 때문이다. 팽창률만 보면 As-Is가 가장 안정적이라는 잘못된 결론이 나온다.

### 4.4 Performance — 자원 (HBM 유휴 KV 감소율)

`1 − (후보의 HBM 유휴 KV 평균 ÷ As-Is의 HBM 유휴 KV 평균)`. **이 DP의 직접적 개선 대상**이다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 50%` | 절반도 줄이지 못하면 계층을 쓰는 이유가 약하다 |
| ★★☆ | `50% ~ 90%` | 부분적 해결 |
| ★★★ | `≥ 90%` | 유휴 KV가 HBM의 10% 미만만 점유한다. HBM 192 GiB 기준 **평균 세션 하나(약 10 GB)분 이하**이므로 "문제가 해소됐다"고 볼 수 있다 |

### 4.5 Flexibility (M-F1)

기존 6종이 갖지 못한 특성 조합을 하나씩 대표하는 신규 메모리 4종을 투입하고, **Configuration 교체만으로 실제 배치가 발생하는지** 센다. 투입 세트는 실행 전에 고정했고 사후에 바꾸지 않았다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `0~1 / 4` | 대부분의 새 특성을 활용하지 못한다 |
| ★★☆ | `2~3 / 4` | 일부만 활용 |
| ★★★ | `4 / 4` | 투입 4종이 각각 다른 특성 축을 대표하므로, 전부 써야 "정책이 적응했다"고 말할 수 있다 |

계수 규칙(설계 문서 §11.3): 배치 bytes = 0이면 **미지원**(존재를 견딘 것이지 적응이 아니다). 코드 수정 없이 배치가 발생하면 지원.

### 4.6 Maintainability — McCabe 순환복잡도

정책 결정 경로의 순환복잡도(분기 수 + 1)를 구현 코드에서 AST로 센다. 공통 인프라는 셋 다 쓰므로 제외하고 **그 정책 때문에 존재하는 코드**만 센다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★★★ | `CC ≤ 10` | McCabe(1976)의 원 권고. 단순하고 테스트 가능한 구간 |
| ★★☆ | `CC 11 ~ 20` | 보통 |
| ★☆☆ | `CC > 20` | **NIST SP 500-235가 "복잡·위험" 으로 분류하는 구간.** 20을 넘으면 모든 분기를 테스트로 덮는 비용이 급증한다 |

> 임계값을 임의로 정하지 않고 널리 인용되는 외부 기준을 그대로 쓴다. 이 QA는 대리 지표이므로 자체 기준을 만들면 근거가 순환하게 된다.

### 4.7 Risk — Endurance (M-E1)

저내구성 매체(HBF·SSD-PIM)에 발생한 쓰기를 `write_amplification`을 반영해 누적하고, Configuration의 `endurance_budget_bytes`로 나눠 예상 수명을 낸다.

| 별점 | 임계 | 근거 |
|---|---|---|
| ★☆☆ | `< 3년` | **데이터센터 하드웨어 교체 주기가 통상 3~5년**이므로, 수명이 3년 미만이면 서비스 기간 내 계획에 없던 교체가 필요해진다 |
| ★★☆ | `3 ~ 5년` | 교체 주기와 비슷 |
| ★★★ | `≥ 5년` 또는 저내구성 매체 미사용 | 수명이 제약이 되지 않는다 |

> HBF의 쓰기 대역폭과 Endurance Budget은 Configuration에서 **ASSUMED**다. 따라서 이 지표의 **절대 수준은 신뢰하지 말고 정책 간 상대 비교로만** 써야 한다. 다만 C1은 저내구성 매체에 **쓰기가 0**이므로, 가정값이 어떻든 C1 > C2라는 방향은 뒤집히지 않는다.

C2 − C1의 짝지은 차이가 **유의한 셀은 18개 중 4개**뿐이다:

### 5.3 꼬리 안정성 — C2의 명확한 약점

Burst 도착 조건에서 `ttft_p99`의 팽창률:

HBM 유휴 KV 감소율(고부하): C1 `89.3~100%` (중앙값 97.9%), C2 `92.9~99.9%` (중앙값 98.2%).

부수적으로 오프로드 채택률은 C1 `0.98`, C2 `0.887`이다. C2가 낮은 것은 Cold 분류분을 연산 불가 계층으로 보내기 때문이며, 이는 설계 의도대로다.

구현 코드에서 AST로 측정. 공통 인프라 제외, 정책 고유 코드만.

|---|---:|---:|---:|
| 유효 LoC | 34 | 56 | **205** |

### 5.7 Risk — Endurance

C1은 저내구성 매체에 **쓰기가 0**이다. C2만 HBF·SSD-PIM을 쓴다.

| 시나리오 / 부하 | C2의 HBF 쓰기 | 예상 수명 |
|---|---|---|
| `mixed_uniform` / mid | 5.79 TiB / 400s | **0.20년** (73일) |
| `mixed_uniform` / high | 8.21 TiB / 400s | **0.14년** (51일) |
| `agent_swarm` / mid | 7.04 TiB / 400s | **0.16년** (58일) |
| `agent_swarm` / high | 10.18 TiB / 400s | **0.11년** (40일) |
| `long_context` / mid | 3.78 TiB / 400s | **0.31년** (113일) |

**C2의 배치 패턴대로면 HBF가 40~113일 만에 수명을 소진한다.** 설계 문서 §11.5가 경고한 "왕복이 반복되면 수명이 소모된다"가 정확히 재현됐다 — C2는 Cold로 분류한 KV를 HBF로 보내고, 그 세션이 다시 활성화되면 되가져오고, 다음 턴에 또 보낸다.

Endurance Budget은 ASSUMED 값이므로 절대 수명은 신뢰할 수 없다. 다만 **C1의 쓰기가 0이므로 방향은 가정값과 무관하게 확정적이다.**

## 6. Sweep — 결론이 무엇에 걸려 있는가

### 6.1 유휴 시간 분포 (가장 중요한 축)

툴 실행 시간 전체를 배수로 조정했다. C2 − C1 Goodput 차이:

| 배수 | As-Is | C1 | C2 | C2−C1 (95% CI) | 유의 |
|---|---:|---:|---:|---|:---:|
| ×0.1 | 85.5 | 160.0 | 161.1 | +1.14 [−1.58, +3.86] | ❌ |
| ×0.3 | 89.9 | 157.5 | 156.5 | −1.05 [−4.28, +2.19] | ❌ |
| ×1.0 | 96.0 | 145.0 | 148.4 | +3.39 [−0.65, +7.42] | ❌ |
| **×3.0** | 110.6 | 115.3 | **134.0** | **+18.64 [+6.75, +30.52]** | ✅ |
| **×10.0** | 106.3 | 87.2 | **107.1** | **+19.85 [+12.54, +27.15]** | ✅ |

**교차 지점은 ×1과 ×3 사이에 있다.** 유휴 시간이 현재 가정의 3배 이상이 되어야 C2의 데이터 특성 분석이 값을 한다. 그보다 짧으면 두 후보가 구분되지 않는다.

이것이 §5.1에서 `agent_swarm`(task 45%, 유휴 수십 초)만 유의했던 이유를 설명한다. **C2의 우위는 "데이터 특성을 본다"는 것 자체가 아니라 "유휴가 충분히 길어 깊은 계층 왕복을 회수할 수 있다"는 조건에서 나온다.**

또한 ×10에서 **C1은 As-Is보다도 나빠진다**(87.2 vs 106.3). 유휴가 매우 길면 C1의 "빠른 계층 우선" 점수 함수가 용량을 낭비하기 때문이다.

### 6.2 배치 크기 — 영향 없음

| 배치 | C1 | C2 | C2−C1 유의 |
|---|---:|---:|:---:|
| 1 | 146.1 | 148.5 | ❌ |
| 4 | 144.9 | 148.4 | ❌ |
| 16 | 145.0 | 148.4 | ❌ |
| 64 | 145.1 | 148.4 | ❌ |

설계 문서 §4.3은 "계층당 왕복 비용이 배치 크기에 반비례"하므로 이 축이 오프로드 이득을 좌우한다고 봤다. **본 구성에서는 그 항이 지배적이지 않다** — `custom_hbm`의 fabric 지연이 1 μs이고 80계층이면 80 μs로, Decode step 예산(50 ms) 대비 0.16%에 불과하기 때문이다. 지연이 μs 급인 `ssd_pim`을 실제로 쓰는 구성에서는 결론이 달라질 수 있다.

### 6.3 동시성 한계 — 우열이 뒤집힌다

| 최대 동시 세션 | As-Is | C1 | C2 | C2−C1 유의 |
|---|---:|---:|---:|:---:|
| **8** | 113.8 | **127.6** | 124.7 | ❌ (C1이 근소 우위) |
| 16 | 90.1 | 167.2 | **175.0** | ✅ |
| 32 | 36.9 | 163.0 | **178.8** | ❌ |
| 128 | 36.4 | 157.4 | **173.2** | ✅ |

**동시성을 8로 조이면 C1이 앞선다**(비유의하지만 부호가 뒤집힌다). 동시 세션이 적으면 용량 압력이 없어 C2가 후보를 좁히는 것이 이득 없이 비용만 된다. 설계 문서 §11.6.1이 경고한 "Scheduler 설정에 따라 우열이 뒤집히면 그 사실 자체가 결과"에 해당한다.

## 7. 조건부 선정

설계 문서 §13의 형식(**"조건 X 범위에서는 C_i, 조건 Y 범위에서는 C_j"**)에 따라 기술한다.

| 조건 | 선택 | 근거 |
|---|---|---|
| **저부하 (GPU 이용률 낮음, 용량 압력 없음)** | **어느 것도 불필요** | 세 정책의 Goodput이 동일(1.00~1.02x). 배치 결정이 실재하지 않는다 |
| **유휴 시간이 짧은 워크로드** (`interactive_coding`, `build_test_loop` — 툴 실행 시간 ×1 이하) | **C1** | 처리량 차이 없음(비유의). C1이 순환복잡도 2 vs 30, Knob 0개 vs 7개, Endurance 리스크 없음 |
| **유휴 시간이 긴 워크로드** (`agent_swarm`, 툴 실행 시간 ×3 이상) | **C2** — 단 조건부 | Goodput +15~20% 유의. **그러나 HBF 수명 40~58일과 꼬리 팽창 13~20x를 함께 받아들여야 한다** |
| **용량 압력이 지배적** (`long_context`) | **C2** | Goodput +2.5~6.6 유의. 유휴 KV 감소율도 근소 우위 |
| **부하가 급변하는 환경** (burst, 과부하) | **C1** | Goodput은 차이 없고 C2의 `ttft_p99`가 3~4배 나쁘다 |
| **동시성을 강하게 제한한 Scheduler** (≤8) | **C1** | 부호가 뒤집힌다 |
| **저내구성 매체(HBF/SSD-PIM)를 실제로 배치에 쓰는 구성** | **C1** | C2는 그 매체의 수명을 1년 내에 소진한다 |

### 종합 판단

**대부분의 조건에서 C1이 낫다.** C2가 유의하게 앞서는 것은 "유휴가 충분히 길고 + 부하가 안정적이고 + 저내구성 매체를 쓰지 않는" 교집합뿐이며, 그 구간에서도 처리량 이득(+15~20%)이 유지보수 비용(복잡도 15배)과 매체 수명 리스크를 정당화하는지는 별도 판단이 필요하다.

**C2를 채택한다면 반드시 함께 해야 할 것:**
1. `PlacementPolicyTable`의 Cold 판정에서 **Endurance Headroom을 후보 형성 조건에 넣을 것.** 현재 구현은 용량과 연산 능력만 보고 내구성을 보지 않는다 — 이것이 §5.7의 원인이다.
2. 7개 Threshold의 튜닝 절차와 재튜닝 주기를 정할 것. 워크로드가 바뀌면 이 값들이 함께 바뀌어야 한다.
3. 부하 급변 시 깊은 계층 배치를 억제하는 안전장치를 둘 것.

## 8. 유효 범위와 한계

**이 결과가 성립하는 범위를 벗어나면 결론을 인용하면 안 된다.**

| 항목 | 내용 |
|---|---|
| **Configuration 의존** | `configs/memories_default.yaml`의 값 위에서만 성립한다. 그중 `custom_hbm`의 **내부 대역폭·용량·fabric 지연**, `hbf`의 **쓰기 대역폭·Endurance Budget**, 연산형 메모리의 **TFLOPS**가 모두 ASSUMED다 |

| **측정하지 않은 것** | GPU Occupancy 실측, 에너지, Prefix Cache 공유 효과, 유휴 중 재조정(직교 축) |
| **M-P8 미측정** | 추정 오차를 의도적으로 주입하는 민감도 실험은 하지 않았다. C2의 추정은 "학습으로 자연히 생기는 오차"만 포함한다 — 즉 **본 결과는 C2에 관대한 쪽**이다 |
