# DP1 구현 UML 검수

**일자** 2026-09-15 · **대상** [`dp1-implementation-uml.md`](dp1-implementation-uml.md)

설계 문서의 주장이 **구조 수준에서 실제로 강제되는지**를 확인했다. UML이 설계 문서와 어긋나는 지점, 다이어그램끼리 어긋나는 지점, 그리고 **주장은 있으나 그림이 뒷받침하지 않는 지점**을 찾는 것이 목적이다.

**후보 구조의 우열은 검수 대상이 아니다.** C1과 C2 중 무엇이 나은지는 측정이 답한다.

---

## 요약

| # | 발견 | 심각도 | 상태 |
|---|---|---|---|
| **U1** | 통합 모듈 뷰가 두 후보의 **합집합**이라 "C1이 무엇을 쓰지 않는지"가 보이지 않는다 | **높음** | ✅ 수정 — §1.2 / §1.3 / §1.4 신설 |
| **U2** | 클래스 10개가 어느 모듈에도 배치되어 있지 않다. 그중 둘은 배치를 잘못하면 §0의 불변식이 깨진다 | **높음** | ✅ 수정 |

| **U4** | 결정점 B는 C1/C2 시퀀스가 있는데 **결정점 A는 하나뿐**이었다 | **중간** | ✅ 수정 — §3.2 신설 |

## 1. 검수 기준

구현 UML이 갖춰야 할 것을 확인했다. 설계 문서와 달리 **운용·마이그레이션 항목은 이 문서의 범위가 아니다** — 아직 서비스에 배포되는 산출물이 아니므로 의도적으로 비운다.

| 항목 | 검수 전 | 검수 후 |
|---|:---:|:---:|
| 설계 문서의 불변식이 구조로 강제되는가 | ✅ Prefill/Decode 모듈 분리 | ✅ |
| **후보별 구조 차이가 그림에서 보이는가** | ❌ 합집합 뷰 하나 | ✅ §1.2 / §1.3 |
| 모든 타입에 소속 모듈이 있는가 | ❌ 10개 미배치 | ✅ |
| 클래스 다이어그램과 시퀀스가 일치하는가 | ❌ U3 | ⚠️ U3 잔존 |
| 결정점별 흐름이 후보별로 있는가 | ❌ 결정점 A 누락 | ✅ |
| 공유 산술이 한 곳에 선언되는가 | ❌ 중복 선언 | ✅ |
| Metric이 구조의 어느 지점을 재는지 지정 | ✅ §4 매핑표 | ✅ |
| 구조가 **강제하지 못하는 것**의 명시 | ❌ | ⚠️ U6이 그 첫 항목 |

> **마지막 항목이 DP3 UML에는 있고 DP1 UML에는 없었다.** DP3 UML은 "구조가 강제하지 못하는 것" 절로 검증에 넘길 항목을 명시한다. DP1 UML에도 같은 절이 있으면 U6 같은 항목이 사후 발견되지 않는다 — §4의 권고에 넣었다.

## 2. 발견 상세

### 2.1 U1 — 합집합 뷰로는 후보 비교가 안 된다 (높음, 수정됨)

**증상.** §1의 Module View는 `policies/` 하위에 `c1`과 `c2`를 나란히 두고 나머지 모듈을 공유하는 **한 장**이었다. 관찰 3에 *"`c1_memory_centric`은 `analyzer.py`에 의존하지 않는다 … M-P8의 증폭률이 C1에서 정확히 0인 것이 구현 구조에서 보장된다"* 고 적혀 있었다.

**왜 문제인가.** 그 문장이 **서술로만 남는다.** 그림에는 `analyzer.py` 상자가 있고 `c2 --> analyzer` 간선이 있으므로, **C1 입장에서 이 시스템이 어떻게 생겼는지**는 독자가 머릿속에서 간선을 지워가며 재구성해야 한다. C1/C2 비교의 상당 부분이 "C1은 추정 경로를 타지 않는다"에 걸려 있는데, 그것이 **그림의 성질이 아니라 주석의 주장**이었다.

**수정.** §1을 네 부분으로 나눴다.

| 절 | 내용 |
|---|---|
| §1.1 | 통합 뷰 — vLLM과의 연결을 보인다 (기존 뷰 + U2 반영) |
| **§1.2** | **C1 모듈 뷰** — C1이 활성화하는 모듈만. `analyzer.py`가 **그래프에 없다** |
| **§1.3** | **C2 모듈 뷰** — C1 집합의 진상위집합 |
| §1.4 | 두 뷰의 차이 — 정량 표 + 정보 흐름 방향 |

**드러난 것.** 차이가 "모듈 두 개"가 아니라 **정보가 흐르는 방향**이었다.

```text
C1     MemoryStateView ══► 후보 형성 ──► TierScorer arg max
C2     KVCharacteristics ══► 후보 형성 ──► MemoryStateView 보정 ──► TierScorer arg max
```

설계 문서 §1의 핵심 설계 질문 — *"메모리 자원 특성과 KV 캐시의 데이터 특성 중 무엇을 1차 기준으로 할 것인가"* — 가 **후보 형성 단계로 들어가는 굵은 간선이 어디서 오는가**로 그림에 나타난다. 통합 뷰에서는 두 간선이 모두 존재해 이 질문이 보이지 않았다.

**부수 소득.** C1 뷰에 `QueueStateView`와 `AgentToolInfo`를 **점선(받지만 읽지 않음)** 으로 그리면서, 설계 문서 §5.4(2)의 공정성 경계가 그림에 들어왔다 — **C1이 큐 정보를 못 봐서 진 것이라면 그것은 정보 격차이지 설계 우열이 아니다.**

### 2.2 U2 — 클래스 10개에 소속 모듈이 없다 (높음, 수정됨)

**증상.** Module View의 상자에 나열된 타입과 Class Diagram이 정의한 클래스를 대조한 결과, **41개 클래스 중 10개가 어느 모듈에도 배치되어 있지 않았다.**

`DataCentricPolicy` · `MemoryCentricPolicy` · `MemoryStateSnapshot` · `DecodePlan` · `TriggerKind` · `ToolLatencyModel` · `TurnHazardModel` · `DecodeLengthModel` · **`QueueStateView`** · **`LinkCostModel`**

앞의 여덟은 소속이 자명해 채워 넣으면 끝난다. **뒤의 둘은 어디에 두느냐가 §0의 불변식을 좌우한다.**

#### `QueueStateView` — `analyzer.py`에 두면 공정성 경계가 깨진다

`QueueStateView`를 읽는 것은 C2의 `KVCharacteristicAnalyzer`뿐이므로, **소속을 채우라고 하면 `analyzer.py`에 넣는 것이 자연스러운 선택이다.** 그런데 그렇게 하면

> 설계 문서 §5.4(2) — 큐 대기 시간은 데이터 특성이 아니라 **시스템 상태**다. C2만 쓰게 하면 공정성 경계가 깨진다.

이 원칙이 **모듈 배치만으로 무너진다.** `analyzer.py`는 C1이 의존하지 않는 모듈이므로(관찰 3), 그 안에 들어간 순간 큐 정보는 구조적으로 C2 전용이 된다. **C1이 "접근 가능하나 쓰지 않는 것"과 "접근할 수 없는 것"은 전혀 다른 이야기**이며, M-P8의 Ablation 변형 중 *"`T_queue_wait`을 C1에도 제공"* 이 아예 불가능해진다.

**수정.** `queue_state.py`를 독립 모듈로 두고 `manager`가 양쪽에 공급한다.

#### `LinkCostModel` — `decode_offload.py`에 두면 Prefill/Decode 분리가 무너진다

`LinkCostModel`은 `LayerPipeline`(decode)과 `PrefillPathPlanner`(prefill) **양쪽**이 쓴다(§2.4의 `..> LinkCostModel : charges` 두 개). `decode_offload.py`에 넣으면 **`prefill_path.py`가 `decode_offload.py`를 import**하게 되고, §0의 최상위 불변식

> `prefill_path.py`에는 메모리로 연산을 보내는 경로가 아예 없다

이 **import 그래프에서 무너진다.** 코드상으로는 `DecodeOffloadPlanner`가 `prefill_path` 네임스페이스에서 호출 가능해지므로, "구조적으로 생길 수 없다"가 "규약상 하지 않는다"로 약해진다.

**수정.** `link_cost.py`를 독립 모듈로 분리했다. **두 모듈이 공유하는 비용 산술은 어느 쪽에도 속하지 않아야 한다**를 §0의 원칙으로 추가했다.

> **이 둘은 후보별 모듈 뷰를 그리지 않았으면 발견되지 않았을 것이다.** 통합 뷰에서는 모든 모듈이 한 덩어리로 보여 "이 타입이 어느 상자에 있어야 하는가"라는 질문이 생기지 않는다. 후보별로 나눠 그리려면 **모든 타입에 소속을 정해야** 하고, 그 과정에서 두 공유 타입의 배치가 불변식을 건드린다는 것이 드러났다.

### 2.3 U3 — `FeasibilityFilter`를 누가 호출하는가 (높음, **미해결**)

**이것이 남은 구조적 결함이며 설계 판단이 필요하다.**

**증상.** 같은 책임이 다섯 다이어그램에서 **세 가지로 갈린다.**

| 위치 | 무엇이라고 말하는가 |
|---|---|
| §2.1 클래스 (공통) | `PlacementPolicy ..> FeasibilityFilter : uses` — **정책이 쓴다** |
| §3.1 시퀀스 (결정점 A) | `Pol->>Feas: filter(...)` — **정책이 직접 호출** |
| §2.2 클래스 (C1) | `PlacementPlanner --> FeasibilityFilter` — **정책 내부의 Planner가 소유** |
| §3.3 시퀀스 (결정점 B, C1) | `Feas`가 **참여자에 없다.** `loop 각 feasible memory m`으로 암묵 처리 |
| §2.3 클래스 (C2) | `MemoryStateAwareRefiner --> FeasibilityFilter` — **정책 내부의 Refiner가 소유** |
| §3.4 시퀀스 (결정점 B, C2) | `Ref->>Ref: feasibility 필터 + TierScorer arg max` — **자기 호출** |

**왜 높음인가.** §2.1이 **스스로 경고한 상황**이 §3.1과 §3.4에서 벌어진다.

> §2.1 — *"정책이 후보 범위를 직접 정하게 하면 두 결정점의 차이가 정책 구현 안에 숨어 C1/C2 비교가 흐려진다."*

`FeasibilityFilter`는 **"결정점에 따라 후보 범위가 달라진다"는 설계 문서 §1의 핵심을 강제하는 장치**다. 그것이 정책 안쪽(Planner·Refiner)으로 들어가 있으면, **두 후보가 서로 다른 시점에 서로 다른 범위로 필터를 적용해도 구조가 막지 못한다.** 그러면 측정된 차이에 "후보 범위를 언제 좁혔는가"가 섞여 들어온다.

**권고 — 세 가지 중 택일.**

| 안 | 내용 | 결과 |
|---|---|---|
| **A. `PlacementManager`가 정책 호출 전에 적용** (권장) | 정책은 **이미 좁혀진 후보 집합**을 인자로 받는다. `place(request, candidates, view)` | 두 후보가 **동일한 범위**를 받는 것이 구조적으로 보장된다. §2.1의 경고가 해소된다 |
| **B. `PlacementPolicy` 추상 클래스가 template method로 고정** | `place()`는 final, 하위 클래스는 `select(candidates, view)`만 구현 | A와 효과는 같고 호출 위치가 정책 쪽 |
| **C. 현행 유지 + 규약** | "정책은 반드시 시작 시점에 한 번 호출한다"를 문서 규약으로 | **권장하지 않음** — 강제되지 않으므로 U3이 재발한다 |

> **A를 권한다.** 후보 범위 결정은 설계 문서 §4.4의 **메모리 성질에서 나오는 판정**이지 정책의 선택이 아니다(§0의 *"오프로드 가능 여부는 메모리가 정하지 정책이 정하지 않는다"*). 정책보다 바깥에 두는 것이 그 원칙과 일치한다. 다만 C2의 `PlacementPolicyTable`이 후보를 **형성**하는 단계와의 순서를 함께 정해야 하므로(feasible 집합을 받아 KV Class로 좁히는가, KV Class로 좁힌 뒤 feasible을 거르는가) **단순한 이동이 아니다** — 그래서 본 검수에서 임의로 처리하지 않았다.

### 2.4 U4 — 결정점 A에 후보별 시퀀스가 없었다 (중간, 수정됨)

**증상.** 결정점 B는 C1(§3.2)과 C2(§3.3)로 나뉘어 있었으나, **결정점 A는 §3.1 하나뿐이었고 참여자가 generic `Pol as PlacementPolicy`** 였다. 그 흐름(`Pol->>Pol: 후보 채점 → arg max`)은 사실상 **C1의 흐름**이다 — C2라면 `analyze → classify → candidates → refine` 4단계여야 한다.

**왜 문제인가.** §4의 비교표는 *"결정점 A 입력: C1 = Memory State만 / C2 = `expected_decode_length` + 재활성 연산"* 이라고 **주장하는데 그 주장을 보여주는 그림이 없었다.** 하필 결정점 A는 [ADR-003](adr/adr-003-two-decision-points.md)이 새로 추가한 결정점이고, **연산형 메모리를 쓸지 말지를 정하는 지점**이다.

**수정.** §3.2 "결정점 A — C2"를 신설하고 §3.1을 "결정점 A — C1"로 명확히 했다. 하위 절을 재번호했다(3.3~3.7).

**드러난 것.** 두 시퀀스를 나란히 놓으면 **결정점 A에서의 차이가 한 가지로 좁혀진다.**

```text
C1   후보(feasible 전체) ──► TierScorer arg max
                              └ compute_term은 가점. "옮길 값이 있는가"를 묻지 않는다

C2   expected_decode_length ──► KVClass ──► 후보 형성 ──► TierScorer arg max
                                              └ "이번 턴 Decode가 길다 → 연산형 메모리로 옮길 값이 있다"
```

**그리고 예상이 하나 나온다.** 연산형 메모리를 쓸지 판단하는 정보(`expected_decode_length`)를 C2만 갖고 있으므로 **결정점 A는 두 후보의 격차가 가장 크게 벌어질 지점**이고, 그 격차는 `DecodeLengthModel`의 추정 품질에 걸려 있으므로 **M-P8의 민감도도 여기서 가장 높을 것**이다. 이는 가설이며, 확인하려면 **M-P5와 M-P8을 결정점별로 분리 보고**해야 한다 — 설계 문서 §11이 현재 요구하지 않는 것이다(§4의 권고).

### 2.5 U5 — `TierScorer`가 두 곳에서 다르게 선언된다 (중간, 수정됨)

**증상.** §2.1(공통)은 `score()` 하나만 선언하고, §2.2(C1)에서 `capacity_term` · `bandwidth_term` · `compute_term` · `load_term` 넷을 덧붙여 **재선언**했다.

**왜 문제인가.** §0은 *"C1의 `PlacementPlanner`와 C2의 `MemoryStateAwareRefiner`가 동일한 `TierScorer`를 쓴다"* 고 못박는다. 그런데 항 분해가 **C1의 다이어그램에만** 있으면 그 네 항이 C1 전용처럼 읽힌다. 특히 `compute_term`은 §2.2의 서술에서 **C1의 약점**으로 언급되므로("가점으로만 반영한다"), C2도 같은 항을 쓴다는 사실이 가려진다.

**수정.** 항 분해를 §2.1로 옮기고 C1 다이어그램의 재선언을 제거했다. §0에 *"어느 후보의 다이어그램에서도 재선언하지 않는다"* 를 원칙으로 추가했다.

### 2.6 U6 — 신규 메모리 편입 방식이 강제되지 않는다 (중간, **미해결**)

**증상.** §1.2·§1.3 양쪽에서 `configs/*.yaml → memories.py`가 유일한 유입 경로이고 정책으로 가는 별도 간선이 없다. **구조상 M-M2(신규 메모리 추가 시 변경 지점 수)가 두 후보에서 같아야 한다.**

그러나 C2의 `PlacementPolicyTable.candidates(kv_class, primitives, memories)`가 KV Class별 후보를 정한다. 이 매핑이

- **원시 연산 지원 여부로 일반 판정**하면 → 신규 메모리가 코드 수정 없이 편입. 변경 지점 C1 = C2
- **`Medium` 값이나 메모리 이름을 열거**하면 → 표를 고쳐야 한다. 변경 지점 C2 = C1 + 1

**시그니처는 `memories`를 인자로 받아 일반 판정이 가능한 형태이지만 강제하지는 않는다.**

**왜 문제인가.** 설계 문서 §11.3의 M-F1은 *"코드 수정 없이 Configuration 교체만으로 배치 발생"* 을 **지원의 정의**로 삼고, §11.4의 M-M2와 짝을 이룬다. **이 구현 선택 하나가 두 지표를 동시에 움직인다** — 그러면 측정된 Flexibility 차이가 설계의 차이가 아니라 **구현자가 표를 어떻게 썼는지**를 재게 된다.

**권고.** `PlacementPolicyTable`이 `Medium`을 열거하지 않는다는 것을 **구현 규약으로 고정**하고, 어기면 드러나도록 테스트를 둔다 — 예: 설정에 없던 메모리를 주입했을 때 표가 그것을 후보로 낼 수 있는지 확인. §1.4.1에 기술했으나 **강제 수단은 아직 없다.**

## 3. 구조가 잘 잡혀 있는 부분

검수는 결함을 찾는 일이지만, **이 문서가 이미 강하게 강제하고 있는 것**을 기록해 둔다 — 이후 수정에서 약해지면 안 되는 지점이다.

| 불변식 | 어떻게 강제되는가 |
|---|---|
| **Prefill은 GPU에 고정** | `prefill_path.py`와 `decode_offload.py`의 모듈 분리. `PrefillPath` enum에 오프로드 항목 자체가 없다(`LOCAL`/`RESTORE`/`STREAM`) |
| **오프로드 가능 여부는 메모리가 정한다** | `MemorySpec.can_serve_decode_attention()`이 §4.4의 네 조건을 한 곳에 모은다. 정책이 고르지 않는다 |
| **자원 병렬화가 목적함수에 나타난다** | `ResourceLedger.turn_time()`이 `max`를 반환. `sum`으로 바꾸면 이 DP의 논거가 사라진다 |
| **추정 오차가 C1에 도달할 수 없다** | `c1_memory_centric → analyzer` 간선의 부재. §1.2에서 그래프에 모듈 자체가 없는 것으로 재확인 |
| **원시 연산 단위 판정** | `AttentionPrimitive`가 연산 단위가 아니라 원시 연산 단위 — `SOFTMAX` 없는 메모리가 첫 조건에서 탈락 |
| **Configuration 교체가 코드 수정을 부르지 않는다** | `configs → memories.py` 단일 경로. M-F1 실험의 전제 |
| **유휴 재조정이 후보와 직교** | `IdleRebalancer`가 `PlacementPolicy` 인터페이스만 안다 |

특히 **`can_serve_decode_attention()`이 `ModelShape`를 받는 것**이 좋다. 오프로드 가능 여부가 **(메모리 × 모델)의 함수**라는 §4.2의 성질이 시그니처에 들어가 있어, 모델이 바뀌면 판정이 바뀐다는 것이 타입에서 보인다.

**3번이 U4에서 파생된 것이라 부연한다.** 설계 문서 §11.2는 M-P5를 정책별로만 나누고 결정점별로는 나누지 않는다. 그런데 **두 결정점은 여유가 다르다** — 결정점 B는 비활성 구간이라 여유가 있지만 결정점 A는 Prefill 종료 직후다. [ADR-003](adr/adr-003-two-decision-points.md)도 이를 실패 모드로 적었다. **합쳐 보고하면 결정점 A의 비용이 결정점 B의 여유에 희석된다.**

> **U3과 U6 모두 "그림은 맞는데 그림이 막지 못한다"는 종류다.** U1·U2·U4·U5가 그림 자체의 결함이었다면, 이 둘은 **구조로 강제할지 규약에 맡길지를 정해야 하는 문제**다. 규약에 맡기기로 한다면 그 사실을 문서에 적어야 사후에 "왜 안 막혔나"를 묻지 않게 된다.
