# ADR-005. DP1을 먼저 실행하고 DP3는 그 실패 처리 경로로 둔다

| | |
|---|---|
| **상태** | Accepted |
| **일자** | 2026-09-15 |
| **범위** | DP1 ↔ DP3 인터페이스 |
| **근거 문서** | DP3 설계 문서 §2.3, §2.4 / DP3 구현 UML §0, §3.1 |

---

## 1. Context

DP3의 실행 시점 후보 중 **E4(비활성 전환)** 는 DP1 설계 문서 §1의 **결정점 B**와 시점도 대상도 같다. 같은 순간에 같은 세션의 KV를 두고 두 정책이 서로 다른 기준으로 결정을 내린다.

```text
   비활성 전환 시점
        ├── DP1: "이 KV를 어느 계층에 둘 것인가"   (재접근 시점·확률 기준)
        └── DP3: "이 KV를 버릴 것인가"             (Attention Importance 기준)
```

**순서를 고정하지 않으면 모순이 생긴다.** 두 결정의 무게가 다르므로([ADR-004](adr-004-demote-vs-drop.md) — Drop은 되돌릴 수 없다) 대칭적으로 다룰 수 없다.

**Goals**

- 두 정책이 같은 KV에 대해 모순된 결정을 내리지 못하게 한다
- 되돌릴 수 없는 결정(Drop)이 되돌릴 수 있는 결정(Demote)보다 먼저 일어나지 않게 한다

**Non-goals**

- DP1과 DP3를 하나의 정책으로 통합하는 것 — 판단 근거가 다르므로 분리를 유지한다

## 2. Decision Drivers

| 순위 | Driver | 왜 중요한가 |
|---:|---|---|
| 1 | 되돌릴 수 없음 | Drop은 복구 불가. 불필요한 Drop은 영구 손실 |
| 2 | 이득 귀속 | 순서가 정해져야 어느 DP가 무엇을 얻었는지 분리된다 |
| 3 | 검증 가능성 | 규칙이 한 지점에 모여 있어야 지켜지는지 확인할 수 있다 |

## 3. Options Considered

| 옵션 | 요약 | 장점 | 단점 | 되돌리기 |
|---|---|---|---|---|
| **A. DP3 먼저** | 중요도 낮은 KV를 먼저 버리고 남은 것을 배치 | 배치 대상이 줄어 DP1이 단순해진다 | **강등만으로 해결됐을 KV를 버린다.** 그 손실은 되돌릴 수 없다 | 어려움 |
| **B. 병렬 결정 + 조정자** | 두 정책이 각자 제안하고 조정자가 중재 | 두 기준을 모두 반영 | 중재 규칙이 사실상 제3의 정책이 된다. **비교 대상이 흐려진다** | 어려움 |
| **C. DP1 먼저, DP3는 실패 시에만** | 채택 | 불필요한 Drop이 구조적으로 발생하지 않는다. 이득 귀속이 명확 | DP3의 개입 빈도가 구성에 좌우된다 | 중간 |

## 4. Decision

**옵션 C를 선택한다. DP1이 먼저 배치를 시도하고, 그 결과가 용량 제약을 만족하지 못할 때만 DP3가 개입한다.**

```text
   비활성 전환
        │
        ▼
   DP1 Placement 결정  ──► 배치 가능한 계층이 있는가?
        │                        │
        │                       Yes ──► 배치 완료. DP3 개입 없음
        │                        No (§2.2의 (a)(b)(c))
        ▼                        │
   DP3 Drop 결정  ◄──────────────┘
        │
        ▼
   Importance 하위 KV 폐기 → 확보된 용량으로 DP1 재시도
```

- **DP3는 DP1의 실패 처리 경로이지 병렬 경로가 아니다.**
- **마지막의 "DP1 재시도"가 중요하다.** Drop은 자리를 만들 뿐이고, 남은 KV를 어디에 둘지는 여전히 DP1의 결정이다. 이 단계가 없으면 DP3가 배치까지 하게 되어 ADR-004의 역할 분담이 무너진다.
- 옵션 A는 영구 손실을 만든다. 옵션 B는 중재 규칙이 측정 대상을 오염시킨다.

## 5. Architecture Impact

**경계와 계약**

- `ReclaimCoordinator`가 **두 정책을 모두 아는 유일한 모듈**이다. 규칙이 한 파일에 모여 있어 지켜지는지 확인 가능하다.
- **`dp3_kv_reclaim`은 `dp1_kv_placement`를 import하지만 그 역은 없다** — 방향성 있는 의존이 "실패 처리 경로"를 구조로 옮긴 것이다.
- 두 정책을 병렬로 호출하는 경로가 구조에 존재하지 않는다.

**측정에 미치는 영향**

- **`else` 분기(DP1 실패)에 들어가는 빈도가 곧 "B1만으로 충분한가"에 대한 답**이다. 시퀀스의 실행 통계로 직접 관측된다.
- 이 분기가 거의 발생하지 않는 구성에서는 **C1/C2 비교 자체가 불필요하다** — 필요 없는 결정을 최적화하는 것이 된다.

**실패 모드**

| 실패 모드 | 조기 탐지 |
|---|---|
| 구현이 DP3를 먼저 호출 | `ReclaimPlan.issued_by` 순서 로그. Demote 없이 Drop이 선행한 사건 수 |
| DP1 실패 판정이 과하게 관대해 DP3가 자주 불림 | M-C5 Drop 비중이 구성 대비 비정상적으로 높음 |

## 6. Validation

- **DP1 실패율을 별도 지표로 집계한다.** 그 값이 DP3의 존재 근거를 직접 측정한다.
- **Drop 선행 사건은 0이어야 한다.** 0이 아니면 구현이 규칙을 위반한 것이며 해당 실행은 비교 불가.

## 7. Consequences

**긍정**

- 불필요한 Drop이 구조적으로 발생하지 않는다
- 두 DP의 이득이 분리 집계된다
- "그 구성에서 DP3가 필요한가"가 실행 통계로 답해진다

**대가**

- DP3의 개입 빈도가 DP1 구성(특히 연산형 계층 용량)에 좌우되므로, **DP3 단독 평가가 불가능하다.** 항상 DP1 Configuration을 병기해야 한다
- DP1 배치가 직렬로 선행하므로 회수 경로 전체 지연이 늘어난다 — E2(Admission)·E3(Step 경계)에서 특히 부담

## 8. 재검토 트리거

| 트리거 | 무엇이 달라지는가 |
|---|---|
| **직렬 선행으로 인한 지연이 SLO를 깨는 것으로 측정** | DP1 배치 가능 여부를 미리 캐싱해 실패를 예측하는 구조를 검토. 순서 자체는 유지 |
| DP1 실패율이 거의 100%인 구성이 상시화 | DP1 시도가 낭비가 된다. 실패 예측 후 DP3 직행 경로를 검토 |
| Drop이 되돌릴 수 있게 되는 경우 (예: 저비용 재계산) | 순서의 근거인 비대칭성이 약해진다 |
