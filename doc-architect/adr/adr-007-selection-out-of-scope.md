# ADR-007. 후보 선정을 설계 문서 범위 밖에 둔다

| | |
|---|---|
| **상태** | Accepted |
| **일자** | 2026-09-15 |
| **범위** | DP1 · DP2 · DP3 공통 |
| **근거 문서** | `doc-architect/README.md` 공통 원칙 / DP1 §13 / DP3 §10 |

---

## 1. Context

세 DP 모두 후보 구조 C1/C2를 제시하고 **정성적 QA 등급**(예: "C2가 Performance Efficiency 우위, C1이 Maintainability 우위")을 부여한다. 그 등급을 그대로 선정 근거로 쓸 것인지, 아니면 정량 측정 뒤로 미룰 것인지를 정해야 한다.

**설계 문서를 쓰는 사람과 측정을 수행하는 사람이 같다.** 결론을 먼저 적으면 이후 측정이 그 결론을 확인하는 방향으로 편향될 수 있고, 그 편향은 사후에 검출되지 않는다.

**Goals**

- 측정이 결론을 확인하는 절차가 되지 않게 한다
- 선정 결과가 유효한 조건 범위와 함께 기술되게 한다

**Non-goals**

- 후보를 영원히 선정하지 않는 것 — 별도 문서에서 정량 근거로 선정한다

## 2. Decision Drivers

| 순위 | Driver | 왜 중요한가 |
|---:|---|---|
| 1 | 결과의 신뢰성 | 확증 편향은 사후 검출이 어렵다 |
| 2 | 조건부 유효성 | 단일 결론은 파라미터 선택에 취약하다 |
| 3 | 의사결정 속도 | 선정을 미루면 구현 착수가 늦어진다 (역방향 Driver) |

## 3. Options Considered

| 옵션 | 요약 | 장점 | 단점 | 되돌리기 |
|---|---|---|---|---|
| **A. 설계 문서에서 선정** | QA 등급으로 후보 결정 | 빠르다. 구현 착수 가능 | **정성 등급은 가설이다.** 측정이 확인 절차로 전락 | 쉬움 |
| **B. 선정을 별도 문서로 분리** | 채택 | 측정이 판정 기능을 유지. 조건부 선정 가능 | 구현 착수가 측정 이후로 밀린다 | 쉬움 |
| **C. 잠정 선정 + 사후 수정** | 하나를 고르고 틀리면 바꾼다 | 착수와 검증을 병행 | **잠정 선정이 사실상 최종이 된다** — 이미 구현한 쪽을 버리기 어렵다 | 어려움 |

## 4. Decision

**옵션 B를 선택한다. 각 설계 문서는 Design Point의 정의와 후보 구조 제시까지를 범위로 하며 후보를 선정하지 않는다.**

선정은 정량 Trade-off 결과를 근거로 별도 문서에서 다루며, **"조건 X 범위에서는 C_i, 조건 Y 범위에서는 C_j"** 형태의 **조건부 선정 + 유효 범위**로 기술한다.

함께 고정하는 세 규칙:

| 규칙 | 내용 |
|---|---|
| **증거의 종류를 밝힌다** | 측정 / 대리 지표 / 실험은 신뢰 수준이 다르므로 같은 표에서 비교하지 않는다 |
| **판정 규칙을 실행 전에 고정한다** | 동일 seed 쌍으로 반복하고 신뢰구간이 0을 지나면 "차이 없음". 점 추정의 부호로 판정하지 않으며 사후에 규칙을 바꾸지 않는다 |
| **단일 수치 대신 곡선으로 보고한다** | 우열이 바뀔 수 있는 파라미터를 Sweep하고 교차 지점을 Band로 보고한다. Sweep 해상도 이상의 정밀도를 주장하지 않는다 |

- 옵션 C가 가장 위험하다. 잠정 선정은 구현 매몰비용이 쌓이면 사실상 최종이 되며, 그때 측정 결과는 되돌릴 힘이 없다.

## 5. Architecture Impact

**측정에 미치는 영향**

- 각 DP의 QA 등급표는 **정성적 가설**로 읽어야 하며, 각 행이 어느 Metric으로 검증되는지가 정해져 있어야 한다.
- 구현은 **두 후보를 모두 만들 수 있는 구조**여야 한다 — 이것이 세 DP의 구현 UML이 공통 인터페이스(`PlacementPolicy` / `DropPolicy`)와 공유 산술(`TierScorer` / `ImportanceScorer`)을 강제하는 이유다.

**대가가 발생하는 지점**

- 두 후보를 모두 구현해야 하므로 구현 비용이 늘어난다. **이 비용이 본 결정의 실제 가격이다.**

## 6. Validation

- 선정 문서가 **조건부 형태**로 쓰였는지 — 단일 결론이면 본 결정이 지켜지지 않은 것
- 판정 규칙이 **실행 전에** 문서화되었는지 — 커밋 시점으로 확인 가능

## 7. Consequences

**긍정**

- 측정이 판정 기능을 유지한다
- 결론이 유효 범위와 함께 기술되어 구성이 바뀔 때 무엇이 달라지는지 알 수 있다

**대가**

- 구현 착수가 측정 이후로 밀린다
- 두 후보를 모두 구현해야 한다

## 8. 재검토 트리거

| 트리거 | 무엇이 달라지는가 |
|---|---|
| **일정 압박으로 측정 전 구현 착수가 필요** | 옵션 C의 위험을 명시적으로 수용하는 결정이 되므로, 본 ADR을 Superseded로 바꾸고 그 사실을 기록한다. 조용히 어기지 않는다 |
| 한 후보가 모든 Sweep 축에서 일관되게 우세 | 조건부 선정이 단일 선정으로 축퇴한다. 본 결정과 모순되지 않는다 |
| 측정 비용이 두 후보 구현 비용을 크게 초과 | 비용 구조가 뒤집히면 재검토 대상 |
