# ADR-006. Prefix Cache 공유 Block을 Drop 대상에서 제외한다

| | |
|---|---|
| **상태** | Accepted |
| **일자** | 2026-09-15 |
| **범위** | DP3 |
| **근거 문서** | DP3 설계 문서 §2.4 / DP3 구현 UML §0, §2.1 |

---

## 1. Context

DP1 설계 문서 §1의 비활성 전환 계기 중 **"재사용분 보존"** 으로 남은 Block은 **다른 Request가 Prefix Cache Hit할 대상**이다. 즉 한 세션의 KV가 아니라 여러 세션이 공유하는 자원이다.

DP3의 판단 근거인 **Attention Importance는 자기 세션의 Query에 대해 산출된 값**이다. 다른 세션의 Query에 대한 중요도가 아니다. C1은 Representative Query에서, C2는 Actual Query에서 점수를 얻는데 **둘 다 그 Block을 참조할 다른 세션의 Query를 보지 않는다.**

따라서 공유 Block을 Drop하면 **판단 근거가 없는 대상에 대해 되돌릴 수 없는 결정을 내리는 것**이 되고, 손실이 해당 세션에 국한되지 않는다.

**Goals**

- 판단 근거가 없는 대상에 Drop이 적용되지 않게 한다
- cross-session 영향을 본 DP의 범위에서 배제한다

**Non-goals**

- 공유 Block의 회수 자체를 금지하는 것 — **Demote는 가능하다**(DP1의 결정)

## 2. Decision Drivers

| 순위 | Driver | 왜 중요한가 |
|---:|---|---|
| 1 | 판단 근거의 유효 범위 | 근거 없는 결정은 측정해도 해석할 수 없다 |
| 2 | 피해 범위 | cross-session 손실은 원인 추적이 어렵다 |
| 3 | 측정 오염 | 공유 Block Drop의 영향이 다른 세션의 지표에 섞여 들어온다 |

## 3. Options Considered

| 옵션 | 요약 | 장점 | 단점 | 되돌리기 |
|---|---|---|---|---|
| **A. 제외 없음** | 공유 여부 무관하게 Drop | 회수량 최대 | 근거 없는 Drop. **Hit 실패가 다른 세션의 TTFT로 나타나 원인 추적 불가** | 쉬움 |
| **B. 참조 수 기준 완화** | `ref_cnt`가 낮으면 Drop 허용 | 회수량과 안전의 절충 | 임계값이 정당화되지 않는다. `ref_cnt`는 과거 관측이고 Drop은 미래에 영향 | 쉬움 |
| **C. 전면 제외** | 채택 | 근거 없는 Drop이 발생하지 않는다. M-R2가 안전장치로 기능 | 회수 가능량이 줄어든다 | 쉬움 — 범위 제한이므로 넓히기 쉽다 |

## 4. Decision

**옵션 C를 선택한다. `ShareScope`가 `PREFIX_SHARED` 또는 `UNKNOWN`인 KVRange는 Drop 대상에서 제외한다.**

- **`UNKNOWN`을 함께 제외하는 것이 핵심이다.** 공유 여부를 모르는 Block을 Drop하면 막으려는 손실이 그대로 발생한다. **모르면 버리지 않는다**가 안전한 기본값이다.
- 이는 **본 DP의 범위 제한**이며 "공유 Block은 회수 불가"라는 뜻이 아니다. Demote는 DP1이 수행한다.

## 5. Architecture Impact

**경계와 계약**

- `DropEligibilityFilter`가 **정책보다 먼저** 걸러낸다. `DropPolicy.decide()`가 받는 목록은 이미 필터를 통과한 집합이다.
- 정책이 스스로 제외하게 두면 **M-R2가 정책 구현의 함수가 되어** 후보 비교가 오염된다.

**측정에 미치는 영향**

- **M-R2(Prefix Cache 오염)는 성능 지표가 아니라 안전장치다.** 0이 아니면 구현이 규칙을 위반한 것이며 해당 실행은 **비교 불가**로 표시한다.
- `UNKNOWN` 비율을 M-C5의 보조로 보고한다 — 이 값이 높으면 회수량 감소가 정책 때문이 아니라 판정 불능 때문이다.

**실패 모드**

| 실패 모드 | 조기 탐지 |
|---|---|
| `ShareScope` 판정이 부정확해 `UNKNOWN`이 과다 | `UNKNOWN` 비율. 회수량이 낮은데 정책 탓으로 오인될 위험 |
| 필터를 우회하는 경로가 생김 | M-R2 ≠ 0 |

## 6. Validation

- **M-R2 = 0을 사전 조건으로 확인한다.** 통과하지 못한 실행은 다른 지표를 읽지 않는다.
- `UNKNOWN` 비율을 결과와 함께 보고한다.

## 7. Consequences

**긍정** — 근거 없는 되돌릴 수 없는 결정이 발생하지 않는다. 지표 오염 경로가 닫힌다

**대가** — **회수 가능량이 줄어든다.** 공유도가 높은 워크로드에서 DP3의 이득이 구조적으로 작아지며, 이는 후보의 성능이 아니라 본 범위 제한의 귀결이므로 결과 해석에 명시해야 한다

**측정 불가능해지는 것** — "공유 Block까지 Drop했다면 얼마나 더 회수했을까"는 본 설계로 답할 수 없다

## 8. 재검토 트리거

| 트리거 | 무엇이 달라지는가 |
|---|---|
| **공유 Block에 대한 cross-session Importance 산출 방법이 마련됨** | 근거가 생기므로 제외 범위를 좁힐 수 있다. 예: 그 Block을 참조한 모든 세션의 Attention을 집계 |
| 공유도가 낮은 워크로드에서만 운용하는 것이 확정 | 제외의 비용이 작아 현행 유지 |
| `UNKNOWN` 비율이 높아 회수량이 크게 제한되는 것으로 측정 | `ShareScope` 판정 정확도 개선이 우선 과제가 된다 |
