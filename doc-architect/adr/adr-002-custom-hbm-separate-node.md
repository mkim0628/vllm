# ADR-002. Custom HBM을 GPU 패키지가 아닌 별도 노드로 모델링한다

| | |
|---|---|
| **상태** | Accepted |
| **일자** | 2026-09-15 |
| **범위** | DP1 (DP2·DP3에 전파) |
| **근거 문서** | DP1 설계 문서 §3.0, §3.2, §3.3 / `configs/memories_default.yaml` |

---

## 1. Context

대상 메모리 6종 중 **Custom HBM을 어디에 붙일 것인가**가 확정되지 않았었다. 이전 판은 on-package를 가정했고, 그때의 외부/내부 비대칭은 약 1.5배였다. 현재 판은 **GPU 노드 옆의 별도 메모리 노드**로 모델링하며 비대칭이 약 8.9배가 된다.

**이것은 성능 수치의 조정이 아니라 결론의 방향을 바꾸는 변경이다.** 이전 판은 "Custom HBM의 오프로드 이득은 대역폭이 아니라 GPU Occupancy뿐"이라고 결론지었으나, 별도 노드에서는 **Attention 오프로드가 선택이 아니라 사실상 전제**가 된다.

**Goals**

- 도달 경로의 대역폭을 물리적 배치에서 유도한다 — 메모리 자체의 대역폭이 아니라
- 연산 오프로드 판단의 1차 기준(외부/내부 비대칭)을 구성에서 계산 가능하게 한다

**Non-goals**

- 실제 제품 스펙의 확정 — 본 결정은 **시뮬레이션의 전제**이며 벤더 데이터가 아니다

**Constraints**

- Custom HBM만으로 구성되어 GPU-HBM을 대체하는 형태
- 연산 다이가 GPU 패키지 면적을 다투지 않는다

**Assumptions (출처 등급 병기 — DP1 §3.5)**

| 항목 | 값 | 등급 |
|---|---|---|
| scale-up fabric 방향당 대역폭 | 0.9 TB/s (NVLink 5 기준) | **공개 제품 수치** |
| 노드 내부 대역폭 | ~8.0 TB/s | **가정값** |
| 용량 | ~1 TiB (GPU HBM의 약 5배) | **가정값** |
| fabric 지연 | ~1 μs | **가정값** |

> **세 개가 가정값이다.** 본 결정에 의존하는 모든 결론은 그 사실을 함께 적어야 한다.

## 2. Decision Drivers

| 순위 | Driver | 왜 중요한가 |
|---:|---|---|
| 1 | 구조적 정합성 | 연산 다이를 넣으면서 HBM급 용량을 확보하는 구성은 on-package로 성립하기 어렵다 |
| 2 | 결정의 가시성 | 비대칭이 커야 "옮길까 vs 연산을 보낼까"가 실제 선택이 된다 |
| 3 | 보수성 | 외부 대역폭을 낮게 잡는 쪽이 오프로드 이득을 **과대평가하지 않는다** |

## 3. Options Considered

| 옵션 | 요약 | 장점 | 단점 | 되돌리기 |
|---|---|---|---|---|
| **A. on-package** | GPU 패키지 안 | 도달 경로가 가장 빠름. 비대칭 ~1.5배 | **용량이 제한된다** — 연산 다이가 면적을 다툰다. 비대칭이 작아 오프로드 이득이 GPU Occupancy로 축소 | — |
| **B. 별도 노드 (scale-up fabric 1홉)** | GPU 옆 메모리 노드 | **용량을 크게 가져갈 수 있다.** 비대칭 8.9배 → 오프로드가 명확한 이득 | fabric 대역폭에 종속. 가정값이 셋 | 중간 |
| **C. CPU 경유 (CXL-PNM과 동일 취급)** | CPU 측 | 기존 계층과 일관 | Custom HBM의 존재 이유(HBM급 내부 대역폭)가 사라진다 | — |

## 4. Decision

**옵션 B를 선택한다. Custom HBM은 GPU 노드 옆의 별도 메모리 노드이며 scale-up fabric 한 홉을 탄다.**

- **용량이 이 메모리의 존재 이유다.** 연산 다이를 넣으면서 GPU HBM의 약 5배 용량을 갖는 구성은 on-package(옵션 A)로 성립하기 어렵다.
- 그 귀결로 **비대칭이 8.9배가 되고, 이 메모리에서는 Attention 오프로드가 전제가 된다** — fabric으로 KV를 끌어내면 로컬 HBM 대비 크게 느리지만, 노드 안에서 Attention을 수행하면 로컬 HBM과 대등한 처리량을 낸다.
- 옵션 C는 Custom HBM을 CXL-PNM과 구분할 이유를 없앤다.

## 5. Architecture Impact

**경계와 계약**

- 세 가지 도달 경로가 구성에서 구분된다 — on-package(0홉) / scale-up fabric(1홉) / CPU 경유(2홉). **대역폭이 자릿수로 다르다.**
- `MemorySpec`에 외부 BW와 내부 BW가 **별도 필드**로 존재해야 한다. 하나로 합치면 이 결정이 표현되지 않는다.

**귀결**

- **DP2가 직접 영향을 받는다.** Custom HBM 노드가 별도 노드이므로 "어느 Compute Node에서 Prefill을 할 것인가"의 후보 구성과 Data Movement Cost가 달라진다.
- DP3의 §2.2 (b) 조건이 완화된다 — 연산형 계층으로 강등해도 그 자리에서 쓸 수 있다.

**실패 모드**

| 실패 모드 | 조기 탐지 |
|---|---|
| 내부 대역폭 가정값(8.0 TB/s)이 실제보다 크게 높아 오프로드 이득이 과대평가 | §4.2 균형점 Sweep에서 이득이 가정값에 과민하게 반응 |
| fabric 세대가 바뀌어 비대칭이 줄면 Mode A와 Mode C의 격차가 사라짐 | fabric 세대 Sweep에서 두 Mode의 교차 |

## 6. Validation

- **DP1 §3.6의 HW팀 확인 항목**이 채워지면 가정값 셋이 공개값으로 대체된다. 그 전까지 이 ADR에 의존하는 결론은 모두 조건부다.
- **Sweep 필수** — `Custom HBM 노드 내부 대역폭`과 `scale-up fabric 세대`를 축으로 훑는다 (DP1 §11.6). 고정값으로 두고 결론을 내면 안 된다.

## 7. Consequences

**긍정**

- 오프로드 판단의 1차 기준(외부/내부 비대칭)이 구성에서 계산된다
- 용량 계층으로서의 값어치와 속도로서의 값어치가 분리되어 보인다

**대가**

- **핵심 수치 셋이 가정값이다.** 이 ADR에 의존하는 모든 정량 결론은 조건부이며, HW 확정 전까지 절대값을 주장할 수 없다
- 이전 판의 결론(“오프로드 이득은 GPU Occupancy뿐”)이 문서에 남아 있으면 모순이 된다 — 기존 서술을 정리해야 한다

## 8. 재검토 트리거

| 트리거 | 무엇이 달라지는가 |
|---|---|
| **HW팀이 실제 스펙을 확정** (§3.6) | 가정값 셋이 대체된다. 비대칭이 크게 줄면 옵션 A 쪽 결론으로 회귀할 수 있다 |
| scale-up fabric 차세대 / UALink 고밀도 구성 | 외부 대역폭이 올라가 비대칭이 줄고, Mode A/C 격차와 스트리밍 성립 여부가 함께 바뀐다 |
| Custom HBM이 on-package 형태로 제품화 | 본 ADR을 Superseded로 바꾸고 새로 쓴다 |
