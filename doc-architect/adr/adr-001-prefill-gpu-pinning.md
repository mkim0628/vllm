# ADR-001. Prefill 연산을 GPU에 고정한다

| | |
|---|---|
| **상태** | Accepted |
| **일자** | 2026-09-15 |
| **범위** | DP1 · DP2 · DP3 공통 |
| **근거 문서** | DP1 설계 문서 §4.2, §4.5 / DP1 구현 UML §0 |

---

## 1. Context

이기종 메모리 중 **Custom HBM · CXL-PNM · SSD-PIM은 근접 연산 유닛을 갖는다.** "연산을 데이터가 있는 곳으로 보낸다"는 전제를 받아들이면, **Transformer의 어느 연산까지 보낼 것인가**를 정해야 한다. Attention은 KV를 읽으므로 후보이고, Prefill과 Decode는 둘 다 Attention을 수행한다.

**Goals**

- 연산형 메모리를 활용할 수 있는 구간을 명확히 한정한다
- HW팀에 요구할 연산 성능의 **상한**을 제시한다 ("최대한 많이"가 아니라 균형점)

**Non-goals**

- Prefill을 *어느 노드의* GPU에서 수행할지 — DP2의 쟁점이다
- Projection·FFN의 실행 위치 — KV에 접근하지 않으므로 본 결정의 대상이 아니다

**Constraints**

- 근접 연산 유닛의 면적·전력 예산은 GPU와 자릿수가 다르다
- Decode step의 지연 예산은 대화형 SLO에 묶여 있다

**Assumptions**

- Attention 연산 강도 `= (H/KVH) × q` [FLOP/byte]는 **연산 자체의 성질**이며 가정이 아니다 (DP1 §4.2의 유도)
- 근접 연산 유닛이 GPU급 연산 성능에 도달하지 못한다 — **가정값**. 벤더 스펙이 확정되면 검증 대상

## 2. Decision Drivers

| 순위 | Driver | 왜 중요한가 | 어떻게 재는가 |
|---:|---|---|---|
| 1 | 구조적 타당성 | 연산 강도가 감당 범위를 넘으면 오프로드가 이득이 아니라 손해 | §4.2의 균형점 대비 실제 연산 성능 |
| 2 | 자원 병렬화 | 이 구조가 얻는 것 자체 (§4.6) | M-P7b 자원 병렬도 |
| 3 | 설계 단순성 | 경로가 하나면 검증할 분기가 줄어든다 | M-M1 결정 경로 복잡도 |

## 3. Options Considered

| 옵션 | 요약 | 장점 | 단점 | 되돌리기 |
|---|---|---|---|---|
| **A. Prefill·Decode 모두 GPU** | 오프로드 없음 | 단순. 현행 vLLM 그대로 | 연산형 메모리를 쓸 이유가 없어진다. 본 과제의 전제가 사라짐 | 쉬움 |
| **B. Decode Attention만 오프로드** | Prefill은 GPU 고정 | 연산 강도가 GQA 비율(상수)로 낮아 근접 연산 유닛 사정거리 안. **자원 병렬화가 성립** | Decode step 자체는 느려질 수 있다 | 중간 |
| **C. Prefill도 오프로드** | 전면 오프로드 | KV를 아예 옮기지 않아도 됨 | **연산 강도가 query token 수(수백~수천)에 비례해 커진다.** 필요 연산 성능이 GPU급이 되어 근접 연산 유닛으로 감당 불가 | 어려움 |

## 4. Decision

**옵션 B를 선택한다. Prefill Attention은 GPU에서 수행하고, Decode Attention만 연산형 메모리로 보낼 수 있다.**

- Attention 연산 강도는 **query token 수에 비례**한다. Decode는 q=1이라 GQA 비율(예: 8:1이면 8 FLOP/byte)에 머물지만, Incremental Prefill은 q=ΔT(수백~수천)라 같은 식이 자릿수로 커진다.
- 따라서 **대역폭 한계(Decode)와 연산 한계(Prefill)로 구조가 갈린다.** 근접 연산 유닛이 잘할 수 있는 것은 전자뿐이다.
- 이 결정이 **요구 연산 성능의 상한을 준다** — `내부 대역폭 × GQA 비율`을 넘는 연산 성능은 대역폭이 병목이 되어 이득이 없다. HW팀에 요구할 숫자가 이 균형점이다.
- 옵션 C는 산술적으로 배제된다. 선호가 아니라 연산 강도의 귀결이다.

## 5. Architecture Impact

**경계와 계약**

- 구현 모듈이 갈린다 — `prefill_path.py`(복원/스트리밍만 결정)와 `decode_offload.py`(오프로드 계획). **`prefill_path.py`에는 메모리로 연산을 보내는 경로가 아예 없다.**
- **어떤 시퀀스에도 "메모리에서 Prefill을 수행하는" 경로가 없어야 한다** — 이것이 구조의 최상위 불변식이다.

**귀결**

- 하위 계층으로 내려간 KV가 재활성되면 **GPU 쪽으로 와야 한다** (DP1 §4.5의 복원/스트리밍 두 경로). Prefill을 보낼 수 없으므로 데이터가 오는 수밖에 없다.
- DP3에서 Drop한 KV의 재계산도 **GPU에서 일어난다** — Drop은 메모리 압력을 GPU 압력으로 전환한다 (DP3 §9.5 M-R1).

**실패 모드**

| 실패 모드 | 조기 탐지 |
|---|---|
| 근접 연산 유닛 성능이 균형점에 크게 못 미쳐 Decode도 연산 한계가 된다 | M-P7 오프로드 채택률이 낮고 M-P3가 개선되지 않음 |
| 재활성이 잦아 GPU Prefill 부하가 병목이 된다 | M-P7b 병목 자원 비율이 GPU 쪽으로 쏠림 |

**관측**

- M-P7b(GPU 점유율 / 자원 병렬도) — §4.6의 이득이 실제로 발생했는지
- M-P2 재활성 TTFT — 이 결정이 지불하는 대가

## 6. Validation

- DP1 §3.6의 HW 확인 항목 1·2·3(근접 연산 유닛의 연산 성능, 내부 대역폭)이 채워지면 **균형점을 계산해 옵션 C의 배제가 수치로 확인된다.**
- 시뮬레이션에서 **자원 병렬도(M-P7b)가 1.0에 머무르면 옵션 B의 근거인 §4.6이 성립하지 않은 것**이다.

## 7. Consequences

**긍정**

- 연산형 메모리에 요구할 성능의 상한이 정해진다 — HW 요구사항이 유한해진다
- Prefill/Decode 경로가 모듈로 갈려 검증할 분기가 줄어든다

**대가**

- 재활성 시 KV가 GPU 쪽으로 와야 하므로 **복원 비용을 피할 수 없다.** 이것이 DP1 결정점 B가 존재하는 이유이자 그 결정의 난이도
- Long Context에서 재계산 비용이 Context 길이에 대해 선형 이상으로 커진다 (DP3 M-R1)

**측정 불가능해지는 것**

- "Prefill을 오프로드했다면 어땠을까"는 본 설계의 시뮬레이션으로 답할 수 없다. 옵션 C를 재검토하려면 별도 실험이 필요하다

## 8. 재검토 트리거

| 트리거 | 무엇이 달라지는가 |
|---|---|
| **Chunked Prefill의 chunk 크기를 매우 작게 잡는 구성** | 연산 강도는 `(H/KVH) × q`이고 q가 chunk 크기다. chunk를 충분히 줄이면 연산 강도가 Decode에 근접한다 — **옵션 C의 배제 근거가 그 구간에서는 약해진다.** 다만 chunk를 줄이면 계층당 왕복 횟수가 늘어 §4.3의 (ii)가 커지므로, 두 효과의 균형점을 따로 계산해야 한다 |
| 근접 연산 유닛의 연산 성능이 GPU급에 근접 | 옵션 C가 다시 후보가 된다 |
| GQA 비율이 크게 높은 모델 (KV head 수가 매우 적음) | Decode의 연산 강도가 올라가 균형점이 이동한다 |
