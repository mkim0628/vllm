# 한눈에 보기

> 일반 SW 개발 관점의 요약이다. 이 문서의 ID(F/Q/C/P)는 슬라이드와 설계 문서가 같이 쓴다.

- **DP0이 정하는 것**: 여러 서버(추론 서버 = vLLM 인스턴스)를 묶어 요청을 나눠 주는 **요청 조율 계층 (Orchestration)** — 로드밸런서 + 스케줄러에 해당 — 을 기성 오픈소스(llm-d)를 확장해서 만들지(1안), 직접 만들지(2안)이다.
- **기능 요구사항 F1~F6 (무엇을 해야 하나)**: 요청 라우팅, 메모리 상태 수집, Prefill/Decode(P/D) 분리 결정, 요청별 노드 지시, 흐름 제어, 서버 발견·확장. 오픈소스가 기본 제공하는 것이 많고, 우리가 더할 것은 "이기종 메모리 상태를 반영하는 부분"이다.
- **품질 속성 Q1~Q4 (얼마나 잘해야 하나)**: 처리량(Q1), 응답 지연(Q2), 변경 용이성(Q3), 서버를 늘릴 때의 확장성(Q4). **목표 수치는 baseline을 측정한 뒤 확정**한다(지금은 만들어 두지 않는다).
- **제약 C1~C6 (반드시 지킬 조건)**: vLLM 고정, GPU 8장 서버 2대 환경, 모델 정확도 불변, 오픈소스 업스트림 추적 가능, 서버 내부 설계(DP1~DP4)와의 접점 계약 고정, 정책 5개(P1~P5) 표현 가능.
- **정책 P1~P5 (우리가 조율 계층에 넣을 판단 로직)**: 메모리 종류별 점수, 실시간 메모리 상태, 비용 기반 적중 점수, 비용 기반 P/D 분리 판단, 요청별 노드 지시. llm-d에서는 설정 2개 / 확장 모듈 2개 / P5는 경로에 따라 확장 모듈 또는 기존 모듈 수정이다.
- **현재 잠정 결과(가설)**: 처리량 동등, 지연 2안 유리(미측정), 변경·유지 용이성 2안 유리(시나리오 3 대 3이나 정책 변경 S2~S4 가중 가정, 같은 가중이면 동등), 확장성 1안 유리(2안은 레플리카 상태 비공유로 ●○○ 예상). QA 4개의 별 합계는 **9 대 9 동점**이고, 동점이면 QA 우선순위(**Q1 처리량 > Q2 지연 > Q3 변경·유지 용이성 > Q4 확장성**, 소유자 확정)가 정하므로 **2안 선택**(조건: E1 선행)이다. 구현 부담·증거 수준 같은 제약·리스크는 QA 밖에 병기한다 (설계 문서 §6.6, §7.4).

# 1. 범위와 읽는 방법

DP0은 이기종 메모리(HBM/DRAM/CXL/HBF/SSD 등)가 섞인 멀티 노드 AI Serving 시스템에서 **서버 간 요청 조율 계층의 구조**를 정한다. 설계 문서는 후보·평가·실험 결과를 다루고, 이 문서는 **요구사항만** 확정한다(단일 출처).

- **서버 간(클러스터) 결정**: 요청을 어느 추론 서버(vLLM 인스턴스)가 처리할지, P/D 짝짓기, 서버 간 KV 캐시 공유. 이 문서의 범위.
- **서버 내부 결정**: 한 인스턴스 안의 배치·블록·메모리 계층 결정. DP1~DP4의 범위(접점은 C5).
- 기능 블록 A~F는 설계 문서 §2.3의 정의를 그대로 쓴다.

| 블록 | 기능 | 쉬운 설명 |
|---|---|---|
| A 요청 경로 | 요청 수신·전달·응답 중계 | 입구(게이트웨이). 모든 F의 전제 |
| B 결정 로직 | 후보 서버 선택 | 후보 서버에 점수를 매겨 고르는 단계 (Filter→Score→Pick) |
| C 상태 수집 | KV index, 메트릭 | 서버들의 상태 수치(메트릭)와 캐시 보유 위치 수집 |
| D 흐름 제어 | admission, 큐잉 | 과부하 시 대기·우선순위·거절 |
| E P/D 조율 | prefill→decode 연결, KV 전송 파라미터 조립 | Prefill 서버와 Decode 서버를 이어 주는 중간 역할 |
| F 발견·확장 | worker 발견, 확장 | 서버 추가·제거 자동 인지 |

# 2. 기능 요구사항 F1~F6 (무엇을 해야 하는가)

> A 요청 경로(요청 수신·중계)는 모든 F의 전제 기능이다. OSS(llm-d)가 기본 제공하는 것은 F5, F6 전부와 F1·F2·F3의 기본 형태이고, 우리가 추가해야 하는 것은 F1~F4에서 **이기종 메모리 상태를 반영하는 부분**(정책 P1~P5)이다.

| ID | 요구사항 | 설명 | 이유 (왜 필요한가) | 대응 블록 | OSS 기본 제공 여부 (llm-d / Dynamo) | 검증 방법 |
|---|---|---|---|---|---|---|
| **F1** | 요청 라우팅 (서버 선택) | 들어온 요청을 어느 추론 서버가 처리할지 고른다. 서버별로 "이전 대화의 중간 결과(KV 캐시)가 어느 메모리에 있는지"와 부하를 반영한다 | 서버 내부에서 얻은 성능 이득(캐시 재사용)이 서버 간 요청 배분에서 사라지지 않게 하려면(이득 보존) 배분이 메모리 상태를 알아야 한다 | B 결정 로직 | 기본 형태 제공(Filter→Score→Pick, 정적 가중치). 이기종 메모리 반영은 P1~P3로 추가 / Dynamo는 KV Router 제공, 새 메모리 반영은 core 수정 필요 [C] | llm-d: 합성 백엔드로 Router를 끝단까지 실행해 P1~P3 점수 확인 [A] (E2). 실제 vLLM end-to-end는 E4 |
| **F2** | 메모리 상태 수집 | 각 서버에서 올라오는 "KV 캐시 보유 위치(메모리 종류)" 이벤트와 "메모리 사용량·전송 대기" 같은 실시간 수치를 모아 결정의 입력으로 쓴다. 새 메모리 종류(CXL, HBF 등)를 구분할 수 있어야 한다 | 결정의 입력 해상도가 낮으면(고정 값, 종류 구분 없음) 이기종 메모리의 이득을 점수에 반영할 수 없다 | C 상태 수집 | 기본 형태 제공(KV 이벤트 수신, `/metrics` 수집) / Dynamo는 이벤트 plane 제공, 메모리 종류는 device/host/disk 고정 필드 [C] | P1·P2 설정으로 새 메모리 이름·수치 반영 확인 [A]. 상태 신선도(이벤트→색인 지연)는 E3 |
| **F3** | Prefill/Decode(P/D) 분리 결정·조율 | 요청마다 입력 처리(Prefill)와 응답 생성(Decode)을 서로 다른 서버에서 나눠 실행할지, Prefill을 어디서 할지 정하고 서버 간 KV 캐시 전송(NIXL) 정보를 전달한다 | P/D 전환점은 첫 응답까지 걸리는 시간(TTFT)과 Goodput에 가장 큰 영향을 주는 레버다 | B 결정 로직, E P/D 조율 | 기본 형태 제공(정적 임계값 기반 decider, P/D 보조 프로세스). 비용 기반 판단은 P4로 추가 / Dynamo는 PrefillRouter + conditional disagg 제공, 새 판단은 core 수정 [C] | P4 wrapper를 끝단까지 실행 [A] (E8). 실제 NIXL 전송 성능은 E4 |
| **F4** | 요청별 노드 지시 전달 | 요청마다 서버에 "KV를 어느 메모리에서 몇 토큰까지 불러와라" 같은 메모리 사용 지시를 내려보낸다 (`kv_load_tiers`, `max_load_tokens`) | 조율 계층의 결정이 서버 내부 동작에 반영되는 출력 경로. 없으면 정보만 보고 지시는 못 내린다 | E P/D 조율 | 일반 경로는 body 변경 지점 제공(확장 모듈로 사용), P/D 경로는 보조 프로세스가 값을 덮어씀 [C] / Dynamo는 일반 송신 경로 없음(추정) [C] | aggregated 경로 body 변경을 Router 끝단까지 확인 [A] (E6). P/D 경로는 코드 분석 [C]. 실제 vLLM에서 메모리 선택이 바뀌는 효과는 **미확인** |
| **F5** | 흐름 제어 | 과부하일 때 요청을 대기·우선순위·거절로 조절해 SLO를 지킨다 | 과부하 시 무제한 수락하면 SLO 위반으로 Goodput이 떨어진다 | D 흐름 제어 | 제공(llm-d 흐름 제어, 기본 off / Dynamo 큐 임계값·`fcfs`/`lcfs`/`wspt`) [C] | 기능 존재는 코드 확인 [C]. 과부하 시 Goodput 효과는 E4 |
| **F6** | 서버 발견·확장 | 서버(인스턴스)가 추가·제거되면 자동으로 알아채고 요청 대상에 반영한다 | 서버 수 증가·장애에 운영자 개입 없이 대응. Q4(확장성)의 전제 | F 발견·확장 | 제공(llm-d 서버 풀/Kubernetes, Dynamo discovery + Planner) [C] | file-discovery로 Router 기동 확인 [A] (llm-d 분석 E3, E4). 실제 확장 동작은 미확인 |

※ 근거: 설계 문서 §2.3, §5.1, §6.1, §7.5. 검증 칸의 실험 번호 E1~E4는 설계 문서 §9.2의 증거 계획 번호이고, 괄호 속 E2·E6·E8 등은 llm-d 분석 문서의 코드 실험 번호(합성 백엔드)이다.

# 3. 품질 속성(QA) Q1~Q4 (얼마나 잘해야 하는가)

과제 QA 목록(Throughput, Latency, Resource Utilization, Functional Correctness, Modifiability, Scalability) 중 DP0에 해당하는 4개를 쓴다. 공통 정의와 근거 수준 규칙은 [`../Evaluation/qa-evaluation-criteria.md`](../Evaluation/qa-evaluation-criteria.md)를 따른다.

## 3.1 QA 시나리오 표 (6요소)

> 아키텍처 QA 시나리오의 6요소: 자극 출처 / 자극 / 환경 / 대상 / 응답 / 응답 측정. **목표 수치는 만들지 않는다.** baseline 측정 후 확정한다.

| ID | QA | 자극 출처 | 자극 | 환경 | 대상 | 응답 | 응답 측정 (지표) | 목표 |
|---|---|---|---|---|---|---|---|---|
| **Q1** | Performance — Throughput | 클라이언트(요청 생성기) | 캐시 재사용이 많은 요청(같은 대화·문서 prefix 반복)이 지속 유입 | 정상 운전, 메모리 종류가 섞인 추론 서버 ≥2대, 요청률을 서비스 목표(SLO)가 깨지기 직전까지 올림 | 요청 조율 계층(블록 B, C) | 이기종 메모리 상태(P1~P3)를 반영해 서버를 선택하고 서비스 목표를 지킴 | **Max SLO Goodput** (서비스 목표를 지키면서 낼 수 있는 최대 처리량, tokens/s). 과제 공통 지표 TPS와 동일 계열 | baseline(기존 OSS 기본 설정, 정적 가중치) 대비 향상. 수치는 baseline 측정 후 확정 |
| **Q2** | Performance — Latency | 클라이언트 | 요청 1건이 도착해 서버가 선택되는 순간 | 정상 운전, 부하 수준별(저·중·고) | 요청 조율 계층의 결정 경로(블록 A, B, 원격 호출 포함) | 결정을 내려 요청을 서버로 전달 | **TTFT**(첫 응답까지 걸리는 시간) p50/p99, 그중 **결정 경로가 더하는 시간**(결정을 비운 "null 결정" 대비 증분), TPOT(토큰당 생성 시간) 악화 여부 | 결정 경로 추가 시간 < 허용 한도(한도는 E1 측정 후 확정), TPOT 악화 없음 |
| **Q3** | Modifiability (변경 용이성) | 개발자(우리 팀) | 새 메모리 종류·새 정책·새 지시 항목 추가 요구 (변경 시나리오 S1~S6, 설계 문서 §7.3) | 개발 시점. OSS 업스트림이 계속 변경되는 중 | 요청 조율 계층의 코드·설정 | 기존 구조를 바꾸지 않고 설정/확장 모듈로 반영 | 시나리오별 **변경 범위**: 수정 모듈 수, 외부(OSS) 코드 수정 여부, 재배포 필요 여부 | S1(새 메모리 종류)은 설정만, S2~S3(비용 함수, P/D 정책 교체)는 확장 모듈, S4(노드 지시 추가)는 최소 수정 |
| **Q4** | Scalability (서버를 늘릴 때의 확장성) | 운영자 / 클라이언트 | 서버 수·노드 수와 요청률이 증가 | 서버 N배 증설, 요청률 N배 | 요청 조율 계층 전체(A~F) | 조율 계층이 병목이 되지 않고 선형에 가깝게 확장 | **Scaling Efficiency (%)** = 서버·노드를 N배로 늘렸을 때 처리량이 N배의 몇 %인가 (과제 공통 정의), 조율 계층이 병목이 되는 시점 | 병목 없이 확장. 우리 환경(2노드)으로는 실측 불가 → 분석·시뮬레이션 |

**QA 우선순위 (소유자 확정)**: Q1 Throughput > Q2 Latency > Q3 Modifiability > Q4 Scalability (QA 번호 순서가 우선순위). 별 합계가 같을 때 처음으로 별이 갈리는 QA가 선택을 정한다(설계 문서 §7.4.4). 근거: DP0의 목적은 이기종 메모리 이득이 요청 배분에서 사라지지 않게 하는 것, 즉 성능 보존이다.

## 3.2 실험과 근거 수준

| ID | 연결 실험 (설계 문서 §9.2) | 근거 수준 | 현재 상태 |
|---|---|---|---|
| Q1 | **E4**: end-to-end Max SLO Goodput (pod 2개 이상, 노드 간 RDMA 유무가 변수). 선행: E2 표현력 프로브(P1~P5 표현 가능 여부) | E4 = [A] 목표, E2 = [A]+[C] | E2 완료(합성 백엔드), E4 미수행. 처리량 "동등"은 가설 |
| Q2 | **E1**: 결정 경로 오버헤드 (null 결정 vs 실제 결정의 TTFT p50/p99 증분. llm-d는 KIND, Dynamo는 bare-metal). **E3**: 상태 신선도(이벤트→색인 지연, 낡은 캐시 적중 비율) | [A] 목표 | 둘 다 미수행. "2안 유리"는 hop 1개 차이라는 구조 가설 [C] |
| Q3 | 구조 논증 + llm-d 코드 실험(E2: 설정 2 / 확장 모듈 2 / P5 경로별) | [C] + 일부 [A] | E2 완료. 업스트림 변경에 대한 호환성 약속은 문서에서 찾지 못함(미확인) |
| Q4 | 분석·시뮬레이션(2노드로 실측 불가) | [C] | 미수행 |

## 3.3 비교에서 제외한 QA와 이유

| QA | 제외 이유 | 처리 |
|---|---|---|

## 3.4 제약 · 리스크 (QA 밖)

> QA 4개의 별 합계에 넣지 않는 **선택의 부가 근거**다. 공통 QA 기준 문서(`../Evaluation/qa-evaluation-criteria.md`)는 바꾸지 않았고, DP0 설계 문서 §7.4.1에서 후보별로 값을 적는다. 별점은 주지 않고 항목마다 유리한 쪽만 표시한다. 유지 부담(업스트림 추종·신기능 확보)은 Q3의 S5·S6에 이미 있으므로 여기서 다시 세지 않는다. 왜 QA에 넣지 않았는지의 논리는 설계 문서 §7.4.1.

# 5. 정책 P1~P5 (우리가 조율 계층에 넣어야 하는 판단 로직)

정책은 "서버 내부의 이기종 메모리 이득을 서버 간 요청 배분에서 살리기 위해 조율 계층이 해야 하는 판단"이다(C6). 구현 방식은 기존 OSS 코드를 얼마나 건드리는지로 구분한다.

| 구분 | 의미 | 설계 문서 §2.5 등급 |
|---|---|---|
| **설정만** | 기존 설정 파일에 이름·값만 추가 | C |
| **확장 모듈(plugin)** | 기존 코드를 안 고치고 끼워 넣는 코드. 자체 실행 이미지 빌드 필요 | P |
| **기존 모듈 수정(patch)** | OSS 코드를 직접 수정 | F |

| ID | 이름 | 쉬운 설명 | 구현 방식 (llm-d) [A=실행 확인] | 근거 |
|---|---|---|---|---|
| **P1** | 새 메모리 종류를 캐시 적중 점수에 반영 | 캐시가 HBM/DRAM/CXL/SSD 중 어디에 있는지에 따라 점수 가중치를 다르게 준다 (메모리 종류별 가중치 표) | **설정만** (가중치 표에 이름·값 추가) [A] | `kvCacheBackendConfigs{name,weight}`. 미설정 가중치는 0.0이라 `storage` 같은 이름은 값을 설정해야 한다 (설계 문서 §7.5) |
| **P2** | 실시간 메모리 상태 반영 | 서버가 알려 주는 "메모리 사용량·전송 대기" 같은 수치를 읽어 점수에 가감한다 | **설정만** (읽을 수치 이름 지정) [A] | `customMetrics` + `endpoint-attribute-scorer`. 캐시 적중 점수와 별도로 가산되므로 근사 |
| **P3** | 비용 기반 적중 점수 | "KV를 다시 계산하는 비용"과 "그 메모리에서 가져오는 비용"을 비교해 점수를 매긴다 (점유율이 높으면 감점) | **확장 모듈(plugin)** 추가 [A] | 외부 Go 모듈의 Scorer. 단위 테스트만으로는 부족했고 끝단 실행으로 확인(설계 문서 §6.1) |
| **P4** | 비용 기반 P/D 분리 판단 | 요청마다 Prefill/Decode를 나눠 실행할지, Prefill을 어디서 할지를 비용 비교로 판단한다 | **확장 모듈(wrapper)** 추가 [A] — 기존 모듈을 감싸는 방식 | `disagg.Handler`를 embed한 P/D 판단 모듈 wrapper. 취약점: 기존 모듈의 관찰된 동작에 의존 |
| **P5** | 요청별 노드 지시 (송신=오케스트레이션, 수신·실행=엔진) | 요청마다 서버에 "어느 메모리에서 몇 토큰까지 불러와라"를 지시한다 | 일반 경로는 **확장 모듈**로 가능 [A], **P/D 경로는 기존 모듈(보조 프로세스) 수정 필요** [C] | P/D 경로에서는 보조 프로세스가 `kv_transfer_params`를 덮어씀. 실제 vLLM에서의 효과는 미확인 |

> **범위**: P5의 **수신·실행**은 vLLM(엔진) 쪽이고 사용자 fork에는 없다(두 후보 공통 선결). DP0가 맡는 것은 **지시의 결정과 송신**이다. 정책별 두 쪽의 분담은 설계 문서 §4.2.

Dynamo 기준 구현 방식은 P1, P2, P4가 core 수정, P3는 제한적 plugin(빌드 미검증), P5는 core 수정(추정)이다 [C] (설계 문서 §7.5).

- QA 목표 수치(Q1 향상 폭, Q2 결정 경로 허용 한도, Q4 효율)는 **정하지 않았다**. baseline(기존 OSS 기본 설정) 측정 후 확정.
- 처리량·지연·확장성 평가는 전부 가설이며 E1, E3, E4는 미수행이다. llm-d 쪽 P1~P5 확인은 합성 백엔드 기준이다.
- 실제 vLLM이 내보내는 KV 이벤트와 llm-d 어댑터의 호환, `kv_load_tiers`/`max_load_tokens`가 실제로 메모리 선택을 바꾸는 효과, 서버 간 RDMA 유무는 미확인이다.
- Dynamo는 코드·문서 읽기 기반이며 Rust 빌드를 하지 않았다.
