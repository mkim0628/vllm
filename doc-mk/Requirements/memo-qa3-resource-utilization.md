# 메모: QA3(Resource utilization)를 DP 공통으로 어떻게 정의할 것인가

> 작성: 2026-10-09. 상태: **Claude 의견, 사용자 결정 전**. 질문: "P/D 풀 사용률을 높이는 것이 우리 런타임이 풀어야 할 목표가 맞는가? DP1은 HBM 사용량이 맞아 보이고 DP2는 풀 사용률이 목표로 보이지 않는다."

## 1. 결론부터

**아니다. P/D 풀 사용률을 높이는 것은 이 런타임의 목표가 아니라 수단이다.** 사용자의 직관이 맞다. 과제 정의(`project-context.md` §1)는 "계층적 memory를 효율적으로 사용해 **성능을 높이는** 런타임"이고, 성능의 최종 지표는 SLO를 지키는 처리량(QA1)과 지연(QA2)이다. 사용률은 그 결과이거나 원인일 뿐 독립된 목표가 아니다.

## 2. 근거

1. **사용률 ↑가 항상 좋은 것은 아니다.** 사용률이 높다는 것은 headroom이 없다는 뜻이기도 하다. 큐가 쌓이고 tail 지연이 커지는 방향이다. 사용률 자체를 올리는 정책은 "일을 억지로 더 시키는" 정책과 구분되지 않는다.
2. **DP2의 `U_useful`은 사실상 goodput을 다시 쓴 것이다.** `U_useful = Σ(iteration 시간 × SLO 충족 요청 토큰 비중) ÷ (노드 수 × 측정 시간)`은 "SLO를 만족한 일의 양 ÷ 용량"이고, 노드 수가 고정이면 QA1(Max SLO Goodput)과 같은 정보다. DP1에서도 이미 같은 현상이 확인되었다(풀 활용률 U와 처리량 배수의 상관 0.99, `qa-criteria-dp1.md` §G). 독립된 품질 속성으로서의 판별력이 없다. DP4가 Resource Utilization을 "Throughput과 같은 원인에서 나와 독립 판별력이 없다"며 제외한 것과 같은 판단이다.
3. **ISO/IEC 25010의 정의와도 다르다.** 내가 기억하는 정의는 "제품이 기능을 수행할 때 **사용하는 자원의 양과 종류가 요구사항을 충족하는 정도**"이다(표준 원문 대조 필요). 즉 "얼마나 가득 찼는가"가 아니라 **요구를 충족하는 데 얼마나 자원을 썼는가**를 묻는다.
4. **심사위원이 방어 가능한 형태**는 "같은 성능을 내는 데 비싼 자원을 얼마나 덜 썼는가"이다. 절대 수치를 판단하지 못하는 심사위원도 상대적 절감을 이해할 수 있다.

## 3. 제안: QA3를 "SLO 충족 조건에서 소모하는 핵심 자원의 양"으로 통일

정의(안): **동일한 부하와 동일한 SLO 충족 조건에서, 해당 DP가 제어하는 희소 자원을 얼마나 적게 쓰는가**(낮을수록 좋음, Baseline 대비). 성능은 고정(SLO 충족)하므로 QA1·QA2와 섞이지 않는다.

| DP | DP가 제어하는 희소 자원 | QA3 metric 후보 | 비고 |
|---|---|---|---|
| DP1 | HBM | **HBM 사용량(GiB, 시간 평균)** — DP1 기존 정의(v6)와 같음 | 비싼 메모리를 얼마나 쓰는가. 성능이 나빠지는 정책이 유리해지는 문제는 QA1·QA2 동반 조건으로 막음 |
| DP2 | GPU 노드(Prefill/Decode 자원) | **같은 부하·SLO를 처리하는 데 필요한 GPU 노드 수 또는 GPU-time per output token**, 보조로 노드 간 KV 이동 bytes | P/D 풀 사용률은 이 값을 줄이는 **수단**이다. 사용률 %는 진단으로 내림 |
| DP3 | HBM | **HBM KV footprint**(DP1과 같은 정의, 설계 문서가 명시) | DP1과 같은 지표라 직접 통합 가능 |
| DP4 | (제어 자원 없음) | 제외 또는 진단(서버 간 부하 균형) | 현 DP4 입장 유지. 조율 계층 자체의 자원은 무시 가능 |

장점은 DP1과 DP3가 같은 지표가 되고, DP2는 "풀을 잘 쓰는가"가 아니라 "같은 일에 노드가 몇 개 필요한가"로 목표와 맞춰진다는 것이다.

## 4. 대안과 한계

| 안 | 내용 | 한계 |
|---|---|---|
| A (제안) | 위의 "SLO 충족 조건의 자원 소모량" | DP마다 자원이 다름(HBM, GPU)이라 지표 이름은 같아도 숫자는 DP별. 임계값 도출 규칙만 통일 가능 |
| B | 사용률(%)을 유지하고 공통 문서 기준(65/85%)을 모든 DP에 적용 | 위 근거 1~2 때문에 목표와 어긋나고 QA1과 중복 |
| C | QA3를 별점에서 제외하고 진단으로 | 과제의 QA 목록에 Resource Utilization이 있어 완전히 빼기 어려움. DP4처럼 제외한 DP와 선정한 DP가 섞이는 현재 상태가 지속 |

## 5. 확인할 것

- 과제 QA 목록의 "Resource Utilization"을 평가 측에서 **사용률(%)** 로 기대하는지, 위처럼 **자원 효율**로 기대하는지(과제 출제 쪽 정의를 사용자가 알고 있는지).
- DP2에서 "연산 가능 메모리(ScHBM, CXL-PNM)가 처리한 연산 비중" 같은 하드웨어 활용 지표를 진단으로 둘지(과제 주제와 맞닿아 있음).
- 이 결정은 **통합 단계(전 DP 훑은 뒤)** 에서 확정한다.
