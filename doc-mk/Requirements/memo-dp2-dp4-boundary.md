# 메모: DP2와 DP4의 경계 (다른 세션에서 깊게 논의하고 결정)

> 작성: 2026-10-09. 상태: **미결, 논의 기록**. 결정은 사용자가 다른 세션에서 한다. 이 문서는 이번 세션에서 오간 내용과 Claude의 의견을 모두 남긴다. 현재 `DP2-requirements.md`와 `DP4-requirements.md`는 **지금 상태로 두고** 진행한다(사용자 결정).

## 1. 사용자가 정리한 두 문제의 성격

- **DP2**: prefill node인지 decode node인지와 무관하게 **Prefill, Decode를 어디서 할지**를 결정한다. 따라서 멀티 노드 환경이다(사용자).
- **DP4**: 이기종 메모리 기반 서버들의 멀티 노드 환경에서 request가 여럿 들어왔을 때 이기종 메모리를 aware해서 **P/D를 얼마나 잘 분배해서 보낼지**의 문제다(사용자).
- 과제 초점이 스케줄링이므로 DP1(데이터 이동), DP2(실행 위치), DP4(요청 분배)는 모두 결정 문제이며 이 초점은 범위·FR·제약에 반영한다(`project-scope.md`).

## 2. 현재 문서가 말하는 두 DP

| | DP2 | DP4 |

| 결정 내용 | Turn마다 `(n_p, n_d)`, `n = (노드, 노드 안 연산·메모리 자원)` | 요청을 어느 vLLM 인스턴스로, P/D 분리 여부와 Prefill 서버 |
| 입력 해상도 | (노드, Tier) 단위 KV 위치, Tier별 BW, 오프로드 능력, 링크 흐름 수 | 인스턴스가 밖으로 내보내는 KV 이벤트(`medium`), `/metrics` |

## 3. QA 관점의 차이 (Claude 분석)

- **종단 결과 QA**(Goodput, TTFT, TPOT)는 두 DP가 같은 지표를 본다. 같은 원인에서 나오는 결과라 각 DP의 기여를 분리하기 어렵다(통합 단계에서 "그 DP를 껐을 때의 차이"로 분리하는 방안).
- **후보를 실제로 가르는 QA**는 다르다.
  - DP2: 결정 신선도 대 결정 비용(Time behavior, Functional appropriateness), 후보 수 증가에 대한 planner 확장(Scalability).
  - DP4: 흡수 대 통제(Modifiability), 업스트림·계약 추종(Interoperability), 결정 경로 hop(Time behavior), 서버 수 증가에 대한 조율 계층 확장(Scalability), 상태 신선도, 가용성.
- 한 줄: DP2는 "결정을 얼마나 잘, 얼마나 빨리"를, DP4는 "그 결정을 가능하게 하는 플랫폼을 어떻게 만들고 진화시키는가"를 판별한다(현재 문서 기준).

## 4. 두 가지 연결 방식 (사용자 제시)

### 방식 ① DP2 = 노드 안, DP4 = 그 범위를 노드 간으로 확장
- DP2는 **한 노드 안에서** P/D를 어떤 자원이 담당할지를 선택한다.
- DP4는 같은 결정을 **노드 간으로 확장**한다.

### 방식 ② DP2 = 노드와 자원 모두 결정, DP4 = 그것을 가능하게 하는 플랫폼
- DP2가 `(노드, 자원)` 모두를 결정하고 DP4는 이를 실행하게 하는 플랫폼(구현 방식)이다. (Claude가 앞 세션에서 현재 문서 서술을 근거로 권장했던 방식)

## 5. 사용자의 판단과 Claude의 의견

- **사용자**: ②는 DP2와 DP4의 경계가 모호하고 **DP4가 설계 이슈가 아니라 구현 이슈**처럼 보인다. ①이 나을 것 같다. 다만 ①이면 **한 노드 안에서 P/D를 나눠 실행하는 설계를 탄탄히 해야 한다**.
- **Claude 의견 (수정)**: 앞 세션의 ② 권장은 현재 문서 서술(DP4 = 플랫폼, 후보 = OSS 대 자체 구현)을 그대로 따른 것이다. 사용자의 지적("DP4가 구현 이슈처럼 보인다")은 타당하다. ①은 다음 이유로 더 자연스럽다.
  1. **문서들의 2-level 구조와 맞는다.** DP4 문서가 이미 cluster level(인스턴스 선택)과 node level(인스턴스 내부 결정)을 구분하고 DP1은 node level, DP2는 "cluster 성분과 node 성분으로 나뉜다"고 적었다. ①은 이 구분을 DP로 옮긴 것이다(DP1·DP2·DP3 = node level, DP4 = cluster level 확장).
  2. **DP4가 설계 질문이 된다.** "같은 결정을 노드 간으로 확장할 때 무엇이 달라지는가(정보 해상도, 전송 비용, 흐름 제어)"가 DP4의 설계 질문이 되고 OSS 대 자체 구현은 그 아래의 구현 선택으로 내려간다.
  3. **DP1·DP2·DP3와 같은 형태**가 된다("결정 변수 하나를 후보로 가름", DP3 문서 B §4).
- **①의 위험(주의)**
  1. **현재 DP2 설계와 평가는 멀티 노드 P/D**(P 노드와 D 노드, 노드 간 링크 모델)다. ①로 가면 DP2의 범위를 노드 안으로 줄이거나, DP2가 "노드 안 자원 선택"과 "노드 선택" 중 무엇을 하는지 다시 정해야 한다. 사용자는 이번 세션에서 "DP2는 당연히 멀티 노드"라고 했으므로 **①과 이 발언이 충돌하는지 확인이 필요**하다.
  2. **노드 안 P/D 결정 공간이 좁을 수 있다.** 평가 시스템 profile 기준으로 Prefill은 연산이 무거워 GPU 외 자원(ScHBM 약 198 TFLOPS, CXL-PNM 약 3.3 TFLOPS)이 전부를 맡기 어렵고, 이 자원들이 지원하는 연산은 attention 계열(QK_GEMM, SOFTMAX, AV_GEMM, CAUSAL_MASK)뿐이다. 따라서 노드 안에서 실질적으로 선택할 수 있는 것은 **Decode attention의 위치(Tier)와 Prefill·Decode 간섭 관리** 쪽에 치우칠 수 있다. 이 해석은 평가 문서의 profile 값에서 읽은 것이며 설계 의도와 맞는지 확인이 필요하다.
  3. 노드 안 P/D 분리의 의미(같은 GPU 집합에서 시간 분할인가, 서로 다른 자원인가)를 먼저 정의해야 한다.

## 6. 다른 세션에서 결정할 질문

1. DP2의 `(n_p, n_d)`에서 **"어느 노드인가"** 는 누구의 결정인가(DP2 / DP4 / 둘 다)?
2. 방식 ① 또는 ②, 또는 제3의 구성(예: DP2는 결정 함수, DP4는 노드 간 확장 + 플랫폼)?
3. 방식 ①이면 DP2를 **노드 안으로 재범위**할 때 기존 DP2 설계(멀티 노드 Cost Model, 링크 모델)와 평가를 어떻게 처리하는가?
4. DP4의 설계 질문을 "OSS 확장 대 자체 구현"으로 둘지, "노드 간 확장 시 무엇이 달라지는가"로 바꿀지.
5. DP4의 P3, P4, P5와 DP2의 Cost Model 중 어느 쪽이 소유하는가(중복 제거).
6. 위 결정 후 QA 구분(§3)을 확정하고 두 DP의 요구사항 문서를 재작성.

## 7. 참고 (이번 세션에서 읽지 않은 것)
