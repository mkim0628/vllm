## 2. Use Case

### UC-1 Tool 호출 대기 중인 KV의 HBM 점유 해소와 재방문 (시나리오: SC-1, S-A) — 제안
> 가정 확정(사용자: 가정대로): idle KV는 요청 종료 후 prefix cache로 남은 블록, 주된 문제는 처리량 감소와 재개 TTFT 증가 둘 다, 대기 시간은 수백 ms~수십 초 예측 불가, prefetch는 Should, 다른 서버로의 재개는 UC-7로 분리.
| 항목 | 내용 |
|---|---|
| Actor | 주: agent 요청 클라이언트(런타임 사용자). 보조: 외부 tool 실행기(시스템 밖) |
| 목표 | tool 호출로 쉬는 세션의 KV가 HBM을 차지해 다른 요청의 성능이 떨어지는 일을 막고, 세션이 재개될 때 불필요한 재계산 없이 빠르게 이어 간다 |
| 사전조건 | 여러 agent 세션이 동시 진행. 세션마다 multi-turn 중. 이기종 메모리(HBM + DRAM/CXL/SSD 등) 사용 가능 `[가정]` |
| 트리거 | 어떤 세션이 tool 호출을 위해 생성을 멈춘다 (idle 구간 시작) |
| 주 흐름 | 1. [S] 시스템이 해당 세션의 KV가 곧 쓰이지 않음을 판단한다. 2. [S] 그 KV를 HBM에서 더 큰/느린 메모리로 옮긴다(HBM 비운다). 3. 비워진 HBM으로 다른 세션의 요청이 처리된다. 4. 클라이언트가 tool 결과와 함께 같은 세션의 다음 요청을 보낸다. 5. [S] 시스템이 옮겨 둔 KV를 찾아 재사용한다(재계산 최소화). 6. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 2a. 옮길 메모리 공간이 부족하면 가장 오래 쓰이지 않은 KV부터 정리한다(재계산으로 대체). 4a. tool 호출이 예상보다 빨리 끝나 이동이 끝나기 전에 재개 요청이 오면, 이동 완료를 기다릴지/재계산할지 중 빠른 쪽을 택한다. 4b. 세션이 재개되지 않으면(이탈) KV를 정리한다 |
| 사후조건 | 재개된 요청의 출력은 이동 없이 처리했을 때와 동일(정확도 불변, GC-7). 다른 세션의 처리량이 유지된다 |
| 관련 데이터 종류 | KV (agent multi-turn) |
| 관련 DP | DP1 중심(배치/이동), 멀티 노드면 DP0, DP4 |
| 파생 FR | FR-1~FR-6 |

### UC-2 HBM 용량을 넘는 Long-context 요청 처리 (SC-2) — 제안
| 항목 | 내용 |
|---|---|
| Actor | long-context 요청 클라이언트(문서 전체 요약, 대형 코드베이스 질의 등) |
| 목표 | KV가 HBM 용량을 넘어도 요청이 실패하지 않고, 지연 증가를 최소화하며 응답받는다 |
| 사전조건 | 요청 context 길이 × 모델 KV 크기 > 가용 HBM. HBM 외 메모리(DRAM/CXL/SSD/HBF) 사용 가능 `[가정]` |
| 트리거 | 매우 긴 prompt 요청이 도착한다 |
| 주 흐름 | 1. [S] 시스템이 prefill 중 생성되는 KV를 HBM과 다른 메모리에 나눠 보관한다. 2. [S] decode 중 매 토큰마다 필요한 KV를 계층에서 읽어 attention을 수행한다. 3. [S] 접근 빈도가 높은 KV(최근 토큰, sink 등)는 빠른 메모리에 둔다. 4. 클라이언트가 스트리밍 응답을 받는다 |
| 대안/예외 흐름 | 2a. 느린 tier 접근이 병목이면 선택적 Drop(DP3)을 쓸 수 있으나 정확도와 교환된다(GC-7 DP3 예외). 1a. 전체 메모리로도 부족하면 요청을 거절하고 이유를 알린다 |
| 사후조건 | Drop을 쓰지 않으면 출력이 HBM만 쓸 때와 동일. Drop을 쓰면 허용 정확도 저하 한도 이내 |
| 관련 데이터 종류 | KV (long-context) |
| 관련 DP | DP1, DP3 (DP2 연계 가능) |
| 파생 FR | FR-7~FR-9 |

### UC-3 RAG 공유 문서 prefix의 반복 재사용 (SC-3) — 제안
| 항목 | 내용 |
|---|---|
| Actor | RAG 질의 클라이언트(다수 사용자) |
| 목표 | 같은 문서를 참조하는 질의가 문서 KV를 매번 다시 계산하지 않고, 빠르게 응답받는다 |
| 사전조건 | 자주 조회되는 문서(hot)와 드물게 조회되는 문서(cold)가 섞여 있다. 문서 KV가 여러 메모리 tier에 분산 `[가정]` |
| 트리거 | 사용자가 이미 처리된 문서를 포함한 질의를 보낸다 |
| 주 흐름 | 1. [S] 시스템이 요청의 문서 prefix가 이미 KV로 존재하는지 찾는다(어느 tier에 있든). 2. [S] 있으면 재사용하고 질문 부분만 prefill한다. 3. [S] 조회 빈도에 따라 hot 문서 KV는 빠른 tier로, cold 문서 KV는 느린 tier로 옮긴다. 4. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 1a. 문서가 갱신되면 이전 문서 KV를 더 이상 쓰지 않고 새로 계산한다. 2a. 가져오는 시간이 재계산보다 길면 재계산한다 |
| 사후조건 | 출력이 재사용 없이 계산했을 때와 동일 |
| 관련 데이터 종류 | KV (RAG prefix) |
| 관련 DP | DP1, DP0 (다중 서버 시), DP4 |
| 파생 FR | FR-10~FR-12 |

### UC-4 LoRA 멀티 테넌트 adapter 전환 (SC-4) — 제안
| 항목 | 내용 |
|---|---|
| Actor | 테넌트별 요청 클라이언트(서로 다른 LoRA adapter를 지정) |
| 목표 | adapter 수가 HBM 용량을 넘어도 요청마다 지정한 adapter로 지연 증가 없이 응답받는다 |
| 사전조건 | adapter 수 × 크기 > HBM에 상주 가능한 양. 일부 adapter는 DRAM/CXL/SSD에 있다 `[가정]`. 테넌트 격리·보안은 범위 밖(GC-6)이며 서빙 성능만 다룬다 |
| 트리거 | 요청이 현재 HBM에 없는 adapter를 지정한다 |
| 주 흐름 | 1. [S] 시스템이 요청의 adapter 위치를 확인한다. 2. [S] HBM에 없으면 빠른 경로로 가져오고, 자주 쓰이는 adapter는 HBM에 유지한다. 3. [S] 가져오는 동안 다른 요청의 처리를 막지 않는다. 4. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 2a. HBM이 가득 차면 가장 덜 쓰이는 adapter를 내린다. 3a. 같은 adapter를 쓰는 요청은 묶어 처리한다 |
| 사후조건 | 지정한 adapter가 정확히 적용된 출력 |
| 관련 데이터 종류 | LoRA adapter weight |
| 관련 DP | DP1, DP0 (adapter 보유 서버 선택 시) |
| 파생 FR | FR-13~FR-15 |

| 대안/예외 흐름 | 2a. 입력 분포가 바뀌어 hot expert가 바뀌면 배치를 다시 조정한다 |
| 사후조건 | 출력이 모든 expert를 HBM에 둘 때와 동일 |
| 관련 데이터 종류 | MoE expert weight |
| 관련 DP | DP1, DP2 |
| 파생 FR | FR-16~FR-17 |

### UC-6 연산 가능 메모리(PIM/PNM) offload (SC-6) — 제안
| 항목 | 내용 |
|---|---|
| Actor | 일반 요청 클라이언트(체감은 지연·처리량 향상). 이 UC는 서빙 시스템 관점의 시나리오다 |
| 목표 | 메모리 대역폭이 병목인 연산을 데이터가 있는 메모리 쪽에서 실행해 GPU와 이동 부담을 줄인다 |
| 사전조건 | 연산 가능 메모리가 있고 지원 연산 목록과 성능 profile이 주어진다(GC-5). kernel/compiler는 주어진 것으로 본다 |
| 트리거 | 대역폭 병목 연산(예: 긴 KV에 대한 decode attention, 느린 tier의 expert 연산)이 필요하다 |
| 주 흐름 | 1. [S] 시스템이 연산 위치(GPU vs 연산 가능 메모리)를 비용 기반으로 정한다. 2. [S] 메모리 쪽 연산을 지시하고 결과만 GPU로 받는다. 3. [S] 이기는 경우에만 사용한다. 4. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 1a. 지원하지 않는 연산이면 GPU 경로로 수행한다. 3a. offload 이득이 없으면(데이터가 작거나 연산이 무거우면) GPU 경로로 수행한다 |
| 사후조건 | 출력이 GPU 단독 실행과 동일(수치 허용 오차 내) `[가정]` |
| 관련 데이터 종류 | KV, MoE expert |
| 관련 DP | DP2 (실행 계획), DP1 |
| 파생 FR | FR-18~FR-20 |

### UC-7 노드 간 KV 이동과 서버 선택 (SC-7) — 제안
| 항목 | 내용 |
|---|---|
| Actor | 요청 클라이언트(세션 재개 요청이 다른 서버로 가거나 공유 문서를 다른 서버가 이미 처리한 경우) |
| 목표 | 다른 서버가 만든 KV를 재계산보다 빠르면 가져와 쓰고, 그렇지 않으면 재계산한다 |
| 사전조건 | GPU 서버 2대 이상, 서버 간 전송 경로 존재(RDMA 유무는 미확인) `[가정]` |
| 트리거 | 요청이 도착했는데 필요한 KV가 다른 서버에 있다 |
| 주 흐름 | 1. [S] 시스템이 KV가 어느 서버·어느 메모리에 있는지 안다. 2. [S] 요청을 KV 보유 서버로 보낼지, KV를 가져올지, 재계산할지를 비용 기준으로 정한다. 3. [S] 선택에 따라 KV를 전송한다. 4. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 3a. 전송이 실패하거나 시간 초과하면 재계산으로 대체한다 |
| 사후조건 | 출력이 로컬 계산 시와 동일 |
| 관련 데이터 종류 | KV |
| 관련 DP | DP0, DP4 |
| 파생 FR | FR-21~FR-23 |

### UC-8 Prefill/Decode 분리 실행 (SC-8) — 제안
| 항목 | 내용 |
|---|---|
| Actor | 요청 클라이언트(긴 입력 + 긴 출력 요청) |
| 목표 | 입력 처리와 생성의 자원 요구가 다름을 활용해 TTFT와 TPOT를 함께 지킨다 |
| 사전조건 | prefill과 decode를 각각 다른 서버/자원에 배치할 수 있다 `[가정]` |
| 트리거 | 요청이 도착한다 |
| 주 흐름 | 1. [S] 시스템이 요청 크기와 현재 자원 상태로 분리 실행 여부를 정한다. 2. [S] prefill을 맡은 곳에서 KV를 만들어 decode를 맡은 곳으로 보낸다. 3. [S] decode가 KV를 받아 생성한다. 4. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 1a. 분리 이득이 전송 비용보다 작으면 한 곳에서 실행한다 |
| 사후조건 | 출력이 분리하지 않은 실행과 동일 |
| 관련 데이터 종류 | KV |
| 관련 DP | DP0, DP2, DP4 |
| 파생 FR | FR-24~FR-25 |

### UC-9 혼합 부하에서의 자원 경쟁 (SC-9) — 제안
| 항목 | 내용 |
|---|---|
| Actor | 다수의 요청 클라이언트(agent, RAG, long-context, LoRA, MoE 요청이 동시에 들어옴) |
| 목표 | 한 종류의 요청이 다른 요청의 지연과 처리량을 크게 해치지 않는다 |
| 사전조건 | UC-1~UC-8의 요청이 같은 시스템에서 동시에 처리된다. 이동·복원 트래픽도 같은 링크를 쓴다 |
| 트리거 | 요청률이 증가해 메모리와 링크 대역폭이 경쟁 상태가 된다 |
| 주 흐름 | 1. [S] 시스템이 요청별 요구와 메모리/링크 상태를 함께 본다. 2. [S] 이동·복원·offload 작업이 서빙 트래픽을 잠식하지 않게 조절한다. 3. [S] 과부하이면 대기·우선순위·거절로 SLO를 지킨다. 4. 클라이언트가 응답을 받는다 |
| 대안/예외 흐름 | 3a. 모든 요청을 SLO 안에서 처리할 수 없으면 일부를 대기시키거나 거절한다 |
| 사후조건 | 어느 한 요청 유형도 SLO를 크게 이탈하지 않음 |
| 관련 데이터 종류 | KV, LoRA, MoE |
| 관련 DP | 전체 (DP0 흐름 제어, DP1, DP2) |
| 파생 FR | FR-26~FR-28 |

| FR-3 | 시스템은 같은 세션의 후속 요청이 오면 옮겨 둔 KV를 찾아 재사용하고, 이미 있는 부분을 재계산하지 않아야 한다 | Must | UC-1 | 재계산 토큰 수, TTFT |

| FR-5 | 시스템은 이동 대상 메모리가 부족하면 쓰이지 않을 가능성이 높은 KV부터 정리하고 필요 시 재계산으로 대체해야 한다 | Must | 도출 | 정리 후 재개 정확성·지연 |
| FR-6 | 시스템은 KV를 이동하거나 복원해도 모델 출력을 바꾸지 않아야 한다(bit-exact) | Must | GC-7 | 이동 유무 출력 비교 |
| FR-7 | 시스템은 KV가 HBM 용량을 넘는 요청을 HBM 외 메모리를 함께 써서 실패 없이 처리해야 한다 | Must | UC-2 | 지원 최대 context 길이 |

| FR-12 | 시스템은 문서가 갱신되면 이전 KV를 재사용하지 않아야 한다 | Must | 도출 | stale KV 재사용 건수 0 |
| FR-13 | 시스템은 HBM 용량을 넘는 수의 LoRA adapter를 요청 지정대로 서빙해야 한다 | Must | UC-4 | 동시 서빙 adapter 수 |
