# DP1 프로토타입 테스트 가이드

이 문서는 `doc-mk/prototype`의 테스트를 **왜 만들었고 어떻게 읽어야 하는지**를 설명한다.

핵심 원칙 하나만 기억하면 된다.

> **테스트는 코드가 아니라 DP 문서를 검증한다.**
> 테스트가 깨지면 코드가 틀렸거나 문서가 틀린 것이다. 어느 쪽인지 판단해야 하고,
> 문서 쪽이면 문서를 고친다. **별점을 맞추려고 테스트를 고치지 않는다.**

---

## 1. 이 프로토타입이 모델링한 것

DP1의 두 후보는 "배치 정책의 인덱스 축을 어디에 두는가"로 갈린다. 그 차이가 코드에
그대로 드러나도록 두 가지를 **타입으로 강제**했다.

### 1.1 관측 가능성의 분리

```python
@dataclass(frozen=True)
class ObservableRequest:      # 할당 시점에 실제로 알 수 있는 것
    prompt_len, max_tokens, endpoint, model, prefix_hit_blocks, attention

@dataclass(frozen=True)
class Oracle:                 # 시뮬레이터만 아는 미래
    actual_output_len, prefix_group
```

배치기는 `Oracle`에 접근할 수 없다. 채점만 본다. 그래서 "hotness는 관측 불가능하다"가
주석이 아니라 **구조**다. `max_tokens`(상한)만 보고 `actual_output_len`(실제)을
맞히지 못하는 상황이 자동으로 재현된다.

### 1.2 익명성의 강제

`TripwireView`는 속성을 읽는 순간 예외를 던진다.

```python
check_anonymity(TierIndexedPlacer(table))    # True  — 요청을 전혀 읽지 않았다
check_anonymity(ObjectIndexedPlacer(table))  # False — 읽어야만 등급을 만든다
```

문서의 "요청 식별자가 경로 어디에도 등장하지 않는다"가 실행으로 증명된다.

### 1.3 스텝 내 staleness

tier 상태는 **스케줄 스텝 경계에서만 갱신**된다(`TierTable.begin_step()`). 한 스텝 안의
결정들은 모두 스텝 시작 시점의 상태를 본다. 이 staleness를 보정하는 유일한 수단이
예약 카운터(`reserve_within_step`)다. herding이 여기서 자연히 발생한다.

## 2. 실행

### 2.1 의존성 없는 실행 (권장)

표준 라이브러리만 쓰므로 아무 환경에서나 돌아간다.

```bash
cd doc-mk/prototype
python3 -m unittest discover -s . -v
python3 -m dp1.run_experiment
python3 -m dp1.run_experiment heterogeneous burst   # 시나리오 선택
```

### 2.2 pytest로 실행 (저장소 규약)

`AGENTS.md`는 시스템 `python3`/`pip` 대신 `uv`와 `.venv`를 쓰도록 규정한다.

```bash
uv venv --python 3.12
uv pip install pytest
.venv/bin/python -m pytest doc-mk/prototype/tests -v
```

테스트는 `unittest.TestCase`로 작성되어 pytest에서도 그대로 수집된다.

## 3. 테스트 지도 — 무엇이 무엇을 검증하는가

| 테스트 클래스 | 검증하는 문서 절 | 핵심 단언 |
|---|---|---|
| `TestExclusivity` | 3.3 양립 불가 논증 | 불변식 충돌 · 익명성 · 상위호환 반박 |
| `TestQA1PlacementQuality` | QA1 배치 품질 | 구분 능력, 균질 워크로드에서의 이득 소멸 |
| `TestQA2InformationCost` | QA2 결정 정보 비용 | 메시지 수, N 의존성, 관측 가능 비율 |
| `TestQA3Adaptivity` | QA3 적응성 | herding, 예약 카운터, 오분류 고착, 공유 블록 |
| `TestQA4Reproducibility` | QA4 재현성 | 도착 순서 의존성, 결정 근거 항목 |
| `TestAppendixD` | 부록 D | 읽기량 계산, 힌트 API 규칙 |
| `TestSelectedStructure` | 11장 최종 선택 | 보강의 효과, **혼합이 아님의 증명** |

### 특히 중요한 세 가지

**① 불변식 충돌** (`test_invariant_conflict_gives_opposite_decisions`)

상위 tier를 가득 채운 뒤 더 높은 등급의 객체를 보낸다.

```
C1 → CUSTOM_HBM,  evictions = 0     (자원 제약이 이긴다)
C2 → HBM,         evictions > 0     (객체 계약이 이긴다)
```

같은 입력에 대해 결정이 **정반대**임을 확인한다. 두 구조가 합쳐질 수 없다는 논증의
실행 가능한 형태다.

**② 상위호환 반박** (`test_c2_can_only_mimic_c1_by_paying_its_own_cost`)

C2에 C1의 정책을 그대로 쓰게 하면(`mimic_c1=True`) 배치 결과는 **완전히 동일**해진다.
그런데 비용은 남는다.

```
C1     : 5.00 msg/decision,   0 object reads
C2 흉내 : 7.00 msg/decision, 270 object reads   ← 같은 결과, 더 비쌈
```

"기능이 포개져 보여도 비용 구조가 다르면 상위호환이 아니다"가 숫자로 나온다.

**③ 혼합이 아님의 증명** (`test_reinforced_c1_is_not_a_hybrid`)

11장에서 선택한 "C1 + 컨텍스트 길이 보강"이 진짜 혼합인지 판정한다. 보강을 켠 채로
불변식 충돌 시나리오를 돌려서, 여전히 **자원 제약이 이기는지**(하위 tier로 흐르고
점유자를 밀어내지 않는지) 확인한다. 통과하면 인덱스 축이 바뀌지 않았다는 뜻이고,
3.3의 배타성 논증이 그대로 유효하다.

## 4. 실험 지표 읽는 법

`python3 -m dp1.run_experiment` 가 내는 열의 의미다.

| 열 | 의미 | 문서 대응 |
|---|---|---|
| `msg/decision` | 배치 결정 1건의 메시지 수 | 4.3 시퀀스 (C1 5개 / C2 7개) |
| `object_reads` | 요청을 읽은 횟수 | 익명성 — C1은 항상 0 |
| `branches` | 데이터 의존 분기 수 | QA2 |
| `grades` | 실제로 사용된 등급 수 | QA1 구분 능력 |
| `herding_1st` | 첫 스텝에서 한 tier가 가져간 비율 (1.0 = 전부 몰림) | QA3 |
| `overcommit` | tier 용량을 넘겨 커밋한 횟수 | **C1의 자기 불변식 위반** |
| `separation` | 대역폭 요구 상위 20%의 평균 tier 대역폭 ÷ 하위 80% | QA1. **1.0 = 구분 못 함, <1.0 = 역전** |
| `bw_match` | 요구 가중 대역폭 달성률 (1.0이 최대) | 배치 품질 총량 |
| `shared_viol` | 공유 블록에서 계약이 깨진 횟수 | QA3 예측 대상 오류 |

### 실측 결과 (현재 코드 기준)

| 시나리오 | 지표 | C1 | C1+보강 | C1 예약없음 | C2 |
|---|---|---:|---:|---:|---:|
| 전 시나리오 | msg/decision | 5.00 | 5.00 | 5.00 | 7.00~7.55 |
| 전 시나리오 | object_reads | 0 | N | 0 | N |
| heterogeneous | separation | 2.06 | **2.47** | 1.57 | **25.40** |
| heterogeneous | bw_match | 0.715 | 0.707 | 0.729 | 0.734 |
| homogeneous | separation | 1.00 | 1.00 | 1.00 | 1.00 |
| homogeneous | bw_match | **1.000** | 1.000 | 1.000 | **0.020** (상향 허용 시 1.000) |
| burst | herding_1st | 0.42 | 0.43 | **1.00** | 1.00 |
| burst | overcommit | 0 | 0 | **72** | 0 |
| misclassification | separation | 1.00 | 1.00 | 1.00 | **0.43** |
| shared_prefix | shared_viol | 0 | 0 | 0 | **99** |

## 5. 테스트가 깨졌을 때의 판단 절차

1. **모델링 오류인가?** 시뮬레이터가 현실과 다르게 굴었는지 먼저 본다.
   예: 하드 제약은 stale view로 보면서 점수는 실시간 값으로 보면 모델이 현실보다
   똑똑해진다. 관측 창은 하나여야 한다.
2. **테스트 자체의 오류인가?** 의도한 상황이 실제로 만들어졌는지 확인한다.
   예: 배치기로 tier를 채우려 하면 예약 때문에 블록이 분산되어 포화되지 않는다.
3. **문서가 틀렸는가?** 위 둘이 아니면 문서를 고친다. 아래 6절이 그 사례다.

## 6. 실측이 문서와 어긋난 지점 — 문서로 되돌려야 할 발견

**이 절이 이 프로토타입의 가장 큰 산출물이다.** 세 건 모두 DP1 문서의 별점 근거에
영향을 준다.

### 발견 ① C2의 오분류는 이득을 없애는 정도가 아니라 배치를 역전시킨다

`misclassification` 시나리오에서 C2의 `separation = 0.43`이 나온다. 1.0 미만은
**실제로 오래 사는 요청이 더 느린 tier를 받았다**는 뜻이다. 같은 시나리오에서 C1은
1.00(구분 못 함, 그러나 역전도 없음)이다.

> 문서는 QA3에서 "오분류가 고착된다"고만 썼다. 실측은 그보다 강하다 —
> **오분류 구간에서 C2는 C1보다 나쁘다.** QA1의 ★★★는 "분류가 맞았을 때"라는
> 조건부임을 별점 근거에 명시해야 한다.

### 발견 ② C2에서 tier 상태는 **아래로만** 작용한다 — 그리고 위로 열면 구분이 무너진다

> 초판에서 이 항목을 "C2의 계약은 capacity-blind다"라고 썼는데 **과한 서술이었다.**
> C2도 tier 상태를 본다. 계약이 지시한 tier가 차면 하위로 내려간다.
> 정확한 사실은 **상태가 아래로만 작용한다**는 것이다 — 위가 비어 있어도 올라가지 않는다.

`homogeneous`에서 순수 C2의 `bw_match = 0.020`, C1은 `1.000`이다. 한 등급이 워크로드를
지배하면 계약이 전부 같은 tier를 지시하고, 상위 tier가 텅 비어 있어도 쓰지 않는다.

**그럼 "적당히" 위도 보게 하면 되지 않나?** 된다. 그래서 계약을 **하한**으로만 쓰고
위쪽 여유를 쓰는 변형(`upgrade_if_free`)을 구현해 측정했다.

| heterogeneous | bw_match (총량 활용) | separation (구분 능력) |
|---|---:|---:|
| C1 | 0.715 | 2.06 |
| C2 순수 — 아래로만 | 0.734 | **25.40** |
| C2 상향 여유 25% | 0.787 | 2.23 |
| C2 상향 여유 50% | 0.808 | 1.52 |
| C2 상향 무제한 | **0.823** | 1.24 |

`homogeneous`의 손해는 실제로 사라진다 (bw_match 0.020 → 0.938~1.000).
**그러나 공짜가 아니다.** 상향을 열수록 구분 능력이 무너지고, 끝까지 열면
**C1보다도 구분을 못 한다**(1.24 < 2.06).

이유는 명확하다. "빈 자리가 있으면 위로"는 **먼저 온 요청이 상위 tier를 독식**하게
만든다. 등급이 낮아도 초반에 오면 HBM에 들어가고, 정작 높은 등급이 나중에 오면
자리가 없다. **도착 순서가 등급을 이긴다** — C1의 실패 모드를 그대로 물려받는 것이다.

물려받는 것이 하나 더 있다. 상향 무제한 변형은 `heterogeneous`에서 `overcommit = 6`을
낸다. 같은 스텝의 여러 결정이 모두 스텝 시작 시점의 여유를 보고 같은 상위 tier로
올라가기 때문이다. **예약 없는 C1이 내던 바로 그 위반이다**(발견 ③).

> 그래서 정정된 결론은 이렇다. `upgrade_headroom`은 C2 내부의 **또 하나의 트레이드오프
> 손잡이**이며 `총량 활용 ↔ 구분 능력`을 조절한다. 부록 D.3의 2차 트레이드오프 목록에
> 세 번째 항목으로 추가해야 한다.
>
> 그리고 이 손잡이를 제대로 쓰려면 **상위 tier의 일부를 고등급 전용으로 유보**해야 하는데,
> 그것은 C1이 herding을 막으려고 쓰는 예약 카운터와 **같은 메커니즘**이다.
> 두 후보 모두 "유보"라는 공통 요소를 필요로 한다.
>
> **QA1 별점은 바꾸지 않는다.** C2의 ★★★는 유효하되 "상향을 닫았을 때"의 값임을
> 별점 근거에 명시하면 된다.

### 발견 ③ 예약 카운터는 완화책이 아니라 정합성 요건이다

`burst`에서 예약 없는 C1은 `overcommit = 72`를 낸다. herding이 성능 문제인 줄
알았는데, 실제로는 **C1이 자기 불변식(자원 제약을 절대 위반하지 않는다)을 스스로
어긴다.**

> 문서는 예약 카운터를 "구현 부담이지 구조 변경은 아니다"라고 썼다. 맞는 말이지만
> 약하다. **예약 카운터가 없으면 C1의 불변식이 성립하지 않으므로, 그것은 선택적
> 완화책이 아니라 C1 정의의 일부다.** QA3 서술을 그렇게 고쳐야 한다.

## 7. 이 프로토타입이 모델링하지 않은 것

정직하게 적어둔다. 아래는 결론을 바꿀 수 있는 요소이므로 실측으로 확장할 때 우선순위다.

- **실제 지연·대역폭**: tier의 `bandwidth_gbps`는 상대 가중치일 뿐 커널 시간이 아니다.
  `bw_match`는 "요구와 배치가 얼마나 맞는가"이지 처리량 예측이 아니다.
- **재배치(migration)**: 최초 배치만 다룬다. DP3의 주제다.
- **eviction 알고리즘**: C2의 축출은 등급 비교로 단순화했다. LRU/ARC를 쓰지 않는다.
- **prefix 공유의 부분 히트**: 그룹 단위로만 모델링한다. 블록 해시 수준이 아니다.
- **분산(TP/PP/DP)**: 워커 간 상태 동기화 비용이 빠져 있다. C2의 메타데이터
  일관성 비용은 실제로는 더 클 것이다.
- **출력 길이 예측기**: 휴리스틱 하나만 넣었다. 11장 PoC의 "예측 정확도 측정"은
  프로덕션 로그가 있어야 하므로 여기서 대체할 수 없다.
