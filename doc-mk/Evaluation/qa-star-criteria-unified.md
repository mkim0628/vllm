# 1. 원칙

1. **같은 QA는 DP와 무관하게 같은 metric·집계·경계를 쓴다.** 달라지는 것은 후보와 시나리오(Common Benchmark + DP 전용 benchmark, SKILL H3)이지 기준이 아니다.
2. **여러 시나리오·시스템은 쌍별 값의 기하평균으로 합친다**(공통 룰 §10). Baseline은 DP마다 다르다(대상이 다르다). 별은 항상 "후보 값 ÷ 같은 DP의 Baseline" 또는 절대 SLO로 매겨 DP 간에 의미가 같다.
3. **각 경계에 근거를 단다**: 측정(잡음 폭), 환산(자원·시간), 문헌/표준, 정책 선택 중 어느 것인지 밝힌다. 정책 선택은 정책 선택이라고 쓴다.
4. **별 합계가 높은 후보를 선택하고, 합계가 같을 때만 QA 우선순위(DP별)로 가른다**(SKILL H13). 합계 규칙은 모든 DP에 같다.
5. **별은 근거 수준과 분리해 표시한다**: 시뮬레이션 [B+C], Baseline 실측+시뮬레이션 [A+C], 변경 시나리오 환산 [C].

# 3. QA별 기준과 근거

## 3.1 QA1 — 처리량

**지표**: R = (후보의 Max SLO Goodput) ÷ (같은 DP Baseline의 Max SLO Goodput). Max SLO Goodput = SLO를 위반한 요청의 output token을 뺀 tok/s의 load sweep 최대값(공통 룰 §4). 시나리오 쌍별 R의 기하평균.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | R ≥ **2.0** | 같은 수요를 **절반의 서버**로 처리한다 = 노드 수·전력·비용 절반이라는 가장 단순한 자원 환산 단위. 새 메모리 HW와 스케줄링 복잡도를 정당화하려면 "서버 한 대로 두 대분"은 되어야 한다는 판단. 문헌에서도 서빙 시스템 수준 개선이 2배를 넘는 사례를 주요 성과로 보고한다(예: vLLM PagedAttention은 기존 시스템 대비 2~4배, [SOSP 2023](https://arxiv.org/abs/2309.06180)) | 환산 [C] + 문헌 [B], 정책 선택 |
| ★★ | 0.97 ≤ R < 2.0 | 하한 0.97 = Baseline끼리 seed 묶음을 바꿔 비교한 20회 집계 범위 0.968~1.033의 아래 끝(DP1 `sim/star_basis.py`). 이 안은 "잡음 이상 개선 ~ 2배 미만"이다 | 측정 [B+C] |
| ★ | R < 0.97 | 잡음 밖의 열세: Baseline보다 느리다 | 측정 [B+C] |

- **v1(1.30)을 버린 이유**: 1.30은 "자원 23% 절감"이라는 정책 선택이었고, DP1 결과(C1 ×1.298, C2 ×1.423)를 본 뒤 그 사이에 놓은 값이라 "왜 1.30인가"에 독립 근거로 답하지 못했다(v1의 정직한 주의 (a)). 2.0은 결과를 보기 전부터 설명 가능한 단위(서버 절반)에 둔다.
- **결과 값은 바꾸지 않는다**: "경계를 올린 만큼 평가 수치도 올리자"는 요청은 따르지 않았다. 처리량 ×1.30은 시뮬레이션이 낸 값이고, 경계에 맞춰 올리면 측정 불가능한 값을 만드는 것이다. 대신 **경계를 올리면 별이 내려가는 결과**를 그대로 보고한다: DP1 C2(×1.42), DP2 C1·C2(×1.66)가 ★★★ → ★★이고 QA1 ★★★ 후보는 없다.
- **DP1 보완 버전(C1+Affinity)이 ★★인 이유**: 처리량 ×1.2976(436 vs 336 tok/s)이라 "×1.3"으로 쓰지만 v1 경계 1.30에서도 0.2% 아래였다. 반올림 표기와 판정 값이 다른 것이 혼란의 원인이므로 문서와 PPT에는 소수 셋째 자리까지 쓴다. v2(2.0)에서도 ★★.
- **이전 기준**: DP1 0.97/1.30, DP2 같음, DP4 공통 룰 0.90/1.10.
- **정직한 주의**: (a) 2.0으로 올리면 QA1은 이번 DP 후보들을 가르지 못한다(★★★ 없음, 상위 구간의 차이 ×1.30 대 ×1.66이 별에 안 보임). 차이는 R 값 자체로 병기한다. (b) 하한 0.97은 DP1 시뮬레이터 잡음에서 나왔다. DP4는 Baseline이 실측이라 같은 잡음 폭이 맞는지 재측정이 필요하다.

## 3.2 QA2 — 지연

**지표**: TTFT P99와 TPOT P99(시나리오 쌍별 값의 기하평균). 두 값으로 **A(절대 수준)**와 **R(Baseline 대비 개선)**을 매기고 **평균(반올림 올림)**을 별로 한다.

- **A — 절대 SLO 등급**(두 지표 중 낮은 등급): ★★★ TTFT P99 ≤ 2 s 그리고 TPOT P99 ≤ 50 ms. ★★ ≤ 4 s 그리고 ≤ 100 ms. 그 밖 ★. 근거: 공통 기본 SLO. TTFT 2 s는 8K prefill 이론 시간 약 0.32 s(H100×8, MFU 0.45)의 약 6배라 큐잉 여유를 포함한 값이고 MLPerf Llama-2-70B 표준 시나리오(TTFT 2 s, TPOT 200 ms 계열)와 같은 자릿수다. ★★은 기본 SLO의 2배.
- **R — 개선 등급**: r = √[(Baseline TTFT P99 ÷ 후보 TTFT P99) × (Baseline TPOT P99 ÷ 후보 TPOT P99)] (>1이면 좋아짐). ★★★ r ≥ **1.20**, ★★ 0.90 ≤ r < 1.20, ★ r < 0.90.

| 별 = 올림((A+R)/2) | R ★★★ (r ≥ 1.20) | R ★★ (0.90~1.20) | R ★ (r < 0.90) |
|---|---|---|---|
| **A ★★★** | ★★★ | ★★★ (2.5→3) | ★★ |
| **A ★★** | ★★★ (2.5→3) | ★★ | ★★ (1.5→2) |
| **A ★** | ★★ | ★★ (1.5→2) | ★ |

| R 경계 | 근거 | 확인 수준 |
|---|---|---|
| 0.90 | 측정 잡음 밖의 열세. 단일 시나리오의 P99 비율은 5 seed에서 중앙값 ±15%(DP3 시뮬레이션 64개 비교의 95% CI 반폭 중앙값 14.7%) 흔들리고, 30여 쌍의 기하평균은 약 ±3%(15%÷√32)까지 줄어든다. 0.90은 그 3배 이상으로 잡은 보수 값 | 측정 [B+C] + 정책 |
| 1.20 | "잡음 폭(±10%)의 2배 = 확실한 개선". 같은 SLO 안에서 지연 20% 감소 | 정책 선택. 아래 주의 참고 |

- **왜 바꿨나**: v1(절대 SLO만)은 Baseline보다 크게 나빠져도 SLO 안이면 ★★★이었다(DP1 1안 = Affinity 없음: TTFT P99 ×1.27 나빠졌는데 ★★★). v2는 절대 수준(A)을 유지하면서 Baseline 대비 개선(R)을 같이 본다. 1안은 A ★★★, R ★(r = 0.86) → ★★.
- **이전 기준**: DP4 절대 SLO(공통 룰 §5). DP1·DP2는 6개 지표(TTFT·TPOT × P50/P95/P99)의 개선 배수 기하평균 ≥ 1.25 / 0.95. v2의 R은 P99 두 지표만 쓴다(DP4가 P99만 보고하므로 같은 지표로 맞춤).
- **정직한 주의**: (a) R 경계 1.20/0.90은 "기존 DP1·DP4 별과 합계를 보존한다"는 제약과 맞는 구간 안에서 골랐다: DP4 후보1(r = 1.11)을 ★★에 두려면 상한 > 1.11, DP1 C1(r = 0.948)을 ★★에 두려면 하한 ≤ 0.948, DP1 1안(r = 0.862)을 ★로 내리려면 하한 > 0.862. 이 안에서 1.20과 0.90은 잡음 폭으로 설명되는 값이지만, 구간을 정한 것은 결과를 본 뒤다(`defined_after_first_look`). (b) DP1 C1은 r = 0.948이라 하한 0.90까지 +5%밖에 안 남는다.

## 3.3 QA3 — 자원 (HBM 사용량)

**지표 (쉬운 말)**: **모델이 돌아가는 동안 HBM에 올라와 있는 Context KV의 평균 크기(GiB)**. 측정 구간 동안 HBM에 있는 KV 양을 계속 재서 시간으로 평균낸다(순간 최대가 아니라 평균). 예: 100초 중 40초는 100 GiB, 60초는 50 GiB 점유 → (40×100 + 60×50) ÷ 100 = **70 GiB**. 모델 가중치·활성값은 제외한다(KV만). 표기: HBM 사용량 감소 배수 = Baseline 값 ÷ 후보 값 (3.0이면 HBM을 1/3만 쓴다). DP1은 "HBM tier에 놓인 KV object 크기 × 머문 시간"을 구간 길이로 나눈 값, DP3는 "상주 Comp.KV 객체 + 요청이 쓰는 작업 사본"의 같은 시간 평균이다. 시나리오 쌍별 값의 기하평균. **성능을 섞지 않는다**: 성능÷비용 같은 효율 지표는 QA1·QA2와 겹쳐 쓰지 않는다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | 감소 배수 ≥ 1.25 | HBM 점유 20% 감소 = DP1 평균 146.6 GiB 중 약 29 GiB(8K KV object 약 1.6개분). QA2와 같은 "눈에 띄는 개선" 크기로 둔 정책 선택 | 환산 [C] |
| ★★ | 0.95 ≤ 감소 배수 < 1.25 | 하한 0.95: Baseline끼리 비교한 점유 잡음 범위 0.984~1.016보다 느슨하게 둠(5% 이내 증가는 열세로 보지 않음) | 측정 [B+C] |
| ★ | 감소 배수 < 0.95 | HBM을 5% 넘게 더 쓴다(잡음 밖) | 측정 [B+C] |

- **이전 기준**: DP1이 위 기준(v5)을 썼다. 공통 룰 §6은 "useful 활용률" 65%/85%인데 이동이 풀 전체 총량을 바꾸지 않아 DP1에서 처리량과 상관이 0.99라 별에 쓰지 않았다. DP3는 이 기준을 그대로 쓴다(DP3의 압축·재사용도 HBM 점유를 줄이는 것이 목적).
- **정직한 주의**: DP1은 QA3 정의를 결과를 본 뒤 여러 번 바꿨다(활용률 → 풀 U → 성능÷비용 → HBM 사용량). 모두 사후 변경이며 마지막 변경이 선택을 C2에서 C1로 바꿨다. 이 기준을 공통으로 승격하면 DP3부터는 사전 등록이 된다.

## 3.4 QA4 — 변경 용이성

**지표**: 변경 시나리오를 구현해 시나리오마다 세 값을 잰다. (M3) 코드 에이전트 토큰 비용(USD, mid tier $3/$15 per MTok), (M2) 개발 공수 MM(1 MM = 21 man-day), (M1) 변경 module 수. 시나리오 단순 평균 후 아래 **점수 S**로 합친다.

> **S = 0.5 × (비용 ÷ $0.5) + 0.3 × (공수 ÷ 0.5 MM) + 0.2 × (module 수 ÷ 2)**  (낮을수록 좋음)

각 항은 ★★★ 경계값으로 나눈 값(1.0 = ★★★ 경계)이고, 가중은 소유자 우선순위(**토큰 비용 > 공수 > module 수**)다.

| 별 | S 기준 | 도출 | 세 지표가 함께 만족하는 모습 |
|---|---|---|---|
| ★★★ | S ≤ 1.0 | 세 지표가 모두 ★★★ 경계(비용 $0.5, 0.5 MM, 2 module)에 있을 때 S = 0.5 + 0.3 + 0.2 = 1.0 | 한 지표가 경계를 넘으면 다른 지표가 그만큼 아래여야 한다. 예: 비용 $0.25(0.25)+공수 0.5 MM(0.3)+module 4(0.4) = 0.95 → ★★★ |
| ★★ | 1.0 < S ≤ 3.2 | 세 지표가 모두 ★★ 경계(비용 $2, 1.0 MM, 6 module)에 있을 때 S = 0.5×4 + 0.3×2 + 0.2×3 = 3.2 | 예: 비용 $0.5(0.5)+공수 1.0 MM(0.6)+module 2(0.2) = 1.3 → ★★ |
| ★ | S > 3.2 | 평균적으로 ★★ 경계도 넘음 | 예: 비용 $2(2.0)+공수 1.0 MM(0.6)+module 8(0.8) = 3.4 → ★ |

| 구성 요소 | 경계(★★★ / ★★) | 근거 | 확인 수준 |
|---|---|---|---|
| M1 module 수 | 2 / 6 | 공통 룰 §7 | 공통 룰 |
| M2 공수 | 0.5 MM / 1.0 MM | 0.5 MM = 엔지니어 1명이 2주 sprint 안에 흡수. 1 MM = 한 달 전담이면 로드맵 항목 | 사전 등록 가정 (DP1 `qa4-preregistration.md`) |
| M3 비용 | $0.5 / $2 (mid tier) | $0.5 = 원본 약 25k 토큰(module 약 3개 읽기 + 소규모 수정)을 한 세션에서 재작업 없이 끝내는 비용(유효 입력 재과금 6배, $3/$15 가정). $2는 그 4배 = 다중 세션·외부 코드 탐색 수준 | 사전 등록 가정 (DP4 pre-reg). 단가는 2차 자료(공식 가격 페이지 확인 필요) |
| 가중 0.5 / 0.3 / 0.2 | | 순서(비용 > 공수 > module)를 반영한 제안값. 토큰 비용은 에이전트 세션 로그에서 읽히는 가장 객관적인 비용, 공수는 토큰에 안 잡히는 사람 시간, module 수는 구조 영향의 대리 지표 | **소유자 결정**(조정 가능) |

- **서로 다른 비중이라는 점**: 세 지표는 같은 비중이 아니다. 같은 "경계 대비 2배"라도 비용이 2배면 S에 +0.5, 공수 2배면 +0.3, module 2배면 +0.2다. 한 지표가 나쁘면 다른 지표가 좋아서 보완할 수 있다(보완 관계).
- **이전 기준**: v1은 세 지표 각각의 별을 구해 "비중 50% 초과" 가중 중앙값으로 정했다(지표별 기준만 있고 교차 시 결과가 표에서 안 보였다). DP1·DP2는 frontier tier $3/$10과 중앙값, DP4는 mid tier $0.5/$2, man-day 3/7, 비용 우선 규칙이었다.
- **통합 방식**: 비용 mid tier, 공수 MM(DP4 man-day ÷ 21), 시나리오 단순 평균, 점수 S. 이 조합에서 DP1·DP2·DP4의 별이 모두 기존과 같다.
- **시나리오 집합**: "새 메모리 tier 추가"를 공통(S-공통)으로 두고 나머지 3개 이상은 DP별로 둔다.
- **정직한 주의**: (a) 공수·비용은 구현 측정(module·LOC)에 **가정 상수**를 곱한 값이며 실제 에이전트 세션 측정이 아니다[B+C]. (b) 선형 합이라 한 지표가 아주 나빠도 다른 지표가 0에 가까우면 ★★★이 가능하다(예: 비용 0, 공수 0, module 10 → S = 1.0). 그런 후보는 이번 DP들에 없지만 개별 지표 가드(어느 지표든 ★ 경계를 넘으면 ★★ 상한)를 둘지는 소유자 결정(D3)이다. (c) DP1 C2는 S = 1.05로 ★★★ 경계에서 5% 위다. (d) 가중 0.5/0.3/0.2는 제안값이다. DP4는 시나리오 가중(S2~S4 ×2)을 써도 별이 같다(`unified_stars_check.md` §3).

## 3.5 QA5 — 기능 정확성 (DP3 전용)

**지표**: F1 점수의 **상대 하락률** = (압축 전 + full recompute의 F1 − 후보의 F1) ÷ (압축 전 + full recompute의 F1). 같은 task·dataset·모델·precision에서 잰다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | 하락 ≤ 1% | 소유자가 정한 허용 정확도 저하 한도(압축 전 + full recompute 대비 F1 1% 이내, 상대 비율, 2026-10-09 확정) | 소유자 결정 |
| ★★ | 1% < 하락 ≤ 3% | **제안값**: 허용 한도의 3배. "눈에 띄는 열화"가 시작되는 구간으로 본다 | 정책 선택, **소유자 결정 필요**. 같은 task의 run-to-run F1 변동을 재서 하한을 확인해야 함 |
| ★ | 하락 > 3% | 허용 한도를 크게 넘은 정확도 손실 | 정책 선택 |

- **정직한 주의**: 두 번째 경계(3%)는 데이터로 도출하지 못했다. 문헌은 KV 압축을 "무시할 만한 성능 저하(negligible)"로 보고하지만(KVzip: 3~4배 KV 축소, 디코딩 지연 약 2배 감소, [NeurIPS 2025](https://neurips.cc/virtual/2025/oral/118742) 초록, 세부 F1은 확인 못 함) F1 하락의 일반적 임계는 없다. 따라서 경계는 소유자 결정이다.
- DP3 외 DP는 정확도를 변화시키지 않는 것이 전제이므로(출력 bit-exact) QA5 별 대상이 아니라 정합성 확인(QA-06 출력 정확성 시나리오)이다.

## 3.6 QA6 — 확장성 (DP4 전용)

**지표**: SE(N) = Goodput(N) ÷ ((N / N0) × Goodput(N0)), N0 = 2 노드, **N_max = 16**. N > 2는 모델 외삽(시뮬레이션, C-04)이다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | SE(N_max) ≥ 90% | 서버를 N배로 늘릴 때 처리량 손실 10% 이내(16노드 규모에서 14.4노드분 효과). 병렬 효율 논문에서 "효율적"이라 보고할 때 흔히 쓰는 90% | 문헌 [B]: [Cornell CVW](https://cvw.cac.cornell.edu/parallel/efficiency/scaling), [arXiv 1704.03329](https://arxiv.org/abs/1704.03329). 90%는 HPC 보고 관행이지 공식 표준이 아니다 |
| ★★ | 70% ≤ SE < 90% | 확장은 되지만 조율 계층이 병목 조짐. 70% 하한 = 10대 증설에 7대분 효과(3대분 낭비). 매우 큰 규모에서 70~80%도 "우수"로 보고한 사례 | 문헌 [B]: [arXiv 2409.16053](https://arxiv.org/abs/2409.16053) (65,536 GPU에서 80%) |
| ★ | SE < 70% | 손실 30% 초과 = 증설 비용의 1/3 이상 낭비. 조율 계층이 병목 | DP4 PPT 31장이 인용한 공통 QA 문서 §13의 임시 정의(현재 `qa-evaluation-criteria.md`에는 §13이 없다) [내부] |

- **이전 기준**: DP4가 위 기준. DP2는 `qa-criteria-dp2.md`에 η(N=32) 0.90/0.70을 제안값으로 두었다(경계 같음, N_max만 다름. DP2 PPT는 QA6가 선정 QA가 아니다). N_max를 16으로 통일하면 DP2도 같은 곡선으로 볼 수 있다.
- **정직한 주의**: DP4 후보 2의 ★(SE 64%)은 레플리카가 상태를 공유하지 않는 설계의 결과이며 보완(샤딩)이 있다. 별은 보완 전 기준이다. 후보 1도 Router가 전체 이벤트를 처리하는 구조라 비슷한 한계가 있을 수 있다.
