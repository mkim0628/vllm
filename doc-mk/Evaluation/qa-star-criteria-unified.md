# 공통 별 기준 v1 — 모든 DP에 같은 QA는 같은 기준

> 상태: **proposal** (소유자 확정 전). 작성: 2026-10-10.
> 목적: DP1~DP4의 같은 QA에 **같은 metric, 같은 집계, 같은 별 경계**를 적용해, 심사에서 "왜 별이 3개이고 2개인가"에 한 가지 기준으로 답한다.
> 이 문서는 `qa-evaluation-criteria.md`(공통 룰)를 바꾸지 않는다(SKILL H11). 공통 룰과 다른 경계는 §6에 표로 남기고, 소유자가 승인하면 DP별 criteria 문서(`qa-criteria-dp1.md` 등)가 이 문서를 가리키도록 맞춘다.
> 숫자는 `tools/unified_stars.py`가 `tools/unified_inputs.json`과 DP1·DP2 `results/data/qa4_modifiability.json`에서 만든다(`unified_stars_check.md`). 손으로 쓴 별은 없다.
> 번호는 사용자 PPT(2026-10-10)를 따른다: QA1 처리량, QA2 지연, QA3 자원(HBM), QA4 변경 용이성, QA5 기능 정확성, QA6 확장성. (요구사항 덱의 QA-05 확장성, QA-06 정확성과 번호가 서로 반대이므로 한쪽을 맞춰야 한다. §8.)

# 1. 원칙

1. **같은 QA는 DP와 무관하게 같은 metric·집계·경계를 쓴다.** 달라지는 것은 후보와 시나리오(Common Benchmark + DP 전용 benchmark, SKILL H3)이지 기준이 아니다.
2. **여러 시나리오·시스템은 쌍별 값의 기하평균으로 합친다**(공통 룰 §10). Baseline은 DP마다 다르다(대상이 다르다). 별은 항상 "후보 값 ÷ 같은 DP의 Baseline" 또는 절대 SLO로 매겨 DP 간에 의미가 같다.
3. **각 경계에 근거를 단다**: 측정(잡음 폭), 환산(자원·시간), 문헌/표준, 정책 선택 중 어느 것인지 밝힌다. 정책 선택은 정책 선택이라고 쓴다.
4. **별 합계가 높은 후보를 선택하고, 합계가 같을 때만 QA 우선순위(DP별)로 가른다**(SKILL H13). 합계 규칙은 모든 DP에 같다.
5. **별은 근거 수준과 분리해 표시한다**: 시뮬레이션 [B+C], Baseline 실측+시뮬레이션 [A+C], 변경 시나리오 환산 [C].

# 3. QA별 기준과 근거

## 3.1 QA1 — 처리량

**지표**: R = (후보의 Max SLO Goodput) ÷ (같은 DP Baseline의 Max SLO Goodput). Max SLO Goodput = SLO를 위반한 요청의 output token을 뺀 tok/s의 load sweep 최대값(공통 룰 §4). 시나리오 쌍별 R의 기하평균.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | R ≥ 1.30 | 같은 수요를 77% 이하의 자원으로 처리한다(자원 23% 이상 절감, 8-GPU 노드 기준 약 1.85 GPU). 추가 메모리 HW와 migration/라우팅 복잡도를 정당화할 크기라는 판단 | 환산 [C], 정책 선택. 결과를 본 뒤 정함 |
| ★★ | 0.97 ≤ R < 1.30 | 하한 0.97 = Baseline끼리 seed 묶음을 바꿔 비교한 20회 집계 범위 0.968~1.033의 아래 끝. 그 안은 잡음이라 열세로 보지 않는다 | 측정 [B+C] (DP1 `sim/star_basis.py`) |
| ★ | R < 0.97 | 잡음 밖의 열세: Baseline보다 느리다 | 측정 [B+C] |

- **이전 기준**: DP1 0.97/1.30(채택), DP2 0.97/1.30(DP1 값을 그대로 가져옴), DP4 0.90/1.10(공통 룰 §4.3 그대로).
- **통합 이유**: 상한은 보고된 모든 값에서 같은 별이 나오는 구간이 1.298 < U ≤ 1.423이다(DP1 C1 1.298 아래, C2 1.423 이하). 따라서 1.30은 이 구간 안의 값이며 DP1이 이미 쓰는 값이다. 하한은 0.97이든 0.90이든 보고된 값(최저 1.04)에서 별이 같다.
- **공통 룰(0.90/1.10)을 쓰면**: DP1 C1 QA1이 ★★ → ★★★로 바뀌어 DP1 별 합계 10 → 11이 된다(`unified_stars_check.md` §3).
- **정직한 주의**: (a) 1.30은 DP1 결과(C1 ×1.298, C2 ×1.423)를 본 뒤 정했다. C1이 경계에서 0.2% 아래다. 경계를 1.25로 하면 C1도 ★★★이다. (b) DP4는 Baseline이 실측([A])이지만 재측정 잡음 폭을 아직 재지 않았다. 0.97은 DP1 시뮬레이터의 잡음 폭이므로 DP4 실측 후 같은 방법(Baseline끼리 seed 묶음 비교)으로 확인해야 한다.

## 3.2 QA2 — 지연

**지표**: TTFT P99와 TPOT P99(시나리오 쌍별 값의 기하평균). **두 지표 중 낮은 등급**을 적용한다(공통 룰 §5). TTFT, TPOT는 별도 행으로 보고한다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | TTFT P99 ≤ 2 s 그리고 TPOT P99 ≤ 50 ms | 공통 기본 SLO. TTFT 2 s는 8K prefill 이론 시간 약 0.32 s(H100×8, MFU 0.45)의 약 6배라 큐잉·스케줄링 여유를 포함한 값이고 MLPerf Llama-2-70B 표준 시나리오(TTFT 2 s)와 같다. TPOT 50 ms = 초당 20 토큰, 성인 묵독 평균 238 wpm(≈ 5~6 tok/s, Brysbaert 2019)의 약 3.5배이고 MLPerf interactive(40 ms)와 표준(200 ms) 사이 | 표준·문헌 [B] (MLPerf 값은 2차 자료) |
| ★★ | TTFT P99 ≤ 4 s 그리고 TPOT P99 ≤ 100 ms | 기본 SLO의 2배 이내 = 체감은 느리지만 대화형 사용은 가능한 한계 | 정책 환산 [C] |
| ★ | TTFT P99 > 4 s 또는 TPOT P99 > 100 ms | 대화형 사용 한계 초과 | 정책 환산 [C] |

- **이전 기준**: DP4는 위 기준(공통 룰 §5). DP1·DP2는 6개 지표(TTFT·TPOT × P50/P95/P99)의 Baseline 대비 개선 배수 기하평균(★★★ ≥ 1.25, ★★ 0.95~1.25). DP1 후보 간 비교 때문에 만든 DP 전용 기준이었다.
- **통합 이유**: 절대 SLO 기준은 모든 DP에 같은 의미이고(공통 룰), DP1·DP2·DP4의 기존 별이 모두 그대로 나온다. 개선 배수 기준을 DP4에 쓰면 DP4 후보 2의 QA2가 ★★★ → ★★로 바뀌어 합계가 9 → 8이 되고 선택이 뒤집힌다(`unified_stars_check.md` §3).
- **개선 배수는 진단으로 남긴다**: 별에 쓰지 않고 병기한다. 또 **Baseline보다 나빠진 시나리오 쌍의 수와 최악 쌍**을 같이 보고한다(DP1 C1: TTFT P99 ×1.04, 21쌍 중 6쌍이 Baseline보다 나쁘고 최악 ×4.32).
- **정직한 주의**: (a) Baseline이 이미 SLO를 만족하는 DP(DP1)에서는 두 후보가 모두 ★★★이라 이 QA는 후보를 가르지 못한다(개선 배수 기준도 같았다). 가르는 것은 진단 값이다. (b) 기하평균 P99는 쌍별 꼬리를 평균하므로 한 쌍이 2 s를 넘는 경우를 가린다. 쌍별 위반 수를 병기해 보완한다. (c) DP4 후보 간 별 차이는 TTFT 2 s 경계를 사이에 둔 약 6%에서 갈린다(후보1 2,060 ms, 후보2 1,940 ms). ±3~4%에서 뒤집힌다.

## 3.3 QA3 — 자원 (HBM 사용량)

**지표**: HBM 사용량(GiB, 시간 평균 점유)의 감소 배수 = Baseline ÷ 후보. 시나리오 쌍별 값의 기하평균. **성능을 섞지 않는다**: 성능÷비용 같은 효율 지표는 QA1·QA2와 겹쳐 쓰지 않는다. 비우되 성능이 나빠지는 정책이 유리하므로 QA1·QA2와 함께 읽는다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | 감소 배수 ≥ 1.25 | HBM 점유 20% 감소 = DP1 평균 146.6 GiB 중 약 29 GiB(8K KV object 약 1.6개분). QA2와 같은 "눈에 띄는 개선" 크기로 둔 정책 선택 | 환산 [C] |
| ★★ | 0.95 ≤ 감소 배수 < 1.25 | 하한 0.95: Baseline끼리 비교한 점유 잡음 범위 0.984~1.016보다 느슨하게 둠(5% 이내 증가는 열세로 보지 않음) | 측정 [B+C] |
| ★ | 감소 배수 < 0.95 | HBM을 5% 넘게 더 쓴다(잡음 밖) | 측정 [B+C] |

- **이전 기준**: DP1이 위 기준(v5)을 썼다. 공통 룰 §6은 "useful 활용률" 65%/85%인데 이동이 풀 전체 총량을 바꾸지 않아 DP1에서 처리량과 상관이 0.99라 별에 쓰지 않았다. DP3는 이 기준을 그대로 쓴다(DP3의 압축·재사용도 HBM 점유를 줄이는 것이 목적).
- **정직한 주의**: DP1은 QA3 정의를 결과를 본 뒤 여러 번 바꿨다(활용률 → 풀 U → 성능÷비용 → HBM 사용량). 모두 사후 변경이며 마지막 변경이 선택을 C2에서 C1로 바꿨다. 이 기준을 공통으로 승격하면 DP3부터는 사전 등록이 된다.

## 3.4 QA4 — 변경 용이성

**지표**: 변경 시나리오를 시뮬레이터(또는 변경 설계)에 구현해 시나리오마다 세 값을 잰다. (M1) 변경 module 수, (M2) 개발 공수 MM(1 MM = 21 man-day), (M3) 코드 에이전트 토큰 비용(USD, **mid tier $3/$15 per MTok** 기준). 시나리오 **단순 평균**(가중 없음)에 경계를 적용한다.

| 별 | M3 비용 ($/변경) | M2 공수 (MM/변경) | M1 module 수 |
|---|---|---|---|
| ★★★ | ≤ $0.5 | ≤ 0.5 | ≤ 2 (주요 interface 유지) |
| ★★ | ≤ $2 | ≤ 1.0 | 2 초과 6 미만(3~5) |
| ★ | > $2 | > 1.0 | ≥ 6 또는 major interface 변경 |

**별 결정 규칙(가중 하한 중앙값)**: 비중은 사용자 우선순위 **토큰 비용 50% > 공수 30% > module 수 20%**. 별 s는 "s 이상인 지표들의 비중 합이 **50%를 넘을 때**" 얻는다. 그래서 가장 비중이 큰 토큰 비용 하나만으로는 별이 정해지지 않고(정확히 50%) 다른 지표 하나가 같이 받쳐줘야 한다.

| 경계 | 근거 | 확인 수준 |
|---|---|---|
| module 수 ≤2 / 3~5 / ≥6 | 공통 룰 §7 그대로 | 공통 룰 |
| 공수 0.5 / 1.0 MM | 0.5 MM = 엔지니어 1명이 2주 sprint 안에 흡수. 1 MM = 한 달 전담이면 로드맵 항목이 된다 | 사전 등록 가정 (DP1 `qa4-preregistration.md`) |
| 비용 $0.5 / $2 (mid tier) | $0.5 = 원본 약 25k 토큰(module 약 3개 읽기 + 소규모 수정)을 한 세션에서 재작업 없이 끝내는 비용(유효 입력 재과금 6배, $3/$15 가정). $2는 그 4배 = 다중 세션·외부 코드 탐색이 들어가는 수준 | 사전 등록 가정 (DP4 pre-reg), 토큰 단가는 2차 자료(공식 가격 페이지 확인 필요) |
| 가중 50/30/20 | 소유자 우선순위(토큰 비용 > 공수 > module 수). 토큰 비용은 에이전트 세션 로그에서 바로 읽히는 가장 객관적인 비용이고, 공수는 토큰에 안 잡히는 사람 시간, module 수는 구조 영향의 대리 지표 | 소유자 결정 |

- **이전 기준**: DP1·DP2는 M3를 frontier tier($15/$75) $3/$10, 별은 **세 sub-star의 중앙값**. DP4는 mid tier $0.5/$2, 공수는 man-day 3/7, 별은 **① 토큰 비용으로 먼저 정하고 같으면 ②③**, 시나리오 6개에 S2~S4 가중 2.
- **통합 방식과 이유**: (a) 비용은 mid tier로 통일(frontier/3과 같은 별이 나옴, DP1·DP2 모두 확인), (b) 공수는 MM으로 통일(DP4 man-day ÷ 21), (c) 시나리오는 단순 평균, (d) 별 결정은 위의 가중 하한 중앙값. 이 조합에서 DP1·DP2·DP4의 별이 모두 기존과 같다. DP4의 man-day 경계(3/7)를 쓰고 단순 평균을 쓰면 DP4 후보 2가 ★★★ → ★★로 바뀐다(`unified_stars_check.md` §3).
- **시나리오 집합**: "새 메모리 tier 추가"를 모든 DP 공통 시나리오(S-공통)로 두고, 나머지 3개 이상은 DP별로 둔다(새 data 종류, 정책 교체, 새 event, vLLM 계약 변경 등). 평균은 그 DP의 시나리오 전체에 대한 단순 평균이다.
- **정직한 주의**: (a) 공수·비용은 구현 측정(module·LOC)에 **가정 상수**를 곱한 값이며 실제 에이전트 세션 측정이 아니다[B+C]. (b) DP1 후보 2는 공수 0.506 MM이 경계 0.5를 1.2% 넘고 비용 $0.495가 경계 0.5의 1% 아래라서 두 값이 경계 양쪽에 걸려 있다. 공수가 0.5 아래였다면 별이 ★★★로 바뀐다(공수와 비용이 같이 ★★★이면 비중 80%). (c) DP4의 시나리오 가중(S2~S4 ×2)을 쓰든 안 쓰든 별은 같다(`unified_stars_check.md` §2).

## 3.5 QA5 — 기능 정확성 (DP3 전용)

**지표**: F1 점수의 **상대 하락률** = (압축 전 + full recompute의 F1 − 후보의 F1) ÷ (압축 전 + full recompute의 F1). 같은 task·dataset·모델·precision에서 잰다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | 하락 ≤ 1% | 소유자가 정한 허용 정확도 저하 한도(압축 전 + full recompute 대비 F1 1% 이내, 상대 비율, 2026-10-09 확정) | 소유자 결정 |
| ★★ | 1% < 하락 ≤ 3% | **제안값**: 허용 한도의 3배. "눈에 띄는 열화"가 시작되는 구간으로 본다 | 정책 선택, **소유자 결정 필요**. 같은 task의 run-to-run F1 변동을 재서 하한을 확인해야 함 |
| ★ | 하락 > 3% | 허용 한도를 크게 넘은 정확도 손실 | 정책 선택 |

- **정직한 주의**: 두 번째 경계(3%)는 데이터로 도출하지 못했다. 문헌은 KV 압축을 "무시할 만한 성능 저하(negligible)"로 보고하지만(KVzip: 3~4배 KV 축소, 디코딩 지연 약 2배 감소, [NeurIPS 2025](https://neurips.cc/virtual/2025/oral/118742) 초록, 세부 F1은 확인 못 함) F1 하락의 일반적 임계는 없다. 따라서 경계는 소유자 결정이다.
- DP3 외 DP는 정확도를 변화시키지 않는 것이 전제이므로(출력 bit-exact) QA5 별 대상이 아니라 정합성 확인(QA-06 출력 정확성 시나리오)이다.

## 3.6 QA6 — 확장성 (DP4 전용)

**지표**: SE(N) = Goodput(N) ÷ ((N / N0) × Goodput(N0)), N0 = 2 노드, **N_max = 16**. N > 2는 모델 외삽(시뮬레이션, C-04)이다.

| 별 | 기준 | 근거 | 확인 수준 |
|---|---|---|---|
| ★★★ | SE(N_max) ≥ 90% | 서버를 N배로 늘릴 때 처리량 손실 10% 이내(16노드 규모에서 14.4노드분 효과). 병렬 효율 논문에서 "효율적"이라 보고할 때 흔히 쓰는 90% | 문헌 [B]: [Cornell CVW](https://cvw.cac.cornell.edu/parallel/efficiency/scaling), [arXiv 1704.03329](https://arxiv.org/abs/1704.03329). 90%는 HPC 보고 관행이지 공식 표준이 아니다 |
| ★★ | 70% ≤ SE < 90% | 확장은 되지만 조율 계층이 병목 조짐. 70% 하한 = 10대 증설에 7대분 효과(3대분 낭비). 매우 큰 규모에서 70~80%도 "우수"로 보고한 사례 | 문헌 [B]: [arXiv 2409.16053](https://arxiv.org/abs/2409.16053) (65,536 GPU에서 80%) |
| ★ | SE < 70% | 손실 30% 초과 = 증설 비용의 1/3 이상 낭비. 조율 계층이 병목 | DP4 PPT 31장이 인용한 공통 QA 문서 §13의 임시 정의(현재 `qa-evaluation-criteria.md`에는 §13이 없다) [내부] |

- **이전 기준**: DP4가 위 기준. DP2는 `qa-criteria-dp2.md`에 η(N=32) 0.90/0.70을 제안값으로 두었다(경계 같음, N_max만 다름. DP2 PPT는 QA6가 선정 QA가 아니다). N_max를 16으로 통일하면 DP2도 같은 곡선으로 볼 수 있다.
- **정직한 주의**: DP4 후보 2의 ★(SE 64%)은 레플리카가 상태를 공유하지 않는 설계의 결과이며 보완(샤딩)이 있다. 별은 보완 전 기준이다. 후보 1도 Router가 전체 이벤트를 처리하는 구조라 비슷한 한계가 있을 수 있다.

# 5. DP3 — 평가가 없다

- `Evaluation/DP3`는 TBD(README, benchmark 틀뿐)이고 설계 문서(`doc-mk/DP3/*.md`, PPT)에도 정량 평가가 없다. 따라서 **별을 채울 값이 없다**. 문헌 수치(KVzip 3~4배 KV 축소, CacheBlend TTFT 2.2~3.3배 감소 등)는 다른 시스템·조건의 값이라 DP3 후보의 별 근거로 쓸 수 없다고 판단했다(SKILL H6, H16).
- DP3에 적용할 기준은 확정이다: QA2(§3.2, TTFT·TPOT P99 절대 SLO), QA3(§3.3, HBM 사용량 감소 배수), QA5(§3.5, F1 상대 하락). 측정하면 `unified_stars.py`가 같은 규칙으로 별을 낸다.
- 필요한 측정:
  1. **Baseline** = As-Is: 압축 없이 전체 Context KV를 재사용(PPT DP3 1장). 정확도 기준값은 압축 전 + full recompute.
  2. **시나리오**: 공통 벤치마크(CB-1~3) + DP3 전용(RAG/Agent 재사용 Context, 길이 32K~128K+ 등). 길이·재사용 횟수·질의 다양성(대표 Query와 실제 Query의 거리)을 변인으로 둔다.
  3. **QA2**: Comp.KV 로드(I/O) + 선택 재계산 + (2안은) Query×KV attention 시간 = TTFT 분해. 2안의 온라인 attention과 재계산 지연이 DP2 자원에서 실행되는 점을 반영한다.
  4. **QA3**: Context KV가 차지하는 HBM(GiB) 시간 평균. 저장 tier는 DP1이 정한다(Comp.KV 위치).
  5. **QA5**: task와 dataset 확정 필요(F1을 정의하는 QA 형태 benchmark. 미정).
- 결정 필요: DP3 평가를 시뮬레이션([B+C])으로 할지, 소규모 실측으로 할지. 지금은 둘 다 없다.
