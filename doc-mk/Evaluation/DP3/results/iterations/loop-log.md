**Trigger 발동**: C2는 TTFT·TPOT가 Baseline보다 나쁘다(집계 QA2 r = 0.88). C1은 집계는 이기지만 TTFT 2쌍(ST-06 H100·B200), TPOT 다수 쌍(ST-03·04·06·08·10 등)에서 Baseline의 95% CI 밖으로 진다. 손실 목록 49건은 `results/data/dp3_summary.json`의 `losses`.

사전 가설과의 대조:
- (a) "C2는 문맥이 짧고 적재가 싸면 TTFT가 Baseline보다 나쁘다" → **틀림(더 넓음)**: 8K뿐 아니라 거의 모든 시나리오(30쌍)에서 C2가 진다. 단 ST-06을 제외하면 손실 폭은 ×0.5~0.97이다.
- (b) "C1은 동시성이 늘어 TPOT 꼬리가 나빠진다" → **맞음**: C1 TPOT 손실은 ×0.57~0.94(ST-03, 04, 06, 08, 10, 11).
- 사전 가설에 없던 것: ST-06(HBF 직접 읽기)에서 C1·C2 모두 TTFT가 Baseline의 1/7~1/12.

## Iteration 1 (진단, 변경 없음)

- **(a) 진단**: C2가 지는 원인과 ST-06 손실을 가리기 위해 같은 코드로 선택 재계산을 끈 what-if를 돌렸다(`sim/sensitivity.py`, rho = 0, r = 0.30, 부하 × 1.0, 비교 가능 쌍).

| 정책 | TTFT 배수 H100 | TTFT 배수 B200 | ST-06 TTFT 배수 H100 / B200 |
|---|---:|---:|---:|
| C1 (rho = 0.15, 기본) | 1.70 | 2.68 | 0.07 / 0.13 |
| C1 (rho = 0) | 5.02 | 4.87 | 2.39 / 3.49 |
| C2 (rho = 0.15, 기본) | 0.87 | 0.84 | 0.06 / 0.11 |
| C2 (rho = 0) | 1.30 | 1.05 | 0.82 / 0.95 |

  → C2의 TTFT 손실과 C1의 ST-06 손실은 **선택 재계산(유지 토큰의 15%를 다시 prefill)** 비용이 지배한다. C2는 전체 KV를 적재하므로 적재 시간 절감이 없고 재계산 + 점수 계산이 그대로 TTFT에 더해진다. ST-06은 Baseline이 HBF를 GPU가 직접 읽어 적재 비용이 0에 가까워 재계산이 순손실이다.
  분류: **P(설계 속성)**. cost-model 오류(M)가 아니다(재계산 token 수 = rho·r·L, prefill 모델은 DP1 것). B/S/N으로도 해소되지 않는다(시나리오·profile·seed 문제 아님).
- **(b)~(c) 변경**: 허용되는 P 변경은 "설계 문서와 일치"해야 한다. rho를 줄이거나 C2에서 재계산을 빼는 것은 설계 문서(재계산 포함)를 바꾸는 일이고, 사전 등록 규칙이 정책 상수(r, rho) 재조정을 금지한다. 시나리오별 special-case(HBF에서는 압축 끄기)도 금지다. 따라서 **변경을 적용하지 않았다.**
- **(d)~(e)**: what-if는 진단이며 평가 결과에 넣지 않았다. 결과 문서 §5·§6에 민감도로 보고한다.
- **(f) 결정**: 사전 등록 규칙으로 허용되는 변경이 없어 loop를 여기서 멈추고 **결과를 그대로 보고하고 소유자에게 올린다**: (1) C2에서 선택 재계산이 필수인지(C2의 KV는 전체 문맥으로 계산된 값이라 재계산이 정확도에 얼마나 필요한지는 이번 평가로 알 수 없다. micro-benchmark는 재계산 없는 eviction 정확도만 측정했다), (2) 외부 tier가 GPU 직접 읽기(HBF)인 경우 압축을 끄는 정책을 DP3 설계에 넣을지.

중단 조건: (i) 충족하지 않음(C2는 Baseline 미만, C1도 ST-06 등에서 미만). (ii) 6 iteration에 도달하지 않았다. 사유는 위 (f)이며 SKILL의 중단 조건과 다르다는 점을 결과 문서에 명시했다.
