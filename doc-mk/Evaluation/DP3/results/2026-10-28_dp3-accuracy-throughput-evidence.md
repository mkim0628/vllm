# DP3 기능 정확성(QA5)과 처리량(QA1)을 함께 평가하는 근거

> 요청: PPT 67페이지 "기능 정확성(Accuracy) — F1 상대 하락률" 기준을 처리량과 같이 평가할 근거를 만들고, 품질 시나리오 목표 수치를 근거로 정한다.
> 기준 문서: `../../qa-star-criteria-unified.md`, `../simulation-plan.md`(사전 등록), `2026-10-11_dp3-qa-evaluation.md`(기존 결과, 덮어쓰지 않음).
> 이 문서의 모든 결합 수치는 **[B+C]**(처리량 시뮬레이션 + 소형 모델 정확도 매핑)이며 [A] 실측 결합이 아니다.

# 0. 최종 요약

**왜 따로 보면 안 되는가.** 압축 비율 r(유지 비율)이 하나의 노브로 처리량과 정확도를 반대 방향으로 움직인다. 기존 평가는 r=0.30 한 점에서 QA1과 QA5를 각각 별점 매겼기 때문에, "어느 r에서 정확도 제약을 지키면서 처리량이 얼마나 나오는가"가 보이지 않았다. 여기서는 같은 r 격자(0.1/0.2/0.3/0.5, 정확도를 실측한 값)에서 두 축을 한 표에 놓는다.

## 0.2 정확도 제약 하 처리량 R_acc (임시 정의, §2)

R_acc(X) = F1 하락 ≤ X%를 만족하는 r 중 최대 goodput 배수 (r=1.0 Baseline=×1.0 포함).

| 후보 | X=1% | X=2% | X=3% | 비고 |
|---|---:|---:|---:|---|
| C1 Offline | ×1.00 | ×1.00 | ×1.00 | 측정한 모든 r에서 F1 하락 12.5~39% → 어떤 X에서도 압축 이득을 쓸 수 없다 |
| C2 Online, 점추정 제약 | ×1.35 (r=0.1) | ×1.35 | ×1.35 | 점추정이 음수(개선)라 모든 r 통과, 최대 이득은 r=0.1 |
| C2 Online, CI 상한 제약 | ×1.00 | ×1.00 | ×1.00 | 반폭이 표본 부족(n=93)이라 r=0.5 외에는 1% 이하를 인증하지 못하고, r=0.5는 ×0.68 |

## 0.3 trade-off의 특징과 이유

- **C1은 처리량 후보, C2는 정확도 후보로 갈린다.** C1은 상주 KV를 r·L로 줄여 적재·admission을 줄이므로 r이 작을수록 goodput이 커진다(r=0.1에서 ×4.0). 그러나 대표 Query가 실제 Query와 어긋나면(repC) 필요한 토큰을 버려 F1이 크게 떨어진다(r=0.3에서 repB +6.9%, repC +37.4%, 매핑 평균 +17.0%). C2는 실제 Query로 점수를 매겨 정확도는 유지하지만 전체 KV를 적재하고 점수 계산·재계산이 요청 경로에 들어와 goodput 이득이 작다(r=0.3에서 ×0.99, r=0.1에서야 ×1.35).
- **r을 낮추면 정확도 쪽 불확실성이 처리량 이득보다 빨리 커진다.** C2 CI 반폭이 r=0.5에서 ±1.5%, r=0.3에서 ±4.8%, r=0.1에서 ±7.3%로 늘어난다(같은 n=93). 처리량 이득이 생기는 구간일수록 정확도 보증이 약하다.
- **곱셈형 합성 지표는 이 trade-off를 가린다.** F1을 곱한 goodput(QGP, 임시)은 C1 r=0.1에서 ×2.44로 모든 점 중 최고인데, F1이 39% 떨어진 설정이다. 정확도는 가중 합산이 아니라 **통과/실패 gate**로 두어야 한다. 그래서 목표를 R_acc 형식(§7)으로 잡았다.

## 0.4 결론 (선택이 아니라 현 상태 판정)

현재 후보 어느 쪽도 "F1 하락 ≤ 1%에서 goodput ≥ 2.0×"를 **인증하지 못한다**. C1은 정확도가 막고, C2는 처리량이 막는다(그리고 정확도 인증도 표본이 부족하다). 이 목표를 달성하려면 C1의 정확도 저하(대표 Query 불일치)를 줄이는 보완 또는 C2의 요청 경로 비용 감소가 필요하다. 보완 효과는 이 문서에서 수치로 주장하지 않는다([C] 미구현).

## 0.5 고려한 시나리오 (서술)

처리량 쪽은 기존 DP3 평가의 18개 시나리오(공통 8K 문맥 재사용 3종, 32K~256K 긴 문맥과 SSD·HBF·CXL 배치, 재사용이 몰린/분산된 경우, 질의가 긴/짧은 경우, 도중에 hot 문맥이 내려가거나 burst가 오는 경우)를 H100·B200 두 시스템에서 그대로 쓴다. 이 중 Baseline이 요청을 끝내지 못하는 4쌍은 기존 평가와 같이 제외해 32쌍이다. 정확도 쪽은 이 시나리오들이 아니라 **한 가지 task**(SQuAD 단락 질의응답, 문맥 약 1.4K token, 방해 단락 포함)이다. 따라서 "긴 문맥 256K의 정확도"는 아직 없는 시나리오이며 §6에 명시한다.

# 2. 평가 항목

| 항목 | 정의 | 출처 |
|---|---|---|
| G(c, r) = QA1 | 쌍별 Max SLO goodput(후보, r) ÷ Max SLO goodput(Baseline)의 기하평균. SLO = TTFT P99 ≤ 2 s, TPOT P99 ≤ 50 ms. 후보 goodput이 0인 쌍은 기하평균에서 빠지므로 개수를 따로 적는다 | unified §3.1 (기존 정의) |

# 5. 결과 분석

1. **C1이 정확도 gate를 못 넘는 이유 — 대표 Query 불일치.** r=0.3에서 같은 단락의 다른 질문(repB)은 +6.9%, 다른 단락의 질문(repC)은 +37.4%이다. 두 값을 mismatch m=0.331로 섞은 것이 +17.0%이다. repB만 써도(m=0) r=0.5에서 +5.2%로 3%를 넘으므로, 이 microbenchmark에서 **대표 Query 방식은 mismatch가 0이어도 ≤3%에 닿지 못한다**. (repB는 "같은 단락의 다른 질문"이라 실제 mismatch=0과는 다르다. 질문이 정확히 같은 경우는 aware에 해당한다.)
2. **C2의 음수 하락(F1 개선)은 정확도 이득이 아니라 이 benchmark의 구조일 가능성이 높다.** 문맥에 방해 단락 5~7개를 섞었으므로 질문 기반 eviction이 방해 단락을 걷어내는 retrieval 효과를 낸다. 단락 하나에 정답이 있는 SQuAD task라서 가능한 효과이며, 요약·다중 hop·코드처럼 전체 문맥이 필요한 task에서는 성립하지 않는다. 이 해석은 가설이며 이번에 검증하지 않았다.
3. **C2가 r=0.3에서 처리량 이득이 없는 이유.** 기존 결과 §5.1과 같다: 전체 KV 적재 + Query×KV 점수 계산 + 선택 재계산이 요청 경로에 들어온다. r을 0.1~0.2로 낮추면 작업 사본이 줄어 HBM 점유가 풀려 이득(×1.18~×1.35)이 생기지만, 이 구간의 정확도 CI가 가장 넓다.
4. **r=0.5에서 두 후보가 모두 Baseline보다 느린 이유.** 유지 KV가 커서 적재·HBM 절감이 줄고 재계산 prefill(0.15·r·L)은 커진다. C1 H100 TTFT가 r=0.5에서 ×0.60이던 기존 민감도와 같은 방향이다. ST-04(256K) H100 한 쌍은 두 후보 모두 SLO를 못 맞춰 goodput 0이다.
5. **문헌 위치.** KVzip은 query-agnostic 압축 후 재사용(multi-query)에서 30% 유지(70% eviction)까지 정확도를 유지한다고 보고하고, query-aware eviction 방법들은 multi-query에서 90% 유지에서도 열화된다고 보고한다(abstract + arXiv HTML 본문). 이는 두 가지를 말한다: (i) C2처럼 **요청마다 자기 Query로 압축하는** 구조는 재사용 이득이 없고(우리 시뮬레이션과 일치), (ii) C1처럼 **한 번 압축해서 여러 Query가 재사용하는** 구조가 정확도를 지키려면 단순 대표 Query attention 점수(우리 repA/repB)가 아니라 KVzip류 문맥 복원 기반 점수 같은 query-agnostic 중요도가 필요하다. 우리 C1 매핑은 단순 attention 점수라 KVzip의 점수 방식과 다르다.

# 6. 한계

1. **PPT 67p와 repo 기준이 다르다.** 67p는 ≤1% ★★★, ≤2% ★★, ≤3% ★. 73p는 "<" 부등호이고 ☆ 미충족 ≥3%를 둔다. `qa-star-criteria-unified.md` §3.5는 ≤1% ★★★, 1~3% ★★, >3% ★이다. 이 문서는 67p를 따랐고, 이 차이가 DP3 별점을 바꾼다(예: 하락 2.5%는 67p에서 ★, unified에서 ★★). 어느 쪽이 최종인지 확정이 필요하다(§8 Q-1). 또 2% 경계는 "정책 선택", 3%는 "KV 선택적 재계산 연구들의 실제 측정값 정확도 하락 3% 관측"이라고 67p에 적혀 있으나 그 연구와 수치의 출처는 이번에 찾지 못했다(미확인).
2. **시뮬레이터 재현성 결함 발견.** `dp3sim.py:112`가 `hash(sc.sid)`로 RNG를 만든다. Python 문자열 해시는 프로세스마다 달라서 같은 명령이 실행마다 다른 값을 낸다. 같은 설정(r=0.30)을 서로 다른 해시 시드로 두 번 돌린 결과, 쌍별 goodput 비율의 차이는 중앙값 C1 3.7%, C2 2.1%, 최대 C1 33%, C2 12%였다. 집계(32쌍 기하평균)는 C1 ×1.524 vs ×1.514, C2 ×0.992 vs ×0.987로 1% 이내라 기존 결론은 유지되지만, **기존 `dp3_qa1.json`·`dp3_results.json`은 비트 단위로 재현되지 않는다.** 이 작업은 `PYTHONHASHSEED=0`으로 고정하고 Baseline도 같은 실행에서 재계산해 비율을 만들었다. `dp3sim.py`는 수정하지 않았다(기존 결과를 조용히 바꾸지 않기 위해). 수정 여부는 소유자 결정이다(SKILL class M).
3. **정확도는 소형 모델·단일 task·n=93 [A 소형]**이다. 70B, 32K~256K, 요약·다중 hop·코드에는 값이 없다. 선택 재계산(rho=0.15)이 없는 eviction만 측정했으므로 실제 하락은 이보다 작을 수 있으나 검증하지 않았다. 표본이 작아 §4.3대로 1% 경계를 판정할 수 없다.
4. **정확도–처리량 결합이 r 하나에만 의존한다.** 처리량은 시나리오 18종, 정확도는 task 1종이다. 시나리오 mismatch m은 평균 0.331로 합쳤고 시나리오별 C1 정확도는 만들지 않았다. 문맥이 길수록 정확도가 달라지는 효과는 모른다.
5. **임시 정의** R_acc, QGP. 룰 문서에 추가하려면 결과를 보기 전 정의로 따로 등록해야 하며, 이번 정의는 분석 스크립트 docstring에 결과 실행 전 적었지만 문서 등록은 아니다.
6. **r 격자가 4점**(정확도 실측 격자)이다. C1이 2.0×가 되는 r≈0.23은 r=0.2와 0.3 사이를 log-log 선형 보간한 값 [C]이다.
7. 기하평균에서 0-goodput 쌍(r=0.5의 ST-04 H100)은 제외되므로 r=0.5의 G는 실제보다 높게 보인다(방향은 결론을 강화).
8. QA1의 SLO 값은 기존 평가(TTFT 2 s, TPOT 50 ms)와 같고 결과를 보고 바꾸지 않았다.

# 7. 결론과 목표 수치

## 7.1 판정

- 현재 후보로 **"정확도 게이트 통과 + 처리량 2×"는 달성되지 않는다.** C1: 정확도 미충족(하락 12.5~39%). C2: 점추정은 통과이나 인증 불가(n 부족) + 처리량은 r=0.1에서도 ×1.35.
- 이득이 존재하는 조건: C1의 처리량 이득은 r ≤ 0.3에서 모든 계열에서 나온다(r=0.3 common ×1.43, stress ×1.50, dynamic ×1.78). 그러나 이 조건에서 정확도 gate를 통과하지 못한다.

> **[정정 2026-10-28]** 아래 7.2의 목표는 PPT 67p의 1/2/3% 경계를 앞세운 초안이다. 사용자 정정("기존 1/2/3%를 무시하고 문헌 근거로")에 따라 **`doc-mk/Requirements/DP3-QS-accuracy-throughput-v2.md`의 문헌 기반 목표로 대체**한다. §0~§6의 측정 결과(r-sweep, R_acc, 재현성 결함)는 목표와 무관하므로 그대로 유효하다. §6-1과 §8 Q-1(별 기준 버전)도 v2 §5로 대체된다.

## 7.2 목표 수치 (근거 기반 제안, 사용자 확정 필요)

품질 시나리오 전문은 `doc-mk/Requirements/DP3-QS-accuracy-throughput.md`.

| 목표 | 값 | 근거 | 라벨 |
|---|---|---|---|
| 정확도 gate (필수) | F1 상대 하락 ≤ 1% (인증형: 95% CI 상한 ≤ 1%) | 소유자 확정 허용 한도 2026-10-09, 67p ★★★ | [DP문서]/[사용자] |
| 정확도 gate (하한) | ≤ 3% | 67p ★ 경계. 근거는 "정책" 성격이며 문헌 근거 없음(67p/73p 주석) | [기준], 근거 약함 |
| 처리량 (gate 통과 조건에서) | Max SLO goodput ≥ 2.0× Baseline | Stakeholder "2배 이상이어야 제품화 논의"(PPT 10p, 55p), 단순 offloading 문헌 하한 2.0~2.3× (InferCept 2.0, LMCache 2.3; PPT 55p 인용값, 원문은 이번에 확인하지 않음) | [DP문서]/[기준] |
| 달성에 필요한 r (참고) | C1은 r ≲ 0.23 (4.3× 압축) | 본 문서 보간 | [C] |

문헌 위치가 의미하는 것: 처리량 2× 목표와 정확도 1% 목표는 **현재 문헌이 보고한 안전 압축 구간의 경계에서 서로 부딪친다**. 같은 설계로 둘을 모두 만족하려면 4.3× 압축이 1% 안에서 가능해야 하는데, 직접 확인한 근거에는 그 수치가 없다(KVzip의 task별 상대 성능은 그림으로만 제시되어 수치를 확인하지 못함). 그래서 정확도 gate와 처리량 목표를 **같은 r에서 동시에** 요구하는 R_acc(1%) ≥ 2.0×를 달성 기준으로 두되, 달성 불가능할 수 있음을 사용자 확정 질문에 올린다.

## 7.3 다음 단계
