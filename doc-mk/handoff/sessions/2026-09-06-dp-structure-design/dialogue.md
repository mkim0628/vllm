## 결정 변수를 바꿔 양립 불가를 성립시켰습니다
기존 문서의 "Memory-Coupled vs Decoupled"는 사실 **C2가 C1의 상위호환**(바인딩을 1:1로 고정하면 C1)이라 제 스킬의 상위호환 테스트를 통과 못 합니다. 그래서 축을 **"capability 사실의 단일 진실 원천을 누가 소유하는가"** 로 다시 잡았습니다.

- **합성 테스트**: 진실 원천은 정의상 하나. 둘 다 두면 불일치 시 어느 쪽이 참인지 정의 불가 → 교차 검증 필요 → C1의 유일한 이점(조회 0회) 소멸. 합친 구조는 **두 후보 모두에 열등**합니다.
- **상위호환 테스트 (양방향)**: C2는 바인딩을 1:1로 고정해도 레지스트리 조회 의존이 남아 "메모리 핸들만으로 실행"이라는 C1 성질을 복원 못 함(캐싱해도 무효화 책임이 남음). C1은 capability가 타입 속성이라 인스턴스별·시점별로 다를 수 없어 C2를 흉내 못 함.

## 가장 날 선 논점
**CUDA graph 캡처가 C2의 실질 한계입니다.** decode 경로가 캡처되는 이상 C2는 리소스 선택을 캡처 이전(요청/배치 경계)으로 올려야 하고, 그러면 선택 granularity가 거칠어져 QA3의 이득이 스스로 줄어듭니다. 반대로 per-op 선택을 고수하면 캡처 조합이 51 × N으로 늘어 시작 시간과 메모리를 먹습니다. 9장 "판단이 갈리는 지점"에 이걸 명시해 뒀습니다 — 실제 리뷰에서 가장 먼저 찔릴 지점이라 선제적으로 열어두는 편이 낫다고 봅니다.

한 가지 추정치가 있습니다: "step당 약 16us"는 dict 조회 100ns × 160회 기준이라 부록 A에 추정임을 표시했습니다. 실측하려면 80-layer 모델 decode step에서 planner 조회를 마이크로벤치로 재야 하는데, 필요하시면 그 벤치 스크립트도 만들어 드리겠습니다.

## 1. "추상화인가?" — 맞습니다. 다만 추상화의 이름과 DP의 이름은 다릅니다

말씀하신 "얼마를 할당해라만 하면 런타임이 알아서 어디에 할당" 은 **요청과 배치의 분리(request–placement decoupling)** 라는 추상화이고, 그 계약은 "요청은 크기만 말한다"입니다. 그런데 이건 **이미 정해진 전제**지 DP에서 고를 대상이 아닙니다. DP는 "정할 게 두 개 이상 있고 어느 쪽도 명백히 낫지 않은 것"이어야 하는데, 이 분리 자체는 대안이 없습니다(스케줄러가 tier를 지정하면 스케줄러가 메모리 토폴로지를 알게 되므로).

그래서 이름을 **DP1 — Memory Placement Decision Basis (메모리 배치 결정 기준)** 으로 잡았습니다. 분리는 전제로 배경(1.2)에 넣고, DP가 고르는 건 "그 분리 안에서 런타임이 **무엇을 근거로** 위치를 정하는가"입니다. "추상화"를 제목에 넣으면 도메인 밖 독자에게 무엇을 정하는 DP인지 안 보입니다.

## 2. 상위호환 문제 — 축을 다시 잘랐습니다

지적하신 게 정확합니다. "tier 정보 기반 vs object 특성 기반"은 **C2 ⊃ C1**입니다. C2도 cost 계산 후 결국 tier를 고르니까요. 이대로면 대안이 아닙니다.

축을 **"정책을 무엇에 매다는가(인덱스 축)"** 로 바꿨습니다.

- **C1 — Tier-Indexed**: tier가 1급 개체, 요청은 **익명**. 불변식 = "자원 제약을 절대 위반하지 않는다"
- **C2 — Object-Indexed**: 객체 클래스가 1급 개체, tier는 **조정 대상**. 불변식 = "객체 클래스의 배치 계약을 지킨다"

배타성 논증 3중:

**(1) 불변식 충돌** — 상위 tier가 꽉 찬 상태에서 hot object가 도착하면 두 정책의 답이 **정반대**입니다. C1은 새 객체를 하위 tier로 흘리고, C2는 기존 cold를 밀어내고 자리를 만듭니다. 동시 성립 불가고, 우선순위를 정하는 순간 진 쪽은 tie-breaker로 격하 = 이미 하나를 고른 것.

**(2) 결정 단위 충돌** — C1은 할당 1건 단위, C2는 객체 단위(블록이 상속). 한 블록이 두 인덱스를 못 가집니다. 특히 `BlockPool.touch()`가 `ref_cnt += 1` 하는 **prefix cache 공유 블록**은 C2에서 특성 소유자가 여럿이라 미정의입니다.

**(3) 상위호환 반박** — 핵심입니다. C2가 tier 정보를 쓰는 건 맞지만:
- **정보에 대한 권한이 반대**입니다. C1에서 tier 상태는 불변 입력(하드 제약), C2에서는 비용 함수의 항이자 밀어내서 바꿀 수 있는 대상.
- C2가 C1을 흉내내려면 모든 객체를 단일 클래스로 분류해야 하는데, 그러면 **특성 추정 파이프라인 비용은 그대로 내면서 이득만 0** → C1보다 비싼 C1. 기능적으로 포개져도 상위호환이 아닙니다.
- 역방향은 원리적으로 불가: hotness/lifetime은 **할당 시점에 관측 불가능한 미래 정보**라 tier 상태만으로 유도 못 합니다.

> 한 줄로: **기능이 포개져 보여도 정보에 대한 권한과 정보 획득 비용의 축이 다르면 상위호환이 아니다.** C1의 정보 비용은 tier 수 T에 비례(요청 수 무관), C2는 요청 수 N에 비례.

## 4. 빠뜨리신 고민점 6가지 (부록 C)

가장 중요한 두 개만:

**① 할당 granularity가 전제와 충돌합니다.** vLLM은 "30GB를 한 번에" 주는 호출 지점이 없습니다. `allocate_slots(request, num_new_tokens)`로 **16토큰 블록 단위 점진 할당**이고(`DEFAULT_BLOCK_SIZE = 16`), 요청 총 사용량은 디코드하면서 늘어납니다. C2의 "할당 시점 정적 결정"이 성립하려면 객체를 **요청/시퀀스 단위로 정의하고 블록이 클래스를 상속**하는 구조여야 합니다. 그냥 "할당 시 결정"으로 두면 스텝마다 재분류가 되어 정적 전제가 깨집니다.

**② C1의 진짜 실패 모드는 herding입니다.** tier 상태를 스텝 경계에서만 갱신하면 그 스텝의 128건이 전부 같은 점수를 보고 **같은 tier로 몰립니다**. 이건 "매 스케줄마다 업데이트"로 안 풀리고, **스텝 내 예약 카운터**가 필요합니다. C2는 객체마다 분류가 달라 이 문제가 구조적으로 없습니다 — C2의 숨은 장점입니다.

나머지: ③ hotness/lifetime의 미래 정보 문제(→ 힌트 API로 풀면 요청 인터페이스 오염) ④ 공유 블록 소유자 ⑤ DP2와의 결합(배치가 곧 실행 가능성을 결정 — PNM에 놓으면 memory-side compute 대상. 객체 축엔 담기고 tier 점수엔 안 담김) ⑥ 재배치 주체(migration cost를 입력으로 쓰는 순간 "누가 옮기나"가 전제됨 → 범위 밖으로 명시).

"C2가 tier 정보를 쓴다 → C2 ⊃ C1" 이 참이면 C1은 **후보가 아니라 C2를 덜 쓴 상태**입니다. 그러면 DP가 성립하지 않습니다. 그래서 "C2가 tier를 읽는다"는 사실을 인정하면서도 포함 관계가 아님을 보여야 합니다.

```
신규 도착 R_new: 32K 토큰 문서 요약 prefill → 2000블록 필요, 매 스텝 attention에서 읽힘(hot)
```

## 반박 ① 같은 값을 읽어도 그 값에 대한 **권한**이 반대다

두 정책 모두 `avail_capacity[HBM] = 0`을 **읽습니다.** 그런데 읽은 뒤가 다릅니다.

| | C1 (Tier-Indexed) | C2 (Object-Indexed) |
|---|---|---|
| `avail[HBM]=0`의 의미 | **명령** — HBM은 후보에서 제거 | **가격표** — HBM을 쓰려면 eviction 비용 X를 내라 |
| 판정 | CXL에 배치 | 챗봇 세션 중 cold를 CXL로 demote → **R_new를 HBM에** |
| 기존 객체 | 건드리지 않음 | 밀려남 |

결과가 정반대입니다. C2는 tier 상태를 **보고 나서 그것을 바꿨습니다.**

> 포인트: `0`이라는 **같은 값**을 하나는 "불가능"으로, 하나는 "비용 X"로 해석합니다. 정보를 **읽는 것**과 정보에 **복종하는 것**은 다릅니다. C1에서 tier 상태는 결정을 구속하는 입력이고, C2에서는 결정에 의해 바뀌는 출력입니다. 이건 포함이 아니라 **화살표 방향의 반전**입니다.

한 문장으로: **C1은 자원이 객체를 이긴다, C2는 객체가 자원을 이긴다.** 같은 순간에 둘 다 이길 수는 없습니다.

## 반박 ② 동작을 재현해도 **비용이 남으면** 상위호환이 아니다

이게 가장 자주 나오는 반박입니다: "C2에서 모든 객체를 같은 클래스로 분류하면 C1이랑 똑같잖아?"

동작은 같아집니다. 남는 걸 세어 봅시다.

```python
# C2를 "C1처럼" 설정한 상태
def place(num_blocks, request):
    cls = classifier.classify(request)   # ← 여전히 호출됨
    tier = contract.target_tier(cls)     # ← 모든 클래스가 같은 답을 줌
    return pool[tier].get_new_blocks(num_blocks)
```

`classify()`를 채우려고 만든 것들이 그대로 남습니다.

- 요청 인터페이스에 추가한 힌트 필드 (`expected_output_len`, `priority_class` …) — API 표면은 이미 오염됨
- 과거 통계 저장소와 콜드스타트 처리
- 요청당 특성 벡터 유지 비용 (O(new_N·D))

즉 **C1의 동작 + C2의 비용**입니다. 이건 C1의 상위호환이 아니라 **C1보다 열등한 C1**입니다.
비용까지 없애려면 `classifier`를 삭제해야 하는데, 삭제하는 순간 그건 C2가 아니라 C1입니다.

> **상위호환의 정의**: 설정만 바꾸면 상대의 **동작과 비용을 모두** 재현하는 것. 동작만 재현하고 비용을 더 내면 그건 "포함"이 아니라 그냥 그 지점에서 진 겁니다.

비유가 정확히 들어맞습니다 — **자동변속기가 수동 모드를 지원한다고 수동변속기의 상위호환은 아닙니다.** 수동 모드로 놔도 토크컨버터 무게와 손실은 그대로 실립니다. SW로는 ORM이 raw SQL을 실행할 수 있어도 raw SQL의 상위호환이 아닌 것과 같습니다 (매핑 계층·세션 관리 비용이 남음).

## 반박 ③ 역방향은 **원리적으로** 불가능하다 (여기서 대칭이 깨지지 않음을 확인)

C1이 C2를 흉내내려면 `TierState.score()`가 객체를 봐야 합니다. 그런데 C1의 입력은 tier 상태 24개뿐입니다. 문제는 "안 넣어서"가 아니라 **넣을 값이 존재하지 않아서**입니다.

```
R_A: prompt 2000토큰, max_tokens=4096, temperature=0.7
R_B: prompt 2000토큰, max_tokens=4096, temperature=0.7   ← 파라미터 완전히 동일

실제 결과:
R_A → 100토큰 만에 EOS   (lifetime 짧음, 블록 7개)
R_B → 4096토큰 전부 생성  (lifetime 40배, 블록 256개)
```

할당 시점에 두 요청을 구분할 정보가 **시스템 어디에도 없습니다.** tier 상태 24개 값에는 당연히 없고, 요청 파라미터에도 없습니다. lifetime은 **실행해봐야 아는 미래 정보**입니다.

여기서 중요한 뉘앙스 하나 — 이 예에서는 **C2도 못 맞힙니다.** 둘을 같은 클래스로 분류해서 똑같이 틀립니다. 이게 QA2의 "관측 불가 지표 100%"가 뜻하는 바이고, 9장 선택 조건 (a) "요청 특성을 신뢰할 수 있는가"가 결정적인 이유입니다. **C2의 우위는 구분 가능한 신호가 실제로 있을 때만 실현됩니다.**

## 대칭성 확인 — C2가 지는 예 두 개

포함 관계가 아니라는 걸 보이려면 반대 방향도 필요합니다.

**(a) 오분류 고착.** 위 R_B가 `(hot, short)`로 분류되어 HBM 계약을 받았다고 합시다. 실제로는 4096토큰짜리 long이었습니다.

- **C2**: 계약이 HBM이므로 4096토큰 내내 HBM을 점유합니다. 그동안 진짜 hot·short 요청들이 CXL로 밀립니다. 특성이 정적이라 **교정 경로가 없습니다.**
- **C1**: 다음 스텝에 `avail[HBM]`이 줄어든 게 보이므로 이후 할당이 자연히 CXL로 흐릅니다. R_B의 기존 블록은 그대로지만 **시스템 전체는 균형으로 되돌아갑니다.**

**(b) 공유 블록.** 동일 system prompt 2000토큰을 쓰는 요청 100개 → prefix cache로 앞 125블록 공유, `ref_cnt = 100`.

- **C2**: 이 블록의 "객체"가 누구입니까? 100개 요청 중 hot 30 / cold 70이면 클래스는 무엇입니까? 병합 규칙(max / 다수결 / 합산)을 새로 정의해야 하고, 요청이 들락날락할 때마다 클래스가 바뀝니다 → **정적 특성 전제가 또 깨집니다.**
- **C1**: "누구 것"을 묻지 않으므로 문제 자체가 없습니다. 블록이 있는 tier와 남은 용량만 봅니다.

C1의 **익명성이 오히려 구조적 장점**이 되는 지점입니다. 양방향 모두 상대가 못 하는 게 있으니 포함 관계가 아닙니다.

## 일반화 — 상위호환 판정 3문항

다음 DP에서 후보 둘을 세울 때 그대로 쓰실 수 있게 정리하면:

1. **설정만 바꿔 상대의 동작을 낼 수 있는가?** → 아니오면 여기서 끝, 상위호환 아님.
2. 낼 수 있다면, **그때 상대의 비용까지 같아지는가?** → 비용이 남으면 상위호환 아님 (자동변속기 논리). 남는 비용을 구체적으로 열거할 수 있어야 합니다 — DP1에서는 힌트 API 필드, 통계 저장소, 요청당 특성 벡터.

## 1. 왜 블록이 아니라 요청을 분류하는가

블록이 생성되는 순간, 그 블록은 **"요청 R의 t번째 16토큰"** 일 뿐입니다. 블록 자신에게는 다른 블록과 구별될 정보가 없습니다.

특성 세 개를 하나씩 보면 전부 요청 속성입니다.

| 특성 | 실제로 무엇에 달려 있나 |
|---|---|
| **lifetime** | 요청이 끝나면 블록이 `free_blocks()` 됨 → **요청의 수명** |
| **hotness** | 앞으로 몇 스텝 동안 attention에서 읽히나 → **요청이 얼마나 더 생성하나** |
| **locality** | 어느 워커/GPU에 붙어 있나 → **요청의 배치** |

블록 100개를 나란히 놓고 "이 중 어느 게 hot이냐"를 물으면, 답은 전부 "그 블록이 속한 요청이 어떤 요청이냐"로 돌아갑니다. 그래서 분류 단위가 요청이 됩니다.

## 2. 그럼 요청을 무슨 기준으로 hot/cold로 나누나

**여기가 C2의 급소입니다. 정답은 "할당 시점엔 알 수 없어서 추정한다"입니다.** QA2의 "관측 불가 지표 100%"가 바로 이 뜻입니다. 실제로 쓸 수 있는 프록시는 이 정도입니다.

| 신호 | 예시 규칙 | 한계 |
|---|---|---|
| 요청 메타데이터 | `prompt_len > 8K && max_tokens < 512` → 문서 요약 = prefill-heavy, 짧은 수명 → **cold** | 같은 파라미터로 와도 실제 출력 길이는 40배 차이날 수 있음 |
| 세션 재방문 | 같은 `conversation_id`로 3회 이상 → 멀티턴 챗 = prefix 재사용 높음 → **hot** | 첫 방문은 판별 불가(콜드스타트) |
| 서비스 등급 | 유료 유저 / SLA 티어 → **hot** | 성능 특성이 아니라 정책. hotness와 무관할 수 있음 |
| 명시적 힌트 API | `priority="high"`, `expected_output_len=4096` | **요청 인터페이스 오염**. 사용자가 정확히 준다는 보장 없음 |
| 과거 통계 | 같은 엔드포인트의 과거 평균 출력 길이 | 저장소 추가, 워크로드 변하면 무효 |

전부 **간접 신호**입니다. 이게 "왜 C2가 이길 때만 이기는가"의 이유입니다 — 이 신호가 실제로 변별력이 있는 환경(내부 서비스, 유저 티어가 명확, 워크로드 패턴이 안정적)에서만 QA1 우위가 실현됩니다.

## 3. 이제 공유 블록 문제

세팅을 구체화하겠습니다.

```
같은 system prompt 2000 토큰 → 125 블록 (16토큰 × 125)
이 prefix를 hit 하는 요청 100개가 시간차를 두고 도착

R1  ~ R30  : 유료 멀티턴 챗 세션   → 분류 hot   → 계약 tier = HBM
R31 ~ R100 : 무료 단발 요약        → 분류 cold  → 계약 tier = CXL
```

**핵심**: 이 125개 블록은 **물리적으로 하나씩만 존재합니다.** vLLM의 prefix caching은 같은 해시의 블록을 재사용하는 것이지 복제하는 게 아닙니다. 두 번째 요청이 오면 새로 할당하는 게 아니라 `touch()`로 `ref_cnt`만 올립니다.

```python
# vllm/v1/core/block_pool.py
def touch(self, blocks):
    for block in blocks:
        if block.ref_cnt == 0 and not block.is_null:
            self.free_block_queue.remove(block)
        block.ref_cnt += 1          # ← 새 할당이 아니라 참조 증가
```

그래서 질문이 생깁니다: **이 125개 블록은 HBM에 있어야 하나, CXL에 있어야 하나?**

- hot 계약 30개는 "HBM에 있어야 한다"고 요구
- cold 계약 70개는 "CXL이면 충분하다"고 요구
- 블록은 하나뿐이라 **둘 다 만족시킬 수 없음**

### 시간축으로 보면 더 심각합니다

| 시점 | 상태 | C2가 내려야 할 판정 |
|---|---|---|
| t0 | R1(hot) 혼자 → `ref_cnt=1` | HBM에 배치 |
| t1 | R31~R100(cold) 합류 → `ref_cnt=71` | 다수결이면 CXL로 내려야? hot인 R1은? |
| t2 | R1~R30 종료 → `ref_cnt=70`, 전부 cold | 다시 판정? |
| t3 | 새 hot 요청 합류 → `ref_cnt=71` | 또 판정? |

**`ref_cnt`가 바뀔 때마다 재판정이 필요합니다.** 그런데 C2의 전제는 "특성은 할당 시점에 정적으로 결정된다"였습니다. 재판정을 넣는 순간 그 전제가 깨집니다.

### 병합 규칙을 정해도 전부 문제가 생깁니다

| 규칙 | 문제 |
|---|---|
| **max** (하나라도 hot이면 hot) | 무료 유저가 hot 요청 하나만 걸어두면 그 prefix가 계속 HBM 점유. 어뷰즈 가능 |
| **다수결** | hot 30개가 cold 70개에 밀려 CXL행. **C2의 불변식("객체 계약을 지킨다") 자체가 깨짐** |
| **가중 합산** | 재판정 시점이 필요 → 정적 전제 붕괴 |
| **최초 소유자 고정** | 우연히 먼저 온 요청이 125블록의 운명을 결정. C2의 강점인 **설명 가능성이 "우연"으로 변질** |

어느 규칙을 골라도 C2가 내세운 것(계약 준수, 정적 결정, 재현 가능한 설명) 중 하나를 포기하게 됩니다.

## 4. C1은 왜 이 문제가 없나

**C1에서는 공유 블록 hit 시 배치 결정이 애초에 일어나지 않습니다.**

`get_cached_block()`으로 이미 있는 블록을 찾아 `touch()`만 하는 경로에는 "어디에 놓을까"라는 질문이 없습니다. 그 블록은 이미 어딘가에 있고, C1은 **새로 할당하는 블록에 대해서만** tier 상태를 보고 결정합니다. 소유자를 묻지 않으니 소유자 충돌도 없습니다.

정리하면:

| | 공유 블록 hit 시 |
|---|---|
| **C1** | 배치 결정 **발생하지 않음** (참조만 증가) → 충돌 없음 |
| **C2** | "이 블록이 내 계약 tier에 있나?" 를 물어야 함 → 안 맞으면 옮길까 말까 → 100명의 계약이 충돌 |

C1의 **익명성**이 여기서 구조적 이점이 되는 이유입니다.

## 5. "그럼 블록 단위로 분류하면 되잖아?" — 그게 C1으로 수렴합니다

사용자님이 원래 생각하셨던 블록 단위 분류를 진지하게 따져보면 흥미로운 결론이 나옵니다. 블록 자신이 가진 **관측 가능한** 신호는 두 개뿐입니다.

**(a) 시퀀스 내 위치** — 오래된 블록 vs 최근 블록
- Sliding window 모델(`SlidingWindowSpec`)이면 윈도우 밖 블록은 안 읽힘 → 진짜 cold. 유효한 신호입니다.
- 그런데 Full attention(`FullAttentionSpec`)이면 **모든 블록이 매 스텝 전부 읽힙니다** → 위치의 변별력 0.
- 즉 이 신호는 **모델 아키텍처에 의존**하고, 주력인 full attention에서는 쓸 수 없습니다.

**(b) `ref_cnt`** — 많이 공유된 블록 = 재사용 많음 = hot. 좋은 신호이고 실제로 관측 가능합니다.
- 그런데 **할당 시점의 `ref_cnt`는 항상 1입니다.** 공유는 나중에 일어납니다 → 다시 미래 정보.
- `ref_cnt`가 올라갈 때마다 재평가하면? 그건 **런타임 상태를 보고 배치를 정하는 것** = C1의 정의입니다.

> **결론**: 블록 단위로 내려가면 관측 가능한 신호가 런타임 상태밖에 없고, 런타임 상태 기반 결정은 곧 C1입니다. **C2가 C2로 남으려면 분류 단위가 요청이어야 합니다.** 그리고 요청 단위여야 하기 때문에 공유 블록에서 소유자 충돌이 필연적으로 발생합니다.

이건 두 후보가 **granularity 축에서도 배타적**이라는 증거이기도 합니다 — 블록 단위 C2는 C2가 아니라 C1이니까요.

**문제**
- **인센티브가 한쪽으로만 작동합니다.** 공개 API면 전원이 `"hot"`이라고 씁니다. 자기 요청이 느려지길 원하는 사용자는 없으니까요. 막으려면 quota나 과금과 묶어야 하는데, 그러면 **배치 정책이 과금 정책과 결합**됩니다.
- 사내 서비스라도 호출하는 팀이 자기 워크로드의 hotness를 정확히 아는 경우는 드뭅니다.
- vLLM은 OpenAI 호환 API라 비표준 필드는 클라이언트 SDK·게이트웨이까지 전파됩니다. 하위호환 부담이 생깁니다.

**"기존 `priority: int` 필드를 재활용하면 되지 않나?"** — vLLM에 이미 있습니다(priority scheduling용). 하지만 **priority는 "스케줄 순서"지 "메모리 hotness"가 아닙니다.** 우선순위 높은 짧은 요청이 HBM을 차지하고 우선순위 낮은 long-context가 SSD로 가면 전체 처리량이 나빠집니다. 두 의미를 한 필드에 겹치면 나중에 분리할 수 없습니다.

## ② 휴리스틱 — 요청에서 추론한다

```python
def classify(req: Request) -> ObjectClass:
    n_prompt = len(req.prompt_token_ids)
    max_out  = req.sampling_params.max_tokens

    # 규칙 1: 긴 프롬프트 + 짧은 출력 → 요약/추출
    if n_prompt > 8192 and max_out < 512:
        return ObjectClass(hot=False, lifetime="short")

    # 규칙 2: 짧은 프롬프트 + 긴 출력 → 생성, 오래 살고 매 스텝 읽힘
    if n_prompt < 1024 and max_out > 2048:
        return ObjectClass(hot=True, lifetime="long")

    return ObjectClass(hot=True, lifetime="medium")   # 기본값
```

**문제 — 두 규칙의 신뢰도가 전혀 다릅니다.**

- **규칙 1은 비교적 안전합니다.** `n_prompt`는 할당 시점에 **이미 확정된 관측값**이니까요.
- **규칙 2는 대량 오분류합니다.** `max_tokens`는 **상한이지 실제 길이가 아닙니다.** 대부분의 클라이언트는 4096 같은 넉넉한 값을 넣고 실제로는 100~200토큰에서 EOS를 냅니다. `ignore_eos=True`인 벤치마크 요청에서만 `max_tokens == 실제 길이`입니다.

> 여기서 규칙이 나옵니다: **휴리스틱의 정확도는 그 규칙이 관측값에 얼마나 의존하는가에 비례합니다.** 미래(출력 길이)를 입력으로 쓰는 규칙은 거의 항상 약합니다.

## ③ 과거 통계 — 학습한다

키를 무엇으로 잡을지가 곧 설계입니다.

```python
key = (model, endpoint, lora_id, prompt_len_bucket)
stats[key] = {
    "p50_out_len": 210, "p95_out_len": 3900,
    "prefix_reuse_rate": 0.72,        # 이건 vLLM이 이미 아는 값에 가깝다
    "n": 1840,
}
```

`prefix_reuse_rate`는 prefix cache hit 통계에서 실제로 뽑을 수 있어 셋 중 가장 쓸 만한 신호입니다.

**문제**
- **콜드스타트**: 새 모델·새 엔드포인트·새 LoRA면 `n=0`. 기본값을 쓰게 되고, 그 구간에서는 **C1과 동작이 같아집니다** — 비용만 더 내면서.
- **분포 이동**: 낮에는 챗, 밤에는 배치 요약. 같은 키인데 분포가 바뀝니다. 윈도우/감쇠를 설계해야 합니다.
- **키 입도가 정확도를 지배**: 잘게 잡으면 샘플 부족, 굵게 잡으면 변별력 소멸.
- 저장소, 갱신 주기, TP/DP 워커 간 공유까지 전부 새로 만들어야 합니다.

## 1. 런타임 상태 기반 결정을 C2가 하면 안 되는 이유?

**금지된 게 아닙니다.** 정확한 표현은 "하면 두 후보의 차이가 사라진다"입니다.

구분해야 할 게 있습니다. C2가 tier 상태를 **비용 항으로 읽는 것**은 이미 C2 정의에 들어 있습니다(문서 3.3-③). 문제는 **재분류(reclassification)** 입니다. 실행해보고 특성을 갱신하면:

1. "특성은 정적"이라는 전제가 깨져 QA4(재현성) 강점이 사라지고
2. 갱신된 등급으로 옮기려면 migration 주체가 필요해 DP 범위가 넘치고
3. 무엇보다 **재분류의 입력이 런타임 관측이면, 그 관측을 tier 점수에 직접 쓰는 C1보다 한 단계 더 도는 것**일 뿐입니다

> DP에서 후보는 **순수한 극단**이어야 트레이드오프가 보입니다. 실제 구현은 중간 어딘가에 있을 수 있지만, DP 단계에서 중간값을 후보로 세우면 비교 자체가 무의미해집니다. "C2 + 런타임 재분류"는 좋은 구현일 수는 있어도 좋은 **후보**는 아닙니다.

## 2. 특성이 lifetime / hotness / locality뿐인가?

아닙니다. 그리고 **이 셋은 잘 고른 셋도 아닙니다** — 하필 관측 불가능한 것만 골랐습니다.

**할당 시점에 이미 아는 것들:**

| 특성 | 출처 | 왜 hotness와 관련되나 |
|---|---|---|
| **컨텍스트 길이** | `len(prompt_token_ids)` | 스텝당 읽는 KV 바이트를 직접 결정 |
| **prefix 캐시 히트 길이** | `get_computed_blocks()` — **allocate_slots 직전에 실행됨** | 이미 재사용되고 있다는 증거 |
| **attention 종류** | `FullAttentionSpec` vs `SlidingWindowSpec` | 슬라이딩 윈도우면 오래된 블록은 **아예 안 읽힘** = 확정적 cold |
| **KV dtype / 양자화** | `KVQuantMode` | 블록당 바이트 |
| `model` / `lora_id` | `lora_request` | locality의 실체 |
| spec decode 여부 | lookahead 토큰 | 추가 블록 요구 |

**끝까지 모르는 것들:** 남은 출력 길이, 총 재사용 횟수, 세션 지속 여부.

여기서 중요한 게 나옵니다. 제가 "관측 불가 100%"라고 쓴 건 **특정 특성 집합을 고른 결과**였지 C2의 본질이 아닙니다. 다만 커플링이 있습니다 — **구분력이 큰 특성일수록 미래 정보입니다.** 관측 가능한 것만 쓰면 안전하지만 hot/cold를 제대로 못 가르고, 잘 가르려면 추정 오류를 안습니다. 이게 C2 내부의 진짜 트레이드오프입니다.

## 3. expected 출력 길이는 어떻게 예측하나?

정직하게: **할당 시점에 잘 예측하는 일반적 방법은 없습니다.** 실제로 쓰이는 것들:

- `max_tokens` — 상한일 뿐. 상관관계 매우 약함
- 과거 통계 p50/p95 by (endpoint, model, prompt_len_bucket) — 정상 구간에선 쓸 만, 콜드스타트/분포이동에 취약
- 프롬프트 기반 길이 예측기(작은 regressor) — 논문은 있으나 편차 큼
- **구조화 출력**: `response_format`이 JSON schema면 길이 상한이 실질적으로 좁아집니다. vLLM의 `structured_output_request`가 있으면 이건 **꽤 강한 신호**입니다
- `stop` 시퀀스 존재 여부

> 결론: 출력 길이는 **C2의 가장 약한 고리**입니다. lifetime 특성을 쓰겠다면 이 예측 정확도를 먼저 측정해야 하고, 측정 없이 설계하면 QA1 별점이 근거를 잃습니다.

## 4. `reuse: "session"` — 맞습니다, 잘못된 예시였습니다

멀티턴이면 prefix caching이 당연히 동작하고, **그 사실을 vLLM이 이미 압니다.** `get_computed_blocks()`가 히트 길이를 세서 `allocate_slots`에 넘기니까요. 사용자가 알려줄 이유가 없습니다.

여기서 규칙이 하나 나옵니다:

> **힌트 API에 넣을 값은 "시스템이 관측할 수 없는 것"뿐이어야 한다.**

- ❌ prefix 재사용 여부, 컨텍스트 길이, 모델 — 이미 앎. 힌트로 받으면 API만 오염
- ⭕ 이 세션의 **다음 턴이 올 것인가**, SLA 등급, 예상 출력 길이 — 모름

## 5. "긴 프롬프트 + 짧은 출력" — 두 군데 다 틀렸습니다

### (a) 태스크를 맞히려 한 것 자체가 잘못

QA일 수도, 코드 리뷰일 수도, 분류일 수도 있습니다. 그리고 **어떤 태스크인지는 배치에 필요 없습니다.** 필요한 건 "KV가 얼마나 오래 살고 얼마나 자주 읽히나"뿐입니다. 규칙은 태스크 이름이 아니라 **KV 접근 패턴**으로 써야 합니다.

### (b) cold라고 한 건 계산해보면 틀렸습니다

```
A: prompt 32K, 출력 200      B: prompt 1K, 출력 4096
```

| 지표 | A | B |
|---|---|---|
| 총 KV 읽기량 | 200 × 32.8K ≈ **6.6M** | Σ(1K+t) ≈ **12.6M** |
| **스텝당 읽기 대역폭** | **32,768 토큰** | 평균 ~3,072 토큰 |
| 블록당 읽히는 횟수 | 모든 블록 200회 균일 | 앞 블록 4096회 ~ 뒤 1회 |

A는 **매 스텝 32K 전체를 읽습니다** (full attention). 하위 tier에 놓으면 스텝 지연이 그대로 직격탄입니다. 어느 정의로 봐도 "cold"가 아닙니다.

그럼 왜 A를 하위 tier로 밀고 싶어질까요? **크기가 커서**입니다. 32K × 100요청이면 HBM을 다 먹으니까요.

> 즉 제 규칙 1은 **hotness를 재는 척하면서 실제로는 capacity를 재고 있었습니다.** 그리고 capacity는 C1이 이미 보는 값입니다 — C2의 고유 이점이 아닙니다.

옳게 쓰려면 hotness를 두 개로 쪼개야 합니다:
- **읽기 빈도** = 남은 디코드 스텝 수 (← 미래 정보, 약함)
- **스텝당 대역폭** = 컨텍스트 길이 (← **관측 가능, 강함**)

둘은 tier 요구가 다릅니다. 대역폭이 병목이면 컨텍스트 긴 요청이 상위 tier로 가야 하고, 용량이 병목이면 반대입니다.

```
1    L1     2048   HBM       5952     HBM      ← 8192가 아니라 5952에서 시작

4    L4     2048   HBM       -192     CUSTOM_HBM   ← 밀려남
```

**결정적 장면은 스텝 4입니다.** `HBM 여유 = -192`. short들이 넘겨서 채운 겁니다.

## 손익 계산

```
short 24개가 HBM 차지  =   768 블록
그 때문에 밀려난 long   =  2048 블록 (1개)

대역폭 요구량 (peak/스텝):
  short 24개 = 24 × 576 토큰  = 13,824
  long   1개 =      32,968 토큰 = 32,968     ← 2.4배 손해
```

**작은 요청 24개를 올리려고 큰 요청 1개를 내린 셈인데, 대역폭 요구량으로는 절반 넘게 손해입니다.**

## 그래서 세 방식의 차이는

| | 무엇을 보나 | 크기를 어떻게 다루나 |
|---|---|---|
| **C1** | 자원 상태 (점수) | 페널티가 **크기에 비례** → 큰 요청의 발자국이 작은 요청을 밀어냄 |
| **C2 아래로만** | 등급 (계약) | 크기와 무관, 등급만 봄 → long이 상위 tier 독점 |
| **C2 상향** | 등급 + 빈자리 유무 | **크기를 아예 안 봄** → 32블록이 2048블록과 동등하게 경쟁 |

핵심은 이겁니다:

> **"빈 자리 있으면 위로"는 자리만 보고 요구량을 안 봅니다.** 요구량 대비 점유 효율이 나쁜 작은 객체가 상위 tier를 잠식합니다. C1의 점유율 페널티는 그걸 "자리를 쓰는 만큼 비싸진다"로 흉내내고 있었던 거고요.

## 2. overcommit

**tier 용량보다 많은 블록을 커밋하는 것**입니다. 프로토타입에서는 커밋 후 `used[tier] > capacity_blocks`가 되면 카운트합니다.

```python
def commit(self, placement):
    self.used[placement.tier] += placement.blocks
    if self.used[placement.tier] > self.specs[placement.tier].capacity_blocks:
        self.overcommits += 1     # ← 없는 메모리를 약속했다
```

**왜 생기나** — 스텝 내 stale view 때문입니다.

```
HBM 용량 8192블록,  한 스텝에 200개 요청 도착 (각 64블록)

예약 없음:  결정 #1~#200 전부 "HBM 여유 8192"를 봄  (스텝 시작 시점 값)
            → 전부 HBM 선택 → 200 × 64 = 12,800블록 커밋
            → 8192를 4,608블록 초과   ← overcommit 72회 발생
```

**실제 시스템에서 무슨 일이 벌어지나** — 이건 통계 지표가 아니라 **버그**입니다. 없는 메모리를 배치하겠다고 약속한 거라서, 실제로는 allocation 실패나 OOM이 나거나, 스케줄러가 요청을 preempt해야 합니다.

**중요한 점**: C1의 불변식은 "**자원 제약을 절대 위반하지 않는다**"였습니다. overcommit은 C1이 **자기 정의를 스스로 어긴 것**입니다. 그래서 스텝 내 예약 카운터(유보 A)가 "있으면 좋은 완화책"이 아니라 **C1 정의의 일부**라고 문서를 고친 겁니다.

## 1.1 배경 — "메모리는 한 종류"라는 전제

**할당 인터페이스가 크기만 받습니다.** 위치를 표현할 인자가 없습니다.

```python
def allocate_slots(self, request, num_new_tokens, ...) -> KVCacheBlocks | None
def get_new_blocks(self, num_blocks: int) -> list[KVCacheBlock]
def get_num_free_blocks(self) -> int      # ← 가용량 관측 지표가 정수 하나
```

블록은 단일 free queue 앞에서 순서대로 꺼내지고, **다 차면 배치를 바꾸는 게 아니라 요청을 preempt** 합니다.

> 전제: **"메모리는 한 종류이고, 부족하면 배치가 아니라 스케줄로 해결한다"**

`kv_offload`가 CPU 계층을 다루지만 이 전제를 안 깹니다 — 그건 배치가 아니라 **사후 이동(load/store)** 이고, 정책도 LRU/ARC처럼 **이미 발생한 접근 이력** 기반입니다.

> 이 분리 자체는 **전제**입니다. 스케줄러가 tier를 지정하면 스케줄러가 메모리 토폴로지를 알아야 하니까요.

## 후보 대표 도면 — [C]의 `???`에 무엇을 두는가

두 후보가 **같은 골격**을 갖고, **Placer에 무엇이 물려 있는가**만 다릅니다.

```
Candidate 1 — Tier-Indexed (자원 축)

    Scheduler ──"n 블록"──► Placer ──► HBM / DRAM / CXL / SSD
                              ▲
                         Tier 상태표          ← 자원이 결정한다
```

|---|---|---|
| **1** | 상위 모듈이 **추상이 아니라 구체**에 의존 | `hasattr(connector, ...)` = "이 커넥터가 특정 구현이면". 인터페이스에 없는 메서드를 찾는 순간 스케줄러는 구체 구현의 존재를 안다 → **DIP 1번 위반** |
| **2** | **추상화가 세부에 의존** | 메서드 이름에 `gpu`가 박혀 있다. 계층이 늘면 `bind_cxl_pool`, `bind_hbf_pool`... → **DIP 2번 위반** |
| **3** | **자기 선언 위반** | `KVCacheBlocks` docstring: *"to hide KVCacheManager's internal data structure from the Scheduler"*. 그런데 스케줄러가 `kv_cache_manager.block_pool`을 직접 꺼내 넘긴다 |

추가 증거: `allocate_slots(..., num_external_computed_tokens)` — KVCacheManager가 **"외부 메모리"의 존재를 이미 안다.**

## 그래서 논증이 바뀝니다

**전(가정법, 약함)**
> 지금은 깨끗하다. 6-tier로 확장하면 깨진다.

**후(실증, 강함)**
> **위반은 이미 있다.** 메모리 계층이 **1개에서 2개(GPU + CPU offload)로 늘어난 바로 그 지점**에서 생겼다.
> 계층이 6개가 되면 **같은 방식으로 5번 더 반복된다.** `hasattr(connector, "bind_cxl_pool")`, `bind_hbf_pool`, ...

YAGNI 반박이 봉쇄됩니다 — "언제 올지 모르는 요구"가 아니라 **"이미 한 번 일어났고 그 흔적이 코드에 남아 있다"** 가 됩니다. 그리고 **위반의 증가율이 계층 수에 비례**한다는 게 확장 비용의 실체입니다.

제가 앞서 "지금은 DIP 지켜져 있다"고 한 건 **핵심 할당 경로(`block_id`, `allocate_slots`)만 보고 커넥터 바인딩 경로를 안 봤기** 때문입니다.
