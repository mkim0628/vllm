# Phase 0~1 — 관련 QA 선정과 문제 정의

## Phase 0. 관련 QA를 먼저 뽑는다

문제 정의는 "무엇이 나빠지는가"의 서술이다. 그 "무엇"이 QA이므로 **QA가 문제 정의보다 먼저** 나온다.

### 선정 규칙
1. **이 DP의 결정 변수에 의해 실제로 갈리는 QA만** 고른다. 두 후보 모두 같은 점수가 나올 QA는 축이 아니다.
2. 3~5개. 6개를 넘으면 별점이 평균으로 수렴해 트레이드오프가 흐려진다.
3. 각 QA는 **질문형 한 문장**으로 정의한다. ("~가 얼마나 작은가 / 얼마나 유연한가")
4. 각 QA에 **정량 프록시**를 반드시 붙인다. 프록시가 없으면 Phase 5에서 정량 근거를 쓸 수 없다.
5. 상위 DP에서 이미 쓴 QA를 관성적으로 재사용하지 않는다. 이 DP의 쟁점이 다르면 QA도 달라야 한다.

### QA 후보 풀과 정량 프록시

| QA 계열 | 질문형 정의 예 | 정량 프록시 예 |
|---|---|---|
| Runtime Efficiency / Latency | 요청이 실제 실행으로 dispatch되기까지의 control overhead가 얼마나 작은가 | op 1회당 indirection hop 수, lookup 횟수, 분기 수, 예상 us |
| Throughput / Scalability | 동시 요청·리소스 증가 시 성능이 어떻게 유지되는가 | 임계 구간 lock 수, batch당 순차 단계 수, O(n) 항의 n |
| Resource Utilization | 가용 리소스를 상황에 맞게 얼마나 활용하는가 | 선택 가능한 리소스 후보 수, 부하 분산 가능 조합 수 |
| Flexibility / Composability | 다양한 조합·토폴로지를 얼마나 표현할 수 있는가 | 표현 가능한 관계(1:1 / 1:N / N:M) 수, 조합 추가 시 코드 변경 여부 |
| Extensibility | 신규 타입·기능 추가 시 기존 추상화 변경이 얼마나 적은가 | 신규 1건 추가 시 수정해야 하는 인터페이스/클래스/파일 수 |
| Maintainability | 변경의 파급 범위가 얼마나 좁은가 | 변경 시 영향받는 모듈 수, 순환 의존 수 |
| Predictability | 실행 경로와 지연이 얼마나 예측 가능한가 | 경로 분기 수, 최악/최선 경로 hop 차이 |
| Testability | 단위 검증이 얼마나 쉬운가 | 테스트 시 mock 해야 하는 컴포넌트 수 |
| Memory Footprint | 구조 유지 비용이 얼마나 작은가 | 메타데이터 엔트리 수 × 엔트리 크기 |
| Portability | 다른 HW/백엔드로 옮길 때 비용이 얼마나 작은가 | HW 종속 코드가 존재하는 레이어 수 |

프록시는 **두 후보 사이에서 값이 달라야** 의미가 있다. 값이 같아질 프록시면 QA를 재정의한다.

## Phase 1. 문제 정의

### 구성 (이 순서를 지킨다)

1. **배경**: 현재 구조/시스템이 무엇을 어떻게 하고 있는가. 사실만.
2. **변화**: 새로 들어온 요구·하드웨어·워크로드. 여기서 전제가 깨진다.
3. **문제**: 그 결과 무엇이 성립하지 않는가. 구체적·명확하게.
4. **발생 위치**: 런타임 스택의 어느 레이어인가.
5. **QA 영향**: Phase 0에서 뽑은 QA 각각이 어떤 방향으로 얼마나 나빠지는가.
6. **문제 한 문장**: 위를 한 문장으로 압축.

1→2→3은 **빌드업**이어야 한다. 각 문단 앞에 "그래서"를 붙여도 자연스럽게 읽히면 통과, 갑자기 문제가 튀어나오면 실패다.

### 런타임 스택 위치 지목

문제가 "시스템 어딘가"에 있으면 설계할 수 없다. 레이어를 지목해야 설계 범위가 확정된다.
vLLM 기준 레이어 예시(대상 시스템이 다르면 해당 시스템의 레이어로 대체):

```text
API / Entrypoint (OpenAI server, LLM class)
        ↓
Engine  (EngineCore, Scheduler, 요청 수명주기)
        ↓
Executor / Worker  (분산, 프로세스·디바이스 배치)
        ↓
ModelRunner  (입력 준비, forward 실행, CUDA graph)
        ↓
Attention / Kernel  (backend 선택, 커널 dispatch)
        ↓
Memory  (KV cache, BlockManager, BlockTable, allocation)
        ↓
HW Abstraction  (Platform, device/memory resource)
```

서술 형식: **"문제는 <레이어>에서 발생한다. 이 레이어는 <역할>을 담당하는데, <변화> 때문에 <가정>이 더 이상 성립하지 않는다."**

### QA 영향 서술 형식

각 QA마다 한 줄:

> **<QA>**: <현재 값/동작> → <문제 발생 후 값/동작>, 즉 <프록시 지표>가 <얼마> 악화된다.

정성 표현 금지. 아래 대비를 참고한다.

| 나쁨 | 좋음 |
|---|---|
| 성능이 떨어진다 | op 1회당 metadata lookup이 1회에서 3회로 늘어난다 |
| 확장이 어렵다 | 신규 백엔드 1종 추가 시 3개 인터페이스와 5개 호출 지점을 수정해야 한다 |
| 구조가 복잡해진다 | Memory–Compute 관계가 N:M이 되어 조합 수가 리소스 수의 곱으로 증가한다 |
| 유연성이 부족하다 | 현재 추상화로는 1:1 관계만 표현 가능해 1:N 토폴로지를 등록할 수 없다 |

### 그 외 명시해야 할 것 (해당되면)
- **제약**: 변경 불가능한 상위 인터페이스, 호환성 요구, 성능 예산(예: op당 control overhead < X us).
- **가정**: 워크로드 특성, HW 토폴로지 가정. 후보 선택 조건과 직결되므로 반드시 남긴다.
- **범위 밖**: 이 DP에서 다루지 않는 것. 후보 비교의 공정성을 위해 필요하다.
- **관련 DP**: 상위 DP의 결정으로 이미 고정된 것.

## Phase 2. 설계 쟁점

문제 정의 다음은 "그래서 무엇을 설계할 것인가"이다. 형식:

> 위 문제는 <레이어>에서 <무엇>이 <어떻게> 표현되지 않기 때문에 발생한다.
> 따라서 이 DP에서는 **<결정 변수>** 를 설계한다.
> 설계 질문: **"<X>를 <누가 소유 / 어디에 배치 / 언제 결정>할 것인가?"**

- 결정 변수는 **하나**다. 두 개면 DP를 쪼갠다.
- 쟁점 문장에 후보 이름(예: "Coupled 방식")을 쓰지 않는다. 답을 선점하면 후보 비교가 형식화된다.
- 배타적 결정 변수인지 확인은 `phase2-candidates.md`의 3-테스트로 한다.
