# DP 구조 설계 규칙

DP 문서는 **"문제 → 쟁점 → 두 후보 → QA 트레이드오프 → PPT 한 장"** 의 단일 사슬이다.
뒤 단계의 재료는 전부 앞 단계에서 나온다. 순서를 바꾸거나 단계를 건너뛰면 사슬이 끊기고,
결과물은 "특징 나열표"로 퇴화한다.

## 실행 순서

| Phase | 산출물 | 참조 |
|---|---|---|
| 0. 관련 QA 선정 | QA 3~5개 + 각 QA의 **정량 프록시** | `references/phase1-problem.md` |
| 1. 문제 정의(배경) | 배경→변화→문제 흐름, 런타임 스택 위치, QA 영향 | `references/phase1-problem.md` |
| 2. 설계 쟁점 | 배타적 **설계 결정 변수** 1개 | `references/phase2-candidates.md` |
| 3. 두 후보 구조 | 후보명, 한 문장 특징, 대표 구조도 | `references/phase2-candidates.md` |
| 4. 다이어그램 | 모듈뷰/컴포넌트/시퀀스/클래스 + 설명 | `references/diagrams.md` |
| 5. 트레이드오프 | QA × 후보 별점 매트릭스 + 정량 근거 | `references/qa-tradeoff.md` |
| 6. PPT 페이지 | 2열 × 5행 비교 표 1장 | `references/ppt-page.md` |

문서 뼈대는 `templates/dp-doc-template.md`를 그대로 복사해서 채운다.
산출 경로는 `doc-mk/vllm-dp<N>-<slug>.md` (기존 `doc-mk/vllm-dp2-candidate-qa-tradeoff.md`와 동일 규약).

## 사슬 규칙 (이 스킬의 핵심)

```text
Phase 0 QA  ────────────────────────────►  Phase 5 평가축
   (여기서 정한 QA 외에 새 축을 만들지 않는다)

Phase 2 결정 변수 ──────────────────────►  Phase 3 두 후보
   (두 후보 = 같은 변수의 서로 다른 값. 다른 축이면 후보가 아니라 별개 DP)

Phase 4 다이어그램 ─────────────────────►  Phase 5 정량 근거
   시퀀스   → hop / lookup / indirection 횟수      → 성능계 QA 근거
   클래스   → 확장 시 수정 인터페이스·클래스 수    → 확장성계 QA 근거
   컴포넌트 → 표현 가능한 조합·인스턴스 수         → 유연성/활용성 QA 근거
```

별점을 매길 때 근거가 다이어그램에서 안 나온다면, 별점이 아니라 다이어그램이 부족한 것이다.

## 게이트 체크리스트

각 Phase 종료 시 아래를 스스로 검사한다. **하나라도 실패하면 다음 Phase로 가지 말고 그 Phase를 다시 쓴다.**

### Gate A — 문제 정의 (Phase 0~1)
- [ ] 이 DP에서 갈리는 QA를 3~5개 **먼저** 뽑았고, 각 QA에 측정 가능한 정량 프록시가 붙어 있다.
- [ ] 배경 → 환경/요구 변화 → 문제 발생이 한 흐름으로 읽힌다. 문단 사이에 "그래서/따라서"를 넣어도 어색하지 않다.
- [ ] 문제가 발생하는 **런타임 스택 레이어를 정확히 지목**했다(하나, 많아야 인접한 둘).
- [ ] 각 QA가 **어느 방향으로 얼마나** 나빠지는지 숫자·횟수·범위로 썼다. ("성능이 떨어진다" 같은 정성 표현 금지)
- [ ] 문제 진술이 한 문장으로 압축된다.

### Gate B — 설계 쟁점 (Phase 2)
- [ ] 쟁점이 **설계 결정 변수 1개**로 표현된다: "X를 누가 소유할 것인가 / 어느 레이어에 둘 것인가 / 언제 결정할 것인가".
- [ ] 쟁점 문장에 후보 구조 이름이 들어 있지 않다(답 선점 금지).
- [ ] 이 쟁점을 풀면 Phase 1의 문제가 실제로 해소된다는 연결이 한 줄로 설명된다.

### Gate C — 두 후보 구조 (Phase 3)
- [ ] 두 후보가 **같은 결정 변수의 서로 다른 값**이다.
- [ ] **양립 불가 논증**이 문서에 있다: 두 구조를 합치려 하면 왜 불가능한지, 또는 합치는 순간 왜 한쪽의 이점이 소멸하는지.
- [ ] **상위호환 아님**: 한 후보의 설정을 바꿔 다른 후보의 동작을 그대로 흉내 낼 수 없다.
- [ ] 각 후보에 한 문장 특징(굵게)이 있다.

### Gate D — 다이어그램 (Phase 4)
- [ ] 대표 구조도: 도형 **7개 이하**, 도메인 용어 최소, 두 후보가 **같은 시각 문법**(같은 추상화 수준·같은 진행 방향)으로 그려졌다.
- [ ] 도메인을 모르는 사람에게 대표 구조도만 보여줘도 "무엇이 무엇을 결정하는 구조인지" 전달된다.
- [ ] 백데이터 4종(모듈뷰·컴포넌트·시퀀스·클래스)이 후보별로 있고, 각각 3~5줄 설명이 붙어 있다.
- [ ] 시퀀스는 두 후보가 **동일 시나리오**를 그린다(hop 수 비교가 성립해야 하므로).

### Gate E — 트레이드오프 (Phase 5)
- [ ] 평가축이 Phase 0의 QA와 **정확히 동일**하다. 새 축 추가 금지, 누락 금지.
- [ ] 3점 별점(★★★/★★☆/★☆☆)으로 평가했다.
- [ ] 모든 셀에 **숫자가 들어간 근거**가 있고, 그 숫자의 출처 다이어그램이 특정된다.
- [ ] **지배(dominance) 없음**: 모든 QA에서 한 후보가 우세하지 않다.
- [ ] 각 후보가 최소 1개의 ★★★를 가진다.
- [ ] 총점 차이 ≤ 2 (비등). 초과하면 QA 축이 한쪽에 편향된 것이므로 Phase 0으로 돌아간다.
- [ ] 두 후보가 같은 별점인 QA는 변별력이 없으므로 축에서 빼거나 더 날카롭게 재정의한다.

### Gate F — PPT 페이지 (Phase 6)
- [ ] 한 페이지, 표 1개. 가로 = 후보 1 / 후보 2, 세로 = 후보 구조 이름 / 대표 구조도(간단) / 장점 / 단점 / TRADEOFF 관계.
- [ ] 표 안의 대표 구조도는 본문보다 더 축약된 **도형 5개 이하** 버전이다.
- [ ] TRADEOFF 행은 "A ↔ B" 대구 한 문장이다.

## 흔한 실패와 교정

| 증상 | 원인 | 교정 |
|---|---|---|
| 한 후보가 전 QA에서 우세 | 후보가 아니라 개선안을 나열함 | Phase 2로 복귀, 배타적 결정 변수 재설정 |
| "둘을 합치면 되지 않나?" 질문에 답 못함 | 결정 변수가 배타적이지 않음(add-on 축) | `references/phase2-candidates.md`의 3-테스트 재적용 |
| 트레이드오프가 특징 나열이 됨 | QA 축 없이 서술 | Phase 0 QA로 축을 고정하고 별점 매트릭스부터 작성 |
| 별점 근거가 "복잡하다/단순하다" | 다이어그램이 얕음 | 시퀀스·클래스 다이어그램을 먼저 그려 숫자를 뽑음 |
| 대표 구조도가 UML처럼 빽빽함 | 백데이터와 대표 구조도를 혼동 | 대표 구조도는 PPT 도형 수준으로 축약, 상세는 백데이터로 |
| 문제 정의가 추상적 | 런타임 스택 위치 미지목 | Gate A의 레이어 지목 항목 재작성 |
